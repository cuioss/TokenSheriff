== Overall Assessment

This is an unusually well-maintained documentation set. Link integrity is excellent — a full scan found *zero broken xref/link file targets and zero broken anchors* across all files, including every `#COMMONS-N`/`#CLIENT-N`/`#VALIDATION-N.M`/`#T-*` anchor and every `link:` code-file reference in the threat models and CVE register. Every file carries the mandated TOC header block, requirement-ID schemes are explicit about non-sequential numbering, and deep sampling shows the specification documents (commons transport/error/observability, client flows, JWE, MP-JWT, health checks, config reference) match the code to a degree rarely seen — down to class names, defaults, and test-class references.

The weaknesses are concentrated: the *entry-point* documents (root `README.md`, `AGENTS.md`, `doc/client/README.adoc`, the `doc/README.adoc` hub) lag behind corrections already made in deeper documents; `doc/LogMessages.adoc` misses two production Quarkus log records and documents a real duplicate-identifier bug; and a stale "128 KB buffer" parser limit survives in two security documents. The most user-impacting defect is a quick-start configuration example that does not work as written.

== Findings

[#D-1]
=== D-1: Quick-start configuration examples omit the mandatory `enabled=true` — the documented minimal setup fails at first use

[cols="1,4"]
|===
|Severity |*major* (first-contact user experience; broken example)
|Confidence |high — verification verdict: PARTIALLY CONFIRMED (example brokenness confirmed; "fails at startup" corrected to "fails at first use", see xref:adversarial-verification.adoc[verification report])
|Location |`README.md:92-97`; `token-sheriff-validation-quarkus/README.adoc` (~108-138, "Basic Configuration" and "Multiple Issuers" YAML examples)
|===

The minimal example shows only `sheriff.token.issuers.keycloak.jwks.http.well-known-url=…`. But issuers default to *disabled*: `IssuerConfigResolver.java:169-174` (`.orElse(false); // Default to disabled — require explicit enabled=true`) and line 122 throws `IllegalStateException("No enabled issuer configurations found")`. The extension's own config reference gets it right ("Issuers must be explicitly enabled (default is disabled)", `META-INF/quarkus-config-doc.adoc:14-15`). The README examples as written do not work: the `IllegalStateException` surfaces at first use — the first `@BearerAuth` request or health probe — rather than at deployment, because no eager startup validation exists (see xref:code-review-quarkus-benchmarking.adoc#Q-3[Q-3]).

[#D-2]
=== D-2: `doc/client/README.adoc` still carries a claim other documents explicitly retracted as false ("issues no HTTP of its own")

[cols="1,4"]
|===
|Severity |*major* (hub-level drift contradicting corrected deeper docs)
|Confidence |high
|Location |`doc/client/README.adoc:19-20`; also `token-sheriff-client/README.adoc` (~55), `client/package-info.java:29`, `doc/commons/README.adoc:22-24`, `doc/README.adoc:30`
|===

The client hub states "The engine owns two aspects and delegates the rest — it issues no HTTP of its own". This exact claim is explicitly retracted elsewhere: `doc/client/requirements.adoc:56` ("It is *not* true that the client 'issues no HTTP of its own.'") and `doc/client/architecture.adoc:138-141` ("an earlier revision claimed the engine 'issues no HTTP of its own.' That claim was false and is corrected here"). The code confirms the retraction: `client/internal/BackChannelHttp.java` drives `java.net.http.HttpClient` directly.

The same stale framing survives in `token-sheriff-client/README.adoc` ("outbound bytes travel through the commons transport base layer" — the client imports only `ParserConfig` from that package), in `doc/commons/README.adoc` ("Transport … *all* outbound IdP HTTP (discovery, JWKS, token, userinfo, revocation, introspection, end-session, PAR)"), and in the hub `doc/README.adoc`. The corrected framing (commons owns discovery + JWKS; the client owns its own back channel) lives in `doc/commons/requirements.adoc` COMMONS-1, `doc/commons/architecture.adoc:39-41`, `doc/commons/specification/transport.adoc:17-19`, and `doc/client/threat-model.adoc:39-43`. Classic multi-file drift: the correction was applied to the spec layer but not to the hub/README layer above it.

[#D-6]
=== D-6: Stale "buffer size (128 KB)" parser limit in two security documents

[cols="1,4"]
|===
|Severity |*major* (security documents describing a removed mechanism)
|Confidence |high
|Location |`doc/validation/security-reference.adoc:51`; `doc/validation/threat-model.adoc:92, 223`; `ParserConfig.java:80-103, 204-205`
|===

Both documents claim `NonValidatingJwtParser` enforces "token size (8 KB), payload size (8 KB), string size (4 KB), buffer size (128 KB)". No 128 KB constant exists anywhere in main code; `ParserConfig` defines maxTokenSize 8 KB, maxPayloadSize 8 KB, maxStringLength 4 KB, maxNestingDepth 10, maxArraySize 1000, with DSL-JSON buffers bounded via `limitStringBuffer(maxStringLength)` and `limitDigitsBuffer(16)`. The 8/8/4 numbers are correct; "buffer 128 KB" is a leftover.

[#D-8]
=== D-8: Wrong default for `dpop.nonce-cache-ttl-seconds` in the config reference

[cols="1,4"]
|===
|Severity |minor
|Confidence |high
|Location |`META-INF/quarkus-config-doc.adoc:75`; `DpopConfig.java:58, 191-192`; `IssuerConfigResolver.java:405-409`
|===

Default listed as `300`; the actual builder default is `DEFAULT_NONCE_CACHE_TTL_SECONDS = 360` (proof max age 300 + 60 s skew), and `DpopConfig.build()` silently raises any configured TTL below `proofMaxAgeSeconds + 60` to that minimum — so even an explicit 300 becomes 360. Code is stricter than documented; the doc is wrong in both the default and the implied configurability. Cross-reference: xref:javadoc-review.adoc#J-8[J-8] (same defect in the property-key Javadoc).
