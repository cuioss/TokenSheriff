== Overview

During the WRK integration benchmarks, Prometheus scrapes CPU, memory, thread and JWT metrics from the Quarkus application. After each benchmark, the metrics of exactly that benchmark's time window are queried, aggregated into statistics and written as one JSON file per benchmark. The JMH micro-benchmarks run without the Quarkus application and collect no server metrics.

== System Architecture

[source]
----
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│   WRK           │────▶│  Quarkus App     │◀────│   Prometheus    │
│  (Load Gen)     │     │  :8443/jwt       │     │   :9090         │
│                 │     │  :8443/q/metrics │     │  (2s scrape)    │
└─────────────────┘     └──────────────────┘     └─────────────────┘
        │                                                  │
        ▼                                                  ▼
┌─────────────────┐                          ┌─────────────────────┐
│  WRK results    │                          │  Time-Series        │
│  (start/end ts) │                          │  Metrics Data       │
└─────────────────┘                          └─────────────────────┘
        │                                                  │
        └──────────────────┬───────────────────────────────┘
                           ▼
                ┌──────────────────────┐
                │  MetricsOrchestrator │
                │  + Transformer       │
                └──────────────────────┘
                           │
                           ▼
                ┌──────────────────────┐
                │ {name}-server-       │
                │      metrics.json    │
                └──────────────────────┘
----

1. **Prometheus** scrapes `/q/metrics` every 2 seconds (`token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests/prometheus.yml`; target `token-sheriff-integration-tests:8443` inside the Docker network, HTTPS with `insecure_skip_verify: true` for the self-signed certificate; the host port `10443` maps to `8443`).
2. Each **WRK benchmark script** embeds `benchmark_name`, `start_time` and `end_time` in its result file.
3. **WrkResultPostProcessor** reads them and calls **PrometheusMetricsManager**, which first checks that Prometheus answers at `prometheus.url` (default `http://localhost:9090`).
4. **MetricsOrchestrator** queries the Prometheus range API for the benchmark window with a 2-second step.
5. **BenchmarkMetricsTransformer** aggregates the time series into statistics.
6. **MetricsJsonExporter** writes `prometheus/{benchmarkName}-server-metrics.json`; the post-processor copies it to `gh-pages-ready/data/`.

The classes are in `benchmarking/benchmarking-common/src/main/java/de/cuioss/benchmarking/common/metrics/`; `PrometheusClient` performs the `query_range` calls.

== Collected Metrics

[cols="2,3,1"]
|===
|Metric |Description |Type

|`process_cpu_usage`
|Process CPU utilization (0.0-1.0)
|Gauge

|`system_cpu_usage`
|Container CPU usage (0.0-1.0)
|Gauge

|`system_cpu_count`
|CPU cores available to the container
|Gauge

|`jvm_memory_used_bytes`, `jvm_memory_committed_bytes`, `jvm_memory_max_bytes`
|Memory usage (the output reports the heap area)
|Gauge

|`jvm_threads_live_threads`, `jvm_threads_daemon_threads`, `jvm_threads_peak_threads`
|Live, daemon and peak thread counts
|Gauge

|`jvm_gc_overhead`
|GC overhead (0.0-1.0)
|Gauge

|`sheriff_token_validation_success_operations_total`
|Successful JWT validations by event type
|Counter

|`sheriff_token_validation_errors_total`
|JWT validation errors by category
|Counter

|`sheriff_token_bearer_token_validation_seconds_count` / `_sum`
|JWT validation count and total validation time
|Counter (histogram-derived)
|===

== CPU Percentage Interpretation

IMPORTANT: CPU percentages are relative to the cores allocated to the container, not to the host. 100% means all allocated cores are fully used.

[cols="1,2,3"]
|===
| Value | 4-Core Container | Interpretation

| 25%
| 1 core fully utilized
| Single-threaded or low load

| 50%
| 2 cores fully utilized
| Moderate load, good headroom

| 85%
| 3.4 cores utilized
| Heavy load (typical JWT validation)

| 98-100%
| ~4 cores fully utilized
| CPU saturation, throughput limited
|===

`process_cpu_usage` covers the application process only, `system_cpu_usage` the whole container.

== Error Handling

Metrics collection never fails the benchmark build:

* Prometheus unreachable at start-up: collection is skipped with a warning.
* A benchmark without complete start/end metadata: no metrics file for that benchmark, logged as an error.
* A failed Prometheus query: logged as an error; the other benchmarks and the reports are still produced.
