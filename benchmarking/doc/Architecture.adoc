== benchmark-integration-wrk

Performs HTTP load testing with WRK. Orchestration is done by Maven and shell scripts; the only Java class is `WrkResultPostProcessor`, which converts WRK output to `BenchmarkData`, collects Prometheus metrics for each benchmark window and generates the reports.

The Maven build uses scripts from two locations:

* `token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests/scripts/` - container lifecycle (`start-integration-container.sh`, `stop-integration-container.sh`) and `dump-keycloak-logs.sh`
* `src/main/resources/wrk-scripts/` - `pre-benchmark-health-check.sh`, the benchmark scripts (`health_live_benchmark.sh`, `jwt_benchmark.sh`, the ablation and JFR dispatchers) and `fetch_tokens.sh`

Container services:

[source]
----
Quarkus:     https://localhost:10443
  /jwt/validate    - JWT validation endpoint
  /q/health/live   - Health endpoint
  /q/metrics       - Metrics endpoint

Keycloak:    https://localhost:1443
  /realms/...      - Token issuance

Prometheus:  http://localhost:9090
  /api/v1/query    - Metrics API
----

== Data Flow

[source]
----
Benchmark Execution (JMH or WRK)
        │
        ▼
Converter (JmhBenchmarkConverter / WrkBenchmarkConverter)
        │
        ▼
BenchmarkData (unified model)
        │
        ├──> ReportGenerator → HTML pages
        │      └──> ReportDataGenerator → data/benchmark-data.json,
        │             history archive, BadgeGenerator → badges/*.json
        └──> GitHubPagesGenerator → 404.html, robots.txt, sitemap.xml, api/*.json
        │
        ▼
target/benchmark-results/gh-pages-ready/
----

The WRK path additionally collects Prometheus metrics for each benchmark window through `PrometheusMetricsManager`, writes them to `prometheus/` and copies them into `gh-pages-ready/data/`.

== Code Placement

[source]
----
Does the code generate reports/badges/artifacts?
├─YES─> benchmarking-common/report/
│
├─NO──> Does it collect or transform metrics?
│       ├─YES─> benchmarking-common/metrics/
│       │
│       └─NO──> Does it manage configuration?
│               ├─YES─> benchmarking-common/config/
│               │
│               └─NO──> Is it a JMH benchmark?
│                       ├─YES─> benchmark-core/
│                       │
│                       └─NO──> Is it WRK-related?
│                               ├─YES─> benchmark-integration-wrk/
│                               │       (or use shell scripts)
│                               │
│                               └─NO──> benchmarking-common/util/
----

* **benchmarking-common**: anything used by both library and integration benchmarks - runner and processor framework, metrics collection, report and badge generation, configuration, HTTP clients.
* **benchmark-core**: JMH `@Benchmark` methods, JFR instrumentation for library tests, library-specific test utilities.
* **benchmark-integration-wrk**: processing of the WRK output format only. Prefer shell scripts over Java for WRK orchestration (container management, test execution).

== Design Patterns

* **Template method** - `AbstractBenchmarkRunner.runBenchmark()` fixes the lifecycle (validate configuration, `prepareBenchmark`, `beforeBenchmark`, execute, `processResults`, `afterBenchmark`, `cleanup` in a `finally` block) and fails when JMH produces no results. New benchmark types extend this class.
* **Builder** - `BenchmarkConfiguration` is a record with a nested `Builder`; `ReportConfiguration` is built the same way.
* **Factory** - `HttpClientFactory` creates the configured HTTP clients.
* **Converter** - `JmhBenchmarkConverter` and `WrkBenchmarkConverter` map both result formats to the one `BenchmarkData` model, so every report is generated by the same code.
