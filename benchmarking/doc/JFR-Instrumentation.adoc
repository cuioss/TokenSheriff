= JFR Instrumentation for Variance Analysis
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js


The JFR-instrumented library benchmarks in `benchmark-core` record custom JFR events per validation and per second, so latency variance can be analysed after a run. JFR profiling of the native integration image is covered in link:../../token-sheriff-quarkus-parent/doc/performance/native-optimization-guide.adoc#_jfr_monitoring_dual_image_maven_profiles[Native Optimization Guide, JFR Monitoring].

== Quick Start

[source,bash]
----
# Run the JFR-instrumented benchmarks (from the project root)
./mvnw verify -Pbenchmark-jfr -pl benchmarking/benchmark-core

# Analyse the recording (the exec plugin needs an absolute path)
./mvnw verify -Panalyze-jfr -pl benchmarking/benchmark-core \
  -Djfr.file="$(pwd)/benchmarking/benchmark-core/target/benchmark-jfr-results/jfr-benchmark.jfr"
----

== JFR Events

The events are defined in `benchmarking/benchmarking-common/src/main/java/de/cuioss/benchmarking/common/jfr/`: `OperationEvent`, `OperationStatisticsEvent` and `BenchmarkPhaseEvent` (benchmark lifecycle phases). `JfrInstrumentation` is the central recorder and statistics aggregator; it records latencies in an HdrHistogram (3 significant digits) and emits the statistics event once per second.

=== de.cuioss.benchmark.Operation

One event per operation. Category `["Benchmark", "Performance"]`.

* `benchmarkName` - benchmark method name
* `operationType` - operation type (e.g. "validation")
* `threadName` - thread executing the operation
* `duration` - captured from event begin/end
* `payloadSize` - token size in bytes (DataAmount)
* `metadataKey` / `metadataValue` - custom metadata (e.g. issuer)
* `success` - operation result
* `errorType` - error classification if the operation failed
* `concurrentOperations` - concurrent operations at execution time

=== de.cuioss.benchmark.OperationStatistics

Periodic snapshot over a 1-second window. Category `["Benchmark", "Performance", "Statistics"]`, period `1 s`.

* `benchmarkName`, `operationType`
* `sampleCount` - operations in the window
* `successCount` / `errorCount`
* `meanLatency`, `p50Latency`, `p95Latency`, `p99Latency`, `maxLatency`, `standardDeviation` (Timespan)
* `variance` (ns²)
* `coefficientOfVariation` - CV as a percentage
* `concurrentThreads` - active threads in the window

== Variance Interpretation

The coefficient of variation (CV) indicates performance consistency:

[cols="1,2,2", options="header"]
|===
|CV Range |Interpretation |Typical Cause

|< 25%
|Low variance
|Well-optimized path

|25-50%
|Moderate variance
|Normal contention

|> 50%
|High variance
|Lock contention, GC
|===

== Analysis Tools

=== Variance Analyzer (`analyze-jfr` profile)

The `analyze-jfr` profile of `benchmark-core` runs `de.cuioss.benchmarking.common.jfr.JfrVarianceAnalyzer` in the `verify` phase on the file given by `-Djfr.file` (absolute path; a relative path fails with `FileNotFoundException`). It reports:

* total operations with the success/failure breakdown
* latency percentiles (P50, P95, P99, Max) in μs
* variance, standard deviation and CV
* maximum concurrent operations observed
* CV statistics over time (average, min, max)

=== JFR Command-Line Tools

[source,bash]
----
cd benchmarking/benchmark-core

jfr print --events de.cuioss.benchmark.Operation target/benchmark-jfr-results/jfr-benchmark.jfr
jfr print --events de.cuioss.benchmark.OperationStatistics target/benchmark-jfr-results/jfr-benchmark.jfr

# Export all benchmark events to JSON (quote the wildcard)
jfr print --json --events 'de.cuioss.benchmark.*' target/benchmark-jfr-results/jfr-benchmark.jfr > events.json
----

=== JDK Mission Control

Open `target/benchmark-jfr-results/jfr-benchmark.jfr` and filter the Event Browser on `de.cuioss.benchmark.*`.

== Configuration

The `benchmark-jfr` profile runs `de.cuioss.sheriff.token.validation.benchmark.JfrBenchmarkRunner`, which selects the benchmarks in the `...benchmark.jfr.benchmarks` package (`CoreJfrBenchmark`, `ErrorJfrBenchmark`, `MixedJfrBenchmark`) and starts the forked JVM with `-XX:StartFlightRecording=...,settings=profile`. `JfrBenchmarkRunner.createConfiguration()` sets these values explicitly:

* 1 fork, 16 threads
* 5 warmup iterations of 3 s, 5 measurement iterations of 5 s
* the include pattern of the `...benchmark.jfr.benchmarks` package
* output directory `target/benchmark-jfr-results/`

These fixed values apply whatever the JMH system properties of the link:../benchmark-core/README.adoc[benchmark-core README] (`jmh.iterations`, `jmh.threads`, `jmh.time`, ...) are set to; of those properties only the result format (`jmh.result.format`) still takes effect for this runner. The runner starts from `BenchmarkConfiguration.builder()`, which reads and validates the required `jmh.*` properties before the overrides above are applied, so those properties must still be present and valid (a missing or blank `jmh.include`, for example, fails the run); only their values are overridden.

== Troubleshooting

[cols="1,3", options="header"]
|===
|Issue |Solution

|**No JFR file created**
a|

* Check the Maven output for the `-XX:StartFlightRecording` argument and for JVM errors
* Check that the run used `-Pbenchmark-jfr`

|**Analyzer fails with ClassNotFoundException**
a|

* Build the modules first: `./mvnw clean install -pl benchmarking/benchmarking-common,benchmarking/benchmark-core`

|**JFR file not found or unreadable**
a|

* Pass an absolute path to `-Djfr.file`
* Verify the file: `jfr summary <file>`; a run killed mid-recording leaves an incomplete file
* Create and analyse the recording with the same Java major version

|**JFR overhead affects the results**
a|

* Switch the recording in `JfrBenchmarkRunner` from `settings=profile` to `settings=default`
* Compare against a run without JFR (`-Pbenchmark`)
|===
