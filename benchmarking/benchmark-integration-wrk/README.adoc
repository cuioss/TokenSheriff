= WRK-based JWT Integration Benchmarks
:toc: left
:toclevels: 3
:source-highlighter: highlight.js
:toc-title: Table of Contents
:sectnums:


High-performance HTTP benchmarking for JWT validation endpoints using WRK, addressing JMH limitations for REST API testing.

== Quick Start

[source,bash]
----
# Quick benchmark (30s duration, skip container lifecycle)
./mvnw clean verify -Pbenchmark,quick -pl benchmarking/benchmark-integration-wrk

# Default benchmark (50 connections, 1 minute per benchmark - GitHub CI friendly)
./mvnw clean verify -Pbenchmark -pl benchmarking/benchmark-integration-wrk

# Stress test (150 connections - moderate stress testing)
./mvnw clean verify -Pbenchmark,stress -pl benchmarking/benchmark-integration-wrk

# Maximum load test (300 connections - tests limits, expect JWT degradation)
./mvnw clean verify -Pbenchmark,max -pl benchmarking/benchmark-integration-wrk

# Start containers manually for fast iteration
cd token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests
./scripts/start-integration-container.sh
----

== Why WRK?

An HTTP client driven from JMH saturates on its own overhead before the server does. WRK is a native load generator with connection reuse (HTTP/1.1 keep-alive) and Lua scripting, so the measured limit is the server's.

== Architecture

=== WRK Execution

WRK runs via Docker for multi-architecture support (ARM64 + x86_64):

* **Docker Image**: `wrk:local` built from `Dockerfile.wrk` (Alpine-based, multi-arch)
* **Execution**: Via `docker compose run --rm wrk` using the `wrk` service defined in `docker-compose.yml`
* **Lua Scripts**: Embedded in image at `/scripts/` (health_live_check.lua, jwt_benchmark.lua)
* **No Installation Required**: Docker automatically selects correct architecture variant

=== Components

* **WRK Scripts** (`src/main/resources/wrk-scripts/`) - shell runners and Lua scripts for request generation
* **Java Post-processor** (`WrkResultPostProcessor.java`) - parses the WRK output, collects the Prometheus metrics of each benchmark window, generates the reports
* **Maven Integration** - lifecycle management via exec-maven-plugin

The module boundaries are described in link:../doc/Architecture.adoc[Module Architecture].

=== Benchmark Flow

1. Build the native integration-test application and its Docker image (skipped with `skip.container.lifecycle=true`)
2. Start the Docker containers (skipped with `skip.container.lifecycle=true`)
3. Check that the service, Keycloak and Prometheus are reachable (`pre-benchmark-health-check.sh`)
4. Run the health, JWT and ablation benchmarks
5. Process the results: reports, badges and Prometheus metrics (`WrkResultPostProcessor`)
6. Dump the Keycloak logs
7. Stop the containers (skipped with `skip.container.lifecycle=true`)

== Configuration

=== Maven Profiles

[cols="2,3,3", options="header"]
|===
|Profile
|Description
|Properties Set

|`benchmark`
|Enables benchmarking
|`skip.benchmark=false`

|`quick`
|Quick testing mode (30s benchmarks)
|`wrk.duration=30s`, `skip.container.lifecycle=true`

|`autoscale`
|Auto-scaled load (8 threads, 200 connections)
|`wrk.threads=8`, `wrk.connections=200`

|`stress`
|Moderate stress testing (10 threads, 150 connections)
|`wrk.threads=10`, `wrk.connections=150`

|`max`
|Maximum load testing (10 threads, 300 connections)
|`wrk.threads=10`, `wrk.connections=300`

|`benchmark-jfr`
|JFR profiling of one benchmark (`-Djfr.benchmark=jwt` by default) against the JFR image; suppresses the standard runs
|`wrk.duration=200s`, `skip.benchmark=true`, `skip.jfr.benchmark=false`
|===

The default (5 threads, 50 connections) is the recommended profile for CI and regular runs: it gave the peak throughput for every endpoint in the link:../doc/Analysis-03.2026-Integration.adoc#_connection_sweep_50_300_connections[connection sweep], and latency rises steadily with more connections. Use `stress`, `autoscale` and `max` for capacity testing only.

Example usage:
[source,bash]
----
# Quick 30-second benchmarks (assumes containers are running)
./mvnw clean verify -Pbenchmark,quick -pl benchmarking/benchmark-integration-wrk

# Auto-scaled load for local development
./mvnw clean verify -Pbenchmark,autoscale -pl benchmarking/benchmark-integration-wrk

# Stress test with high load
./mvnw clean verify -Pbenchmark,stress -pl benchmarking/benchmark-integration-wrk

# Custom duration with specific profile
./mvnw clean verify -Pbenchmark,autoscale -Dwrk.duration=60s -pl benchmarking/benchmark-integration-wrk

# CI-friendly configuration (GitHub Actions)
./mvnw clean verify -Pbenchmark -pl benchmarking/benchmark-integration-wrk
----

The `skip.container.lifecycle` property optimizes benchmark iteration:

[cols="2,3,3", options="header"]
|===
|Property Value
|Behavior
|Use Case

|`false` (default)
|Full lifecycle: build, start, stop containers
|CI/CD, first run, clean environment

|`true`
|Skip container operations, only run benchmarks
|Fast iteration, containers already running
|===

== Output

Results in `target/benchmark-results/`:

[cols="2,3", options="header"]
|===
|File
|Description

|`wrk/wrk-health-live-results.txt`
|Raw WRK output for health endpoint

|`wrk/wrk-jwt-results.txt`
|Raw WRK output for JWT endpoint

|`wrk/wrk-ablation-results.txt`
|Raw WRK output of the ablation benchmarks

|`gh-pages-ready/`
|Reports, badges, `data/benchmark-data.json` and API files, see link:../README.adoc#_generated_structure[Generated Structure]

|`prometheus/{benchmarkName}-server-metrics.json`
|Prometheus metrics of one benchmark window (`healthLiveCheck`, `jwtValidation`, ...), format in link:../doc/benchmark-metrics.adoc[Benchmark Metrics System]; copied to `gh-pages-ready/data/`

|Application logs from benchmark run (written by Quarkus file logging)

|`keycloak-logs-<timestamp>.txt`
|Keycloak container logs dumped after benchmarks
|===

=== Adding New Benchmarks

1. Create Lua script in `src/main/resources/wrk-scripts/`
2. Add Maven execution:

[source,xml]
----
<execution>
    <id>run-wrk-custom-benchmark</id>
    <phase>integration-test</phase>
    <goals><goal>exec</goal></goals>
    <configuration>
        <skip>${skip.benchmark}</skip>
        <executable>bash</executable>
        <arguments>
            <argument>${wrk.script.dir}/custom_benchmark.sh</argument>
        </arguments>
        <outputFile>${wrk.output.dir}/wrk-custom-results.txt</outputFile>
        <timeout>240000</timeout>
        <environmentVariables>
            <WRK_THREADS>${wrk.threads}</WRK_THREADS>
            <WRK_CONNECTIONS>${wrk.connections}</WRK_CONNECTIONS>
            <WRK_DURATION>${wrk.duration}</WRK_DURATION>
            <WRK_TIMEOUT>${wrk.timeout}</WRK_TIMEOUT>
            <COMPOSE_DIR>${integration.compose.dir}</COMPOSE_DIR>
        </environmentVariables>
    </configuration>
</execution>
----

The shell script uses `docker compose run --rm wrk` to execute WRK inside the Docker network and
prints the `=== BENCHMARK METADATA ===` header (`benchmark_name`, `start_time`) and the `end_time`
footer (see `health_live_benchmark.sh` for the reference implementation). `WrkResultPostProcessor`
processes every `wrk/*-results.txt` file; it needs no further configuration, and it attaches the
Prometheus metrics by the embedded `benchmark_name`.

== Troubleshooting

=== Common Issues

[cols="2,3,2", options="header"]
|===
|Issue
|Cause
|Solution

|High latency (>10ms)
|Connection pool saturation
|Reduce connections: `-Dwrk.connections=10`

|Container startup fails
|Port conflict or Docker issue
|Check ports 10443, 1443 are free

|Timeout errors or a failing `pre-benchmark-health-check.sh`
|Service, Keycloak or Prometheus not ready
|Check `quarkus.log` and the dumped Keycloak logs

|No Prometheus metrics files
|Prometheus not reachable at `http://localhost:9090`
|Check the Prometheus container; the health check fails and the build stops before the benchmark runs
|===
