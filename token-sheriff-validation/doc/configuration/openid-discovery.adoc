= OpenID Connect Discovery Configuration
:toc: left
:toclevels: 3
:source-highlighter: highlight.js
:toc-title: Table of Contents
:sectnums:


The library supports automatic configuration through OpenID Connect Discovery, allowing dynamic retrieval of issuer metadata and JWKS endpoints.

== Basic Discovery Setup

[source,java]
----
HttpJwksLoaderConfig jwksConfig = HttpJwksLoaderConfig.builder()
    .wellKnownUrl("https://accounts.google.com/.well-known/openid-configuration")
    .build();

IssuerConfig issuerConfig = IssuerConfig.builder()
    .issuerIdentifier("https://accounts.google.com")
    .expectedAudience("your-client-id")
    .httpJwksLoaderConfig(jwksConfig)
    .build();

TokenValidator validator = TokenValidator.builder()
    .issuerConfig(issuerConfig)
    .build();
----

The explicit `issuerIdentifier` is the default and recommended form, also together with `wellKnownUrl`. `IssuerConfig` requires it for every enabled issuer and propagates it into the loader configuration when it is built, so it is configured once and need not be repeated on the `HttpJwksLoaderConfig`. The `issuer` advertised by the discovery document is always compared with it. A mismatch is a hard failure: no keys are loaded, an `ISSUER_MISMATCH` security event is counted, and every token for that issuer is rejected.

If the `HttpJwksLoaderConfig` carries an identifier as well, it must be identical to the `IssuerConfig` identifier; a differing value makes `IssuerConfig.build()` fail with an `IllegalArgumentException`. A standalone `HttpJwksLoaderConfig` used without `IssuerConfig` may omit the identifier for discovery; no comparison with the advertised issuer takes place then (see xref:#discovery-issuer-check[Discovery issuer check and migration]).

== Discovery Document

The well-known endpoint returns a JSON document with issuer metadata:

[source,json]
----
{
  "issuer": "https://accounts.google.com",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/v2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "id_token_signing_alg_values_supported": ["RS256"],
  "subject_types_supported": ["public"],
  "response_types_supported": ["code", "token", "id_token"]
}
----

[source,java]
----
WellKnownConfig wellKnownConfig = WellKnownConfig.builder()
    .wellKnownUrl(wellKnownUrl.toString())
    .parserConfig(ParserConfig.builder()
        .maxPayloadSize(4096)  // Limits parsed JSON payload size

    .build();

HttpWellKnownResolver wellKnownResolver = new HttpWellKnownResolver(wellKnownConfig);

Optional<String> jwksUri = wellKnownResolver.getJwksUri();
Optional<String> issuer = wellKnownResolver.getIssuer();

== Configuring HttpJwksLoaderConfig

[source,java]
----
HttpJwksLoaderConfig jwksConfig = HttpJwksLoaderConfig.builder()
    .wellKnownUrl("https://your-issuer.com/.well-known/openid-configuration")
    .issuerIdentifier("https://your-issuer.com")
    .refreshIntervalSeconds(300)    // Refresh keys every 5 minutes
    .connectTimeoutSeconds(30)
    .readTimeoutSeconds(60)
    .sslContext(customSslContext)    // Optional custom SSL context
    .build();
----

For a local or containerised issuer reached by a name its certificate was never issued for, hostname
matching can be relaxed on its own. This is a *separate* configuration — it deliberately does not
supply `sslContext`, because the two cannot be combined:

[source,java]
----
HttpJwksLoaderConfig jwksConfig = HttpJwksLoaderConfig.builder()
    .wellKnownUrl("https://keycloak:8443/.well-known/openid-configuration")
    .issuerIdentifier("https://keycloak:8443")
    .refreshIntervalSeconds(300)
    .connectTimeoutSeconds(30)
    .readTimeoutSeconds(60)
    .allowedEgressHost("keycloak")    // Local/dev only — see the note below
    .verifyHostname(false)    // Local/dev only — see the warning below
    .build();
----

NOTE: The `allowedEgressHost` call is required for this example to work, and is a *separate* control
from `verifyHostname`. A container name such as `keycloak` resolves to a private bridge address, which
the egress policy rejects *before* the TLS handshake — and therefore before hostname verification is
ever reached. Relaxing hostname matching alone would leave the fetch blocked at the earlier gate.
`allowedEgressHost` governs *where* a JWKS fetch may go; `verifyHostname` governs *whether the
certificate's name must match*. Both are development-only opt-ins, and neither implies the other.

WARNING: `verifyHostname` defaults to `true`. Setting it to `false` relaxes *hostname matching only* —
certificate chain trust, expiry, and algorithm constraints all remain fully enforced, so an untrusted
or expired certificate is still rejected. It **cannot** be combined with `sslContext(...)`: the
relaxation applies only to the default-trust-store context the transport derives, so a caller-supplied
context leaves nothing to relax, and `build()` throws `IllegalArgumentException` when both are set.
With hostname verification relaxed, trust material therefore comes exclusively from the JVM default
trust store (`javax.net.ssl.trustStore` and its companions). Use it for local development and test
topologies only, never in production. See
xref:../../../doc/adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]
for the decision and its rationale.

== Complete Integration Example

[source,java]
----
public class OpenIDConnectValidator {

    public static TokenValidator createFromDiscovery(String issuerUrl, String clientId) {
        HttpJwksLoaderConfig jwksConfig = HttpJwksLoaderConfig.builder()
            .wellKnownUrl(issuerUrl + "/.well-known/openid-configuration")
            .refreshIntervalSeconds(300)
            .build();

        IssuerConfig issuerConfig = IssuerConfig.builder()
            .issuerIdentifier(issuerUrl)
            .expectedAudience(clientId)
            .expectedClientId(clientId)
            .httpJwksLoaderConfig(jwksConfig)
            .build();

        return TokenValidator.builder()
            .issuerConfig(issuerConfig)
            .build();
    }
}
----

== Multiple Providers with Discovery

[source,java]
----
public class MultiProviderDiscovery {

    public static TokenValidator createMultiProvider() {
        TokenValidator.TokenValidatorBuilder builder = TokenValidator.builder();

        addProviderFromDiscovery(builder, "https://accounts.google.com", "google-client-id");
        addProviderFromDiscovery(builder, "https://login.microsoftonline.com/common/v2.0", "microsoft-client-id");
        addProviderFromDiscovery(builder, "https://dev-123456.okta.com", "okta-client-id");

        return builder.build();
    }

    private static void addProviderFromDiscovery(
            TokenValidator.TokenValidatorBuilder builder, String issuerUrl, String clientId) {
        try {
            IssuerConfig issuerConfig = IssuerConfig.builder()
                .issuerIdentifier(issuerUrl)
                .expectedAudience(clientId)
                .httpJwksLoaderConfig(HttpJwksLoaderConfig.builder()
                    .wellKnownUrl(issuerUrl + "/.well-known/openid-configuration")
                    .build())
                .build();
            builder.issuerConfig(issuerConfig);
        } catch (Exception e) {
            LOGGER.warn("Failed to configure provider %s: %s", issuerUrl, e.getMessage());
        }
    }
}
----

== Considerations

=== Initial Latency

* Discovery adds startup latency (network request)

=== Security Best Practices

* Always use HTTPS for discovery endpoints
* Validate the discovery document structure
* Configure the issuer identifier explicitly on `IssuerConfig`; the advertised `issuer` is always compared with it, and an identifier repeated on `HttpJwksLoaderConfig` must be identical
* Pin certificates for known providers if possible

[#discovery-issuer-check]
== Discovery issuer check

Every `IssuerConfig` that loads its keys through well-known discovery compares its configured `issuerIdentifier` with the `issuer` advertised by the discovery document. A single trailing slash difference is tolerated. On a mismatch the loader stops before it fetches the advertised `jwks_uri`: no keys are loaded, an `ISSUER_MISMATCH` security event is counted, and every token for that issuer is rejected.

A discovery document that advertises no `issuer` is a hard failure as well: no keys are loaded, the advertised `jwks_uri` is never fetched, and every token for that issuer is rejected.

Troubleshooting an `ISSUER_MISMATCH`:

* Check that the `issuer` advertised by your discovery document equals your configured `issuerIdentifier`, apart from a single trailing slash.
* The identifier is configured once, on `IssuerConfig`. If you also set it on `HttpJwksLoaderConfig`, it must be identical to the `IssuerConfig` identifier, otherwise `IssuerConfig.build()` fails.
* A pre-built loader of type `WELL_KNOWN` passed via `IssuerConfig.builder().jwksLoader(...)` must carry the same identifier, otherwise `IssuerConfig.build()` fails.
