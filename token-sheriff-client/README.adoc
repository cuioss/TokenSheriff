= Token-Sheriff Client
:toc: left
:toclevels: 3
:source-highlighter: highlight.js
:toc-title: Table of Contents
:sectnums:

Framework-agnostic OIDC/OAuth *client* engine for Token-Sheriff — the outbound counterpart to
`token-sheriff-validation`. Pure Java, no framework dependency: a server-side confidential-client
engine that retrieves tokens, holds and refreshes them server-side, and drives the OAuth 2.0 /
OpenID Connect flows. It is the engine a Backend-For-Frontend (BFF) is built on — it is not
itself a BFF.

== Maven Coordinates

[source,xml]
----
<dependency>
    <groupId>de.cuioss.sheriff.token</groupId>
    <artifactId>token-sheriff-client</artifactId>
</dependency>
----

== Features

Organized by package under `de.cuioss.sheriff.token.client`:

* *Discovery* (`discovery`) — OIDC provider-metadata resolution (`DiscoveryResolver`,
  `ProviderMetadata`) with TLS enforcement and issuer verification, over an optional
  per-client TLS trust seam (`ClientConfiguration.sslContext`) shared by every discovery and
  back-channel call.
* *Flows* (`flow`) — authorization-code flow with mandatory PKCE `S256`
  (`AuthorizationCodeFlow`, `PkceChallenge`), client-credentials (`ClientCredentialsFlow`)
  and refresh (`RefreshFlow`) grants, pushed authorization requests (`ParClient`, RFC 9126),
  RFC 9207 `iss` mix-up defence (`IssValidator`), callback validation (`CallbackHandler`,
  `CallbackParameters`), and RFC 9470 step-up authentication (`StepUpHandler`).
* *Client authentication* (`auth`) — `client_secret_basic` / `client_secret_post` and
  `private_key_jwt` (RFC 7523) via `ClientAuthenticationSelector`. mTLS (`tls_client_auth`,
  RFC 8705) is an *alpha* capability: declared so an advertised entry resolves, never selected.
* *Sender-constraining* (`dpop`) — DPoP proof generation (`DpopProofGenerator`, RFC 9449)
  with replay-safe `jti` handling and constraint binding. Proof keys may be RSA, EC (curve
  `P-256`) or OKP (curve `Ed25519`), signed with `RS256` / `RS384` / `RS512`, `PS256`, `ES256`
  or `EdDSA`. FAPI 2.0 §5.4.1 conformance is reached through the DPoP route by passing `PS256`,
  `ES256` or `EdDSA` to the existing algorithm parameter — there is no separate
  algorithm-allowlist configuration knob. The algorithm and the proof key are checked against
  each other at construction time, so a mismatch fails fast.
* *Token handling* (`token`) — every retrieved token is validated through
  `token-sheriff-validation` (`TokenValidationBridge`, `IdTokenValidationBridge`), userinfo
  retrieval with `sub` binding (`UserInfoClient`, `SubBindingValidator`), and refresh-token
  rotation with reuse detection (`RefreshTokenFamily`).
* *Lifecycle* (`lifecycle`) — server-side token storage (`TokenStore` abstraction with
  `InMemoryTokenStore`), refresh scheduling (`RefreshScheduler`), and revocation
  (`RevocationClient`, RFC 7009) via `TokenLifecycleManager`.
* *Logout* (`logout`) — RP-initiated logout / `end_session` (`EndSessionFlow`) with
  exact-match `post_logout_redirect_uri` validation (`PostLogoutRedirectValidator`).

It adds *flows, not HTTP plumbing*: outbound bytes travel through the `commons` transport base
layer (`de.cuioss.sheriff.token.commons.transport`) that ships inside `token-sheriff-validation`.
Because it validates the tokens it retrieves, it depends on `token-sheriff-validation` and gets the
`commons` base layer transitively.

== Quick Start

Configure the client once per issuer with the immutable `ClientConfiguration` value object,
then drive the flow you need:

[source,java]
----
ClientConfiguration config = ClientConfiguration.builder()
    .issuer("https://issuer.example.com/realms/demo")
    .clientId("my-confidential-client")
    .clientSecret(secret)
    .authMethod(ClientAuthMethod.CLIENT_SECRET_BASIC)
    .scope("openid")
    .sslContext(sslContext) // <1>
    .discoveryDocumentMaxSize(128 * 1024) // <2>
    .build();
----
<1> Optional. Supply an `SSLContext` when the authorization server presents a private-CA or
self-signed certificate: the trust is scoped to this one client, so no process-global
`javax.net.ssl.trustStore` override is needed. Omit it — the default — and the JVM / cui-http
default truststore applies. When present, the context is used for every discovery and
back-channel call this client makes (`CLIENT-23`); it selects trust material only and does not
relax the TLS protocol floor.
+
WARNING: The supplied `SSLContext` MUST perform full certificate-chain validation. It is taken
verbatim — a trust-all `TrustManager` silently disables server authentication for every
credential-bearing back-channel request. This knob narrows trust to a known CA; it is not a way
to skip verification.
+
NOTE: The scope is this client engine only. JWKS retrieval for token *validation* runs through
`HttpJwksLoaderConfig`, which carries its own independent `sslContext()`. Against a private-CA
authorization server, configure both — otherwise token retrieval succeeds and validation then
fails the JWKS fetch with a PKIX error.
+
NOTE: `sslContext` cannot be combined with `verifyHostname(false)` (see below). The hostname
relaxation applies only to the default-trust-store context the transport derives, so a
caller-supplied context leaves nothing to relax; `build()` rejects the pair with an
`IllegalArgumentException`. Choose per-client trust material *or* relaxed hostname matching, never
both.

<2> Optional. The byte ceiling for the authorization server's discovery document, enforced during
the read. Defaults to 64 KiB — a ceiling sized for a discovery document rather than borrowed from
the 8 KiB JWT payload bound, which an ordinary Keycloak realm already exceeds. Raise it only for an
authorization server whose `.well-known/openid-configuration` is larger still; it bounds how much
of that response is buffered, so keep it as tight as the deployment's actual documents allow. Under
Quarkus the same knob is `sheriff.client.discovery-document-max-size`.

=== Relaxing hostname verification (local/dev only)

For a local or containerised authorization server reached by a name its certificate was never issued
for, hostname matching can be relaxed on its own. This is a *separate* configuration from the one
above — it deliberately does not supply `sslContext`, because the two are mutually exclusive:

[source,java]
----
ClientConfiguration config = ClientConfiguration.builder()
    .issuer("https://keycloak:8443/realms/demo")
    .clientId("my-confidential-client")
    .clientSecret(secret)
    .authMethod(ClientAuthMethod.CLIENT_SECRET_BASIC)
    .scope("openid")
    .verifyHostname(false) // <1>
    .build();
----
<1> Optional. Defaults to `true`. Setting it to `false` relaxes *hostname matching only* — certificate
chain trust, expiry, and algorithm constraints all remain fully enforced, so an untrusted or expired
certificate is still refused. It applies to every discovery and back-channel call this client makes.
It is independent of `allowInsecureHttp`, which governs the URL *scheme* rather than certificate
matching.
+
WARNING: Never use `verifyHostname(false)` in production. Disabling hostname verification removes the
guarantee that the certificate presented belongs to the host actually contacted, which re-opens the
man-in-the-middle vector that chain validation alone does not close. It exists for local development
and test topologies serving SAN-mismatched certificates.
+
NOTE: It cannot be combined with `sslContext` — `build()` rejects the pair with an
`IllegalArgumentException`. With hostname verification relaxed, trust material therefore comes
exclusively from the JVM default trust store (`javax.net.ssl.trustStore` and its companions), not
per-client. The validation side carries the same knob on `HttpJwksLoaderConfig`, under the same
constraint; against such a server, configure both. See
xref:../doc/adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]
for the decision and its rationale.

=== Reaching the authorization server under an internal address (back-channel origin)

In a split-horizon deployment the issuer identity is a public URL — the one browsers are redirected
to and the one tokens carry in `iss` — while the application can only reach the authorization server
under an internal address, for example a container-network name. `backChannelOrigin` routes the
back-channel calls to that internal address without changing the issuer:

[source,java]
----
ClientConfiguration config = ClientConfiguration.builder()
    .issuer("https://idp.example.com/realms/demo") // <1>
    .clientId("my-confidential-client")
    .clientSecret(secret)
    .authMethod(ClientAuthMethod.CLIENT_SECRET_BASIC)
    .scope("openid")
    .backChannelOrigin("http://keycloak:8080") // <2>
    .allowInsecureHttp(true) // <3>
    .build();
----
<1> The issuer stays the public identity. The discovery-document `issuer` check, the token `iss`
checks and the RFC 9207 `iss` response check all compare against this value, unchanged. The
discovery request itself (`{issuer}/.well-known/openid-configuration`) shares the issuer origin and
is therefore sent to the back-channel origin under the rule below.
<2> Optional, absent by default. The value must be a bare `http`/`https` origin
(`scheme://host[:port]`) — no path, query, fragment or user-info; a single trailing `/` is accepted
and dropped. Any other form fails `build()` with an `IllegalArgumentException` naming
`backChannelOrigin`.
<3> Needed here because this back-channel origin uses `http://`: the per-request scheme check is
evaluated against the host actually contacted. An `https://` back-channel origin does not require
the flag on its own account, but the flag is still required whenever the issuer itself is an
`http://` URL, because discovery checks the scheme of the configured issuer before any request is
sent.

*Mapping rule.* Every back-channel call — discovery, token, PAR, userinfo and revocation — whose
advertised endpoint URL has the *same origin* as the issuer is sent to the back-channel origin, with
its path and query kept verbatim. Origins are compared on lower-cased scheme, lower-cased host and
effective port, so `https://idp.example.com` and `https://idp.example.com:443` are the same origin.
An endpoint the authorization server advertises on any other origin is contacted unchanged. The
target is derived from configuration alone: neither the request nor the discovery document can
steer a call to a third origin.

*What is not rewritten.* The resolved provider metadata keeps the advertised public endpoint URLs,
and the front-channel URLs sent to the browser (authorization request, end-session) keep the public
origin.

*DPoP proofs name the URL actually contacted.* The client signs a DPoP proof's `htu` claim with the
URL it actually contacts, as RFC 9449 §4.2 requires of the target URI of the request. On a mapped
call the proof therefore names the back-channel origin with the advertised path —
`http://keycloak:8080/realms/demo/protocol/openid-connect/token` in the example above — not the
advertised public URL. This was verified against Keycloak 26.8.1 and 26.5.7, which compare `htu`
with the URL of the request they received. An authorization server that instead compares `htu` with
a configured public URL is not covered by this release: a deployment behind such a server must not
set `backChannelOrigin` for a DPoP-constrained client, because it maps every endpoint on the issuer
origin, userinfo included. See
xref:../doc/adr/0015-DPoP_htu_names_the_back-channel_URL_actually_contacted.adoc[ADR-0015] for the
evidence and this open risk.

*Transport policy follows the contacted host.* The per-request controls — the `allowInsecureHttp`
scheme check, `verifyHostname` and `sslContext` — are applied to the back-channel origin. With
`https://`, the certificate the internal host presents must be trusted and must match the internal
host name — supply matching certificates or trust material rather than relaxing hostname
verification. The issuer-scheme check at discovery is separate and still applies to the configured
issuer: an `http://` issuer requires `allowInsecureHttp` even when the back-channel origin is
`https://`. See `CLIENT-24` in the
xref:../doc/client/requirements.adoc#CLIENT-24[client requirements].

NOTE: The scope is this client engine only. JWKS retrieval for token *validation* runs through
`HttpJwksLoaderConfig`, whose JWKS URL is configured separately and is not rewritten by
`backChannelOrigin`. In a split-horizon deployment, point that JWKS URL at the reachable address
yourself. Under Quarkus the same knob is `sheriff.client.back-channel-origin`.

Endpoints are resolved via OIDC discovery against
`{issuer}/.well-known/openid-configuration`. See the
xref:../doc/client/specification/retrieval-flow.adoc[Retrieval & Flow specification] for the
flow contracts and the xref:../doc/client/best-practices.adoc[Best Practices] checklist.

== Framework bindings

The engine is framework-agnostic. The Quarkus binding lives in
`token-sheriff-quarkus-parent/token-sheriff-client-quarkus` (runtime + deployment); other runtimes
(e.g. a CDI/RESTEasy portal adapter) can bind the same engine. See the
xref:../doc/adr/0001-Validation_and_Client_Module_Split_with_a_Commons_Base_Layer.adoc[module-architecture decision].
