All `sheriff.client.*` properties for the OIDC/OAuth confidential-client Quarkus extension. For the
resource-server (token validation) side, see
xref:../../../../../token-sheriff-validation-quarkus/src/main/resources/META-INF/quarkus-config-doc.adoc[Token-Sheriff Quarkus Extension Configuration Reference].

== Minimal Configuration

[source,properties]
----
# A client is considered configured only when both issuer and client-id are present
sheriff.client.issuer=https://keycloak.example.com/realms/master
sheriff.client.client-id=my-service
sheriff.client.client-secret=${MY_SERVICE_CLIENT_SECRET}
----

== Client Configuration

[cols="2,1,1,3", options="header"]
|===
|Property |Type |Default |Description
|`sheriff.client.issuer` |String |— (required) |Authorization server issuer identifier URL. Together with `client-id` it is what makes the client configured at all
|`sheriff.client.client-id` |String |— (required) |OAuth 2.0 `client_id`
|`sheriff.client.client-secret` |String |— |Client secret for the shared-secret authentication methods. Absent for the key-based methods. Never logged
|`sheriff.client.auth-method` |String |`client_secret_basic` |Client authentication method, as the RFC 8414 `token_endpoint_auth_methods_supported` value. An unrecognised value fails the mapping
|`sheriff.client.scopes` |String (csv) |— (none requested) |OAuth 2.0 scopes to request
|`sheriff.client.redirect-uri` |String |— |The single exact `redirect_uri` for the interactive `authorization_code` flow. Absent for non-interactive clients
|`sheriff.client.allow-insecure-http` |boolean |`false` |Permit plaintext `http://` discovery and back-channel endpoints (testing only)
|`sheriff.client.discovery-document-max-size` |int |`65536` |Max size in bytes of the authorization server's discovery document. Must be positive. Raise only for a server whose `.well-known/openid-configuration` exceeds the ceiling
|`sheriff.client.strict-scope-reconciliation` |boolean |`false` |Refuse a refresh whose granted scope is *broader* than the requested scope (see NOTE below)
|`sheriff.client.verify-hostname` |boolean |`true` |Enforce TLS hostname verification on this client's outbound calls. Set to `false` only for SAN-mismatched development certificates (see NOTE below)
|`sheriff.client.back-channel-origin` |String |— (absent) |Origin (`scheme://host[:port]`) under which the client reaches the authorization server on the back channel, for split-horizon deployments. Must be a bare `http`/`https` origin — no path, query, fragment or user-info; an invalid value fails the mapping (see NOTE below)
|===

NOTE: `sheriff.client.back-channel-origin` serves deployments where the issuer is a public URL (for
example `https://idp.example.com/realms/demo`) that the application can only reach under an internal
address (for example `http://keycloak:8080`). Every back-channel call — discovery, token, PAR,
userinfo, revocation — whose advertised endpoint has the *same origin* as the issuer is sent to the
configured origin with its path and query kept verbatim; an endpoint advertised on any other origin is
contacted unchanged. The issuer stays the identity: the discovery-document `issuer` check and the
token `iss` checks are untouched, the published provider metadata and the DPoP `htu` keep the public
URLs, and the front channel (authorization-request and end-session URLs sent to the browser) keeps
the public origin. Transport policy follows the host actually contacted: `verify-hostname` and the
configured trust apply to the back-channel host, and an `http://` back-channel origin requires
`sheriff.client.allow-insecure-http=true`. The validation-side JWKS URL
(`sheriff.token.issuers.<name>.jwks.http.url`) is configured separately and is not affected by this setting.

NOTE: `sheriff.client.verify-hostname` defaults to `true` — it is the one switch in this table whose
secure value is the *enabled* one. Setting it to `false` relaxes *hostname matching only*:
certificate chain trust, expiry, and algorithm constraints stay fully enforced, so an untrusted or
expired certificate is still rejected. The setting is *client-wide*, not per-endpoint — it applies to
every outbound discovery and back-channel call this client makes (discovery, token, userinfo,
revocation, PAR). It also cannot be combined with a caller-supplied `SSLContext`; with verification
disabled, trust material must come from the JVM default trust store. The legitimate topologies are
local development and CI serving certificates whose SAN does not match the host actually contacted.
Never set it to `false` in production — without hostname verification there is no guarantee that the
presented certificate belongs to the host contacted, which re-opens the man-in-the-middle vector
chain validation alone does not close. See
xref:../../../../../../doc/adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]
for the rationale.

NOTE: `sheriff.client.strict-scope-reconciliation` defaults to `false` deliberately. At the default a
broadened grant is accepted, `WARN`-logged, and surfaced on `RotationResult` so the application can
act on the delta; RFC 6749 §3.3 permits an authorization server to grant a scope other than the one
requested provided it discloses the result, and several major authorization servers canonicalise or
expand scope sets as a matter of course. Enabling strict mode refuses such a grant with a
`ClientProtocolException` — turning a benign server quirk into a total authentication outage, with no
attacker in the loop. Enable it only against an authorization server known not to canonicalise or
expand scope sets; the outage risk falls entirely on the deployment that opts in.
