All `sheriff.client.*` properties for the OIDC/OAuth confidential-client Quarkus extension. For the
resource-server (token validation) side, see
xref:../../../../../token-sheriff-validation-quarkus/src/main/resources/META-INF/quarkus-config-doc.adoc[Token-Sheriff Quarkus Extension Configuration Reference].

== Minimal Configuration

[source,properties]
----
# A client is considered configured only when both issuer and client-id are present
sheriff.client.issuer=https://keycloak.example.com/realms/master
sheriff.client.client-id=my-service
sheriff.client.client-secret=${MY_SERVICE_CLIENT_SECRET}
----

== Client Configuration

[cols="2,1,1,3", options="header"]
|===
|Property |Type |Default |Description
|`sheriff.client.issuer` |String |— (required) |Authorization server issuer identifier URL. Together with `client-id` it is what makes the client configured at all
|`sheriff.client.client-id` |String |— (required) |OAuth 2.0 `client_id`
|`sheriff.client.client-secret` |String |— |Client secret for the shared-secret authentication methods. Absent for the key-based methods. Never logged
|`sheriff.client.auth-method` |String |`client_secret_basic` |Client authentication method, as the RFC 8414 `token_endpoint_auth_methods_supported` value. An unrecognised value fails the mapping
|`sheriff.client.scopes` |String (csv) |— (none requested) |OAuth 2.0 scopes to request
|`sheriff.client.redirect-uri` |String |— |The single exact `redirect_uri` for the interactive `authorization_code` flow. Absent for non-interactive clients
|`sheriff.client.allow-insecure-http` |boolean |`false` |Permit plaintext `http://` discovery and back-channel endpoints (testing only). It does not relax the refusal of a non-`https` value, advertised by an `https` issuer's discovery document, for any endpoint the client models and uses
|`sheriff.client.discovery-document-max-size` |int |`65536` |Max size in bytes of the authorization server's discovery document. Must be positive. Raise only for a server whose `.well-known/openid-configuration` exceeds the ceiling
|`sheriff.client.strict-scope-reconciliation` |boolean |`false` |Refuse a refresh whose granted scope is *broader* than the requested scope (see NOTE below)
|`sheriff.client.verify-hostname` |boolean |`true` |Enforce TLS hostname verification on this client's outbound calls. Set to `false` only for SAN-mismatched development certificates (see NOTE below)
|`sheriff.client.back-channel-origin` |String |— (absent) |Origin (`scheme://host[:port]`) under which the client reaches the authorization server on the back channel, for split-horizon deployments. Must be a bare `http`/`https` origin — no path, query, fragment or user-info; an invalid value fails the mapping (see NOTE below)
|`sheriff.client.allow-loopback-egress` |boolean |`false` |Let the host-address egress policy permit an endpoint whose host resolves to a loopback address (local development only). Every other refused range stays refused (see NOTE below)
|`sheriff.client.allowed-egress-hosts` |String (csv) |— (none) |Host names the host-address egress policy lets through without any address-range check, matched case-insensitively. Each entry must be a bare host — a host name, an IPv4 literal or an IPv6 literal, bare or in brackets, never `host:port`. A port-carrying entry (such as `keycloak:8080`) or one with surrounding whitespace fails the mapping with an `IllegalArgumentException` naming the entry index but never the entry; entries are not trimmed and empty CSV elements are dropped by the configuration reader (see NOTE below)
|===

NOTE: Every discovery and back-channel call — discovery, token, PAR, userinfo, revocation — passes a
host-address egress policy on the URL *actually contacted*, that is after the
`sheriff.client.back-channel-origin` rewrite. The policy is secure by default: an endpoint whose host
resolves to a loopback, link-local (including the `169.254.0.0/16` cloud-metadata range), site-local,
IPv6 unique-local, carrier-grade NAT (`100.64.0.0/10`), wildcard, broadcast or multicast address is
refused with a `TransportException`. *This default can refuse an endpoint the deployment configured or
the issuer advertised on an internal address, including a back-channel origin such as
`http://keycloak:8080`.* There are exactly two relaxations, both explicit:
`sheriff.client.allow-loopback-egress=true` lifts the loopback refusal only, and
`sheriff.client.allowed-egress-hosts` lists hosts that bypass the range check entirely — list the
back-channel origin's host there for a split-horizon deployment. A listed host is trusted wherever it
appears, including in an advertised endpoint, so keep the list narrow. The check resolves the host
immediately before the fetch; the HTTP client resolves it again when it connects, so a DNS answer that
changes in between is not seen (the DNS-rebinding limit). The policy is the client's own and is
independent of the validation side's JWKS egress settings.

NOTE: `sheriff.client.back-channel-origin` serves deployments where the issuer is a public URL (for
example `https://idp.example.com/realms/demo`) that the application can only reach under an internal
address (for example `http://keycloak:8080`). Every back-channel call — discovery, token, PAR,
userinfo, revocation — whose advertised endpoint has the *same origin* as the issuer is sent to the
configured origin with its path and query kept verbatim; an endpoint advertised on any other origin is
contacted unchanged. The issuer stays the identity: the discovery-document `issuer` check and the
token `iss` checks are untouched, the published provider metadata keeps the public URLs, and the
front channel (authorization-request and end-session URLs sent to the browser) keeps the public
origin. A DPoP proof's `htu` names the back-channel URL actually contacted — the configured origin
with the advertised path — because `htu` is the target URI of the request the proof travels with
(RFC 9449 §4.2); see
xref:../../../../../../doc/adr/0015-DPoP_htu_names_the_back-channel_URL_actually_contacted.adoc[ADR-0015].
Transport policy follows the host actually contacted: the host-address egress policy, `verify-hostname`
and the configured trust apply to the back-channel host — so an internal back-channel origin must be
listed in `sheriff.client.allowed-egress-hosts` — and an `http://` back-channel origin requires
`sheriff.client.allow-insecure-http=true`. The issuer-scheme check at discovery is the one exception:
it still applies to the configured issuer, so an `http://` issuer requires
`sheriff.client.allow-insecure-http=true` even when the back-channel origin is `https://`. The validation-side JWKS URL
(`sheriff.token.issuers.<name>.jwks.http.url`) is configured separately and is not affected by this setting.

NOTE: `sheriff.client.verify-hostname` defaults to `true` — it is the one switch in this table whose
secure value is the *enabled* one. Setting it to `false` relaxes *hostname matching only*:
certificate chain trust, expiry, and algorithm constraints stay fully enforced, so an untrusted or
expired certificate is still rejected. The setting is *client-wide*, not per-endpoint — it applies to
every outbound discovery and back-channel call this client makes (discovery, token, userinfo,
revocation, PAR). It also cannot be combined with a caller-supplied `SSLContext`; with verification
disabled, trust material must come from the JVM default trust store. The legitimate topologies are
local development and CI serving certificates whose SAN does not match the host actually contacted.
Never set it to `false` in production — without hostname verification there is no guarantee that the
presented certificate belongs to the host contacted, which re-opens the man-in-the-middle vector
chain validation alone does not close. See
xref:../../../../../../doc/adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]
for the rationale.

NOTE: `sheriff.client.strict-scope-reconciliation` defaults to `false` deliberately. At the default a
broadened grant is accepted, `WARN`-logged, and surfaced on `RotationResult` so the application can
act on the delta; RFC 6749 §3.3 permits an authorization server to grant a scope other than the one
requested provided it discloses the result, and several major authorization servers canonicalise or
expand scope sets as a matter of course. Enabling strict mode refuses such a grant with a
`ClientProtocolException` — turning a benign server quirk into a total authentication outage, with no
attacker in the loop. Enable it only against an authorization server known not to canonicalise or
expand scope sets; the outage risk falls entirely on the deployment that opts in.

== Discovery Cache

The discovery cache is *off by default*. Without any `sheriff.client.discovery-cache.*` property the
produced `DiscoveryResolver` bean fetches the discovery document on every call, exactly as before.
Setting `sheriff.client.discovery-cache.enabled=true` makes a `CachingDiscoveryResolver` bean
available alongside it; an application injects that bean explicitly to use the cache. The plain
`DiscoveryResolver` bean stays the default and is unchanged either way.

[source,properties]
----
sheriff.client.discovery-cache.enabled=true
sheriff.client.discovery-cache.ttl=PT5M
sheriff.client.discovery-cache.grace-period=PT10M
----

[cols="2,1,1,3", options="header"]
|===
|Property |Type |Default |Description
|`sheriff.client.discovery-cache.enabled` |boolean |`false` |Enable the opt-in discovery cache and make the `CachingDiscoveryResolver` bean available. An application that injects that bean while the cache is not enabled fails the deployment (see NOTE below)
|`sheriff.client.discovery-cache.ttl` |Duration |— (required when enabled) |How long a resolved discovery document is served without a refresh. Must be positive and at most 365 days. There is no default: the deployment states how long a document may be reused
|`sheriff.client.discovery-cache.grace-period` |Duration |`PT0S` |How long past its TTL the last resolved document is still served while refreshes fail. After `lastSuccess + ttl + grace-period` a resolution fails closed. At `PT0S` it fails closed as soon as the TTL has elapsed and a refresh fails. Must not be negative and at most 365 days
|`sheriff.client.discovery-cache.min-refresh-interval` |Duration |`PT0S` |The minimum time between a failed refresh and the next refresh attempt; within it the stale policy answers from the cache. At `PT0S` nothing is held back: every call after a failure retries. Must not be negative and at most 365 days
|`sheriff.client.discovery-cache.jitter` |Duration |`PT0S` |The upper bound of a random amount by which each freshness window is shortened, so clients sharing a TTL do not refresh at the same instant. Must not be negative and must be smaller than the TTL
|===

NOTE: A refresh runs on demand, on the calling thread — there is no background thread — and
concurrent callers share a single refresh. Every refreshed document passes the same checks as an
uncached resolution (TLS, the issuer match, the endpoint schemes, the media type, the size bound), so
a refused document never replaces the cached one.

NOTE: An orphaned or invalid discovery cache property fails application startup with an
`IllegalStateException` naming the property and the fix: setting `ttl`, `grace-period`,
`min-refresh-interval` or `jitter` while `sheriff.client.discovery-cache.enabled` is not `true` would
otherwise be silently ignored, so it is refused whatever its value, and
`sheriff.client.discovery-cache.enabled=true` without a `ttl` has no usable time to live. With the
cache enabled, every value rule in the table above is checked at startup, before the first
resolution: a value that does not parse as a `Duration`, a `ttl` that is not positive, a negative
duration, a `ttl`, `grace-period` or `min-refresh-interval` longer than 365 days, and a `jitter` that
is not smaller than the `ttl`. The check reads the configuration only; every client bean stays lazy.

NOTE: An application that injects `CachingDiscoveryResolver` — directly or through `Instance`,
`Provider` or `InjectableInstance` — while `sheriff.client.discovery-cache.enabled` is not `true`
fails the deployment: the build records the injection point, and a runtime-init check refuses the
start with an `IllegalStateException` naming `sheriff.client.discovery-cache.enabled` before the
application serves. An application that injects no `CachingDiscoveryResolver` gains no runtime work
from this check. A dynamic lookup the build cannot see (`CDI.current().select(...)`,
`Arc.container().instance(...)`) is not covered: with ArC's default removal of unused beans no
injection point keeps the bean, so the lookup finds none, and where the bean is retained its first use
fails with the same `IllegalStateException`.
