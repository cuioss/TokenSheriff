== Overview

The Quarkus DevUI integration provides read-only monitoring of JWT validation configuration and a token debugging tool, available only in Quarkus dev mode.

Two pages:

* **Status & Config** -- Consolidated view of validation status, JWKS endpoints, issuers, and runtime configuration
* **Token Debugger** -- Validates a JWT token against configured issuers

== Architecture

=== File Structure

[source]
----
token-sheriff-validation-quarkus-deployment/src/main/resources/dev-ui/
├── qwc-jwt-status-config.js   # Merged status and configuration viewer
└── qwc-jwt-debugger.js        # Token validation tool
----

=== Technology Stack

* **Frontend**: Lit Element web components
* **Communication**: JSON-RPC over WebSockets
* **Styling**: CSS custom properties using Lumo theme variables
* **Icons**: Font Awesome 6 Free (solid) via Vaadin iconset

=== Backend Integration

DevUI pages are registered during build time in `TokenSheriffProcessor.java`:

[source,java]
----
@BuildStep(onlyIf = IsDevelopment.class)
CardPageBuildItem createJwtDevUICard() {
    CardPageBuildItem cardPageBuildItem = new CardPageBuildItem();
    cardPageBuildItem.addPage(Page.webComponentPageBuilder()
        .icon("font-awesome-solid:shield-halved")
        .title("Status & Config")
        .componentLink("qwc-jwt-status-config.js"));
    cardPageBuildItem.addPage(Page.webComponentPageBuilder()
        .icon("font-awesome-solid:bug")
        .title("Token Debugger")
        .componentLink("qwc-jwt-debugger.js"));
    return cardPageBuildItem;
}
----

The JSON-RPC service is registered via `createJwtDevUIJsonRPCService()` in `TokenSheriffProcessor.java` and provided at runtime by `TokenSheriffDevUIRuntimeService.java` (`@ApplicationScoped`, injects a single `ObservedValidatorResolver`).

The resolver reports on the `TokenValidator` actually in use, so the panel stays functional when an
application supplies its own `TokenValidator` and leaves the `sheriff.token.issuers.*` namespace
empty. Its three outcomes map to three view states:

* `PROPERTY_CONFIGURED` — the extension's own validator; every view renders its full data.
* `EXTERNAL_VALIDATOR` — an externally-produced validator is observed. Token validation works, but
  its issuer configurations and parser limits are not exposed, so `getJwksStatus()` reports
  `EXTERNAL_VALIDATOR` with an empty `issuers` array and `getConfiguration()` emits a
  `{"status": "unavailable (external validator)"}` marker for the `parser` section and for
  `httpJwksLoader.sizeLimit`.
* `NOT_CONFIGURED` — nothing observable. Every method returns a well-formed response rather than
  throwing; the same two surfaces carry the `unavailable (not configured)` marker, and
  `getHealthInfo()` reports `configurationValid=false` and `healthStatus=DOWN`.

The `qwc-jwt-status-config.js` web component renders an explicit notice for the unavailability
marker instead of the underlying field values.

== JSON-RPC Methods

[cols="2,3,4"]
|===
|Method |Purpose |Response Fields

|`getValidationStatus()`
|Whether JWT validation is active
|`enabled`, `status`, `statusMessage`, `validatorPresent`

|`getJwksStatus()`
|Configured issuer endpoints
|`status`, `issuers[]` with `name`, `issuerUri`, `jwksUri`, `loaderStatus`, `lastRefresh`

|`getConfiguration()`
|Resolved runtime configuration
|`enabled`, `logLevel`, `parser{}`, `httpJwksLoader{}`, `issuers{}`

|`validateToken(token)`
|Validate a JWT access token
|`valid`, `error?`, `tokenType?`, `claims?`, `issuer?`, `details?`

|`getHealthInfo()`
|Overall extension health
|`configurationValid`, `tokenValidatorAvailable`, `securityCounterAvailable`, `overallStatus`, `message`, `healthStatus`
|===

NOTE: `validateToken` only validates access tokens. ClaimValue objects are converted to simple strings for JSON-RPC serialization.

== Component Details

=== Status & Config (`qwc-jwt-status-config.js`)

Read-only view calling all four JSON-RPC methods in parallel on load, with auto-refresh every 30 seconds.

Sections: Status Overview (indicator dot, metrics grid), Issuers (per-issuer cards), Parser Configuration, HTTP JWKS Loader settings, General Settings. Health indicator badge and refresh button in toolbar.

=== Token Debugger (`qwc-jwt-debugger.js`)

* Token input textarea
* "Validate Token" button -- calls `validateToken()` JSON-RPC method
* "Load Sample" / "Clear" buttons
* Result display: success shows token type and formatted JSON claims; failure shows error details

== Security Considerations

* **Development-only**: Excluded from production builds (`@BuildStep(onlyIf = IsDevelopment.class)`)
* **No sensitive data storage**: Validated tokens are not logged or persisted
* **Claim serialization**: ClaimValue objects converted to plain strings

== Usage

. Start Quarkus in dev mode: `./mvnw quarkus:dev`
. Open `http://localhost:8080/q/dev-ui/`
. Locate the "Token-Sheriff" extension card

== [[testing]] Testing

The web components are tested at two levels: Jest unit tests of each Lit component in isolation
with mocked JSON-RPC responses, and Playwright end-to-end tests against a running Quarkus dev
instance.

=== Unit tests (Jest)

Run from `token-sheriff-validation-quarkus-deployment/` with `npm test` (also `test:watch`,
`test:coverage`, `test:ci`). The tests live under `src/test/js/`:

[source]
----
src/test/js/
├── setup/              # Jest configuration and setup
├── mocks/              # Mock implementations (Lit, DevUI, directives)
└── components/         # qwc-jwt-status-config.test.js, qwc-jwt-debugger.test.js,
                        # simple-component.test.js
----

The setup provides the custom matchers `toHaveRenderedContent()`, `toHaveShadowClass()` and
`toBeDefinedAsCustomElement()` and the helpers `waitForComponentUpdate()`, `createTestComponent()`
and `cleanupTestComponents()`.

=== End-to-end tests (Playwright)

The suite lives in `token-sheriff-quarkus-parent/e-2-e-playwright/`:

[source]
----
e-2-e-playwright/
├── tests/
│   ├── self-devui-accessible.spec.js          # Environment gate-keeper tests
│   ├── 01-verify-status-config.spec.js        # Status & Config page
│   ├── 03-verify-token-debugger.spec.js       # Token Debugger page
│   └── accessibility-wcag-compliance.spec.js  # WCAG 2.1 AA compliance, keyboard navigation
├── utils/                                     # constants, SPA navigation, Keycloak token
│                                              # acquisition, pre-flight checks, logging
└── fixtures/
    └── test-fixtures.js                       # Shared test fixtures
----

Run from `token-sheriff-quarkus-parent/`. Start only the `keycloak` service: a plain `up -d` also starts
the `token-sheriff-integration-tests` service, whose image build copies a prebuilt native runner that this
procedure does not build. `quarkus:dev` stays in the foreground, so keep it running in the first terminal
and run Playwright in a second one:

[source,bash]
----
# Terminal 1
docker compose -f token-sheriff-quarkus-integration-tests/docker-compose.yml up -d keycloak
../mvnw -f token-sheriff-quarkus-integration-tests/pom.xml quarkus:dev

# Terminal 2
cd e-2-e-playwright && npx playwright test
----

Quarkus DevUI is a single-page application (Vaadin Router and Lit web components) that registers
extension sub-page routes lazily, so the tests navigate by clicking through the extension card,
traversing the shadow DOM to the anchors inside the `qwc-extension-link` elements.
