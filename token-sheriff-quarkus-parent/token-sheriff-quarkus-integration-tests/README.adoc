== Overview

Integration tests for the Token-Sheriff Quarkus extensions with native container testing, HTTPS support, health checks, and metrics validation. Covers both the validation extension (token validation, bearer auth, DPoP, JWE) and the client engine (discovery, flows, logout) against a real Keycloak.

== Port Configuration

* **Application Internal**: `8443` (HTTPS inside container)
* **External Test**: `10443` (Docker mapped port)
* **Keycloak External**: `1443` (Docker mapped HTTPS port)
* **Retry Probe External**: `10444` (Docker mapped HTTPS port of the second application container, see <<_retry_probe>>)

== Features

* Native container testing with production-like behavior
* HTTPS with self-signed certificates
* Keycloak integration with four test realms
* Multi-IDP testing with Dex (via Docker Compose profile)
* Health check and metrics validation
* Automated build and test scripts

== Quick Start

=== Prerequisites

* Java 21+ or Java 25+ (recommended for native image compilation), Maven 3.9+ (via `./mvnw`), Docker

=== Test Execution

[source,bash]
----
# Native integration tests - Keycloak only (requires Docker)
./mvnw clean verify -Pintegration-tests -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests -am

# Multi-IDP integration tests - Keycloak + Dex (requires Docker)
./mvnw clean verify -Pmulti-idp-tests -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests -am

# JVM unit tests only (no Docker required)
./mvnw clean test -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests

# Manual container testing
./scripts/start-integration-container.sh
curl -k https://localhost:10443/q/health
./scripts/stop-integration-container.sh
----

== Image Variants

The integration tests support two optimized container variants for different use cases:

=== Distroless (Production)

* **Dockerfile**: `Dockerfile.native.distroless`
* **Base Image**: Quarkus Distroless (security-hardened)
* **Size**: 104MB
* **Use Case**: Production deployments, CI/CD pipelines
* **Features**: Minimal attack surface, fast startup, optimized security

[source,bash]
----
# Build distroless variant
DOCKERFILE=Dockerfile.native.distroless DOCKER_IMAGE_TAG=distroless docker compose build token-sheriff-integration-tests

# Run integration tests with distroless
./mvnw clean verify -Pintegration-tests -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests
----

=== JFR-Enabled (Profiling) - Local Development Only

* **Dockerfile**: `Dockerfile.native.jfr`
* **Base Image**: UBI 9 Micro with debugging tools
* **Size**: 96MB
* **Use Case**: Performance analysis, profiling, debugging (local development only)
* **Features**: Full JFR profiling, debugging tools, monitoring capabilities
* **Note**: JFR profile is disabled in CI/CD due to container startup issues in GitHub Actions

NOTE: Only the `jfr` Maven profile compiles JFR support into the native executable (it sets `quarkus.native.monitoring=jfr`). The executable that the `integration-tests` and `multi-idp-tests` profiles build has no JFR support, so build the executable with `-Pjfr` before using `Dockerfile.native.jfr`.

[source,bash]
----
# Build JFR variant
DOCKERFILE=Dockerfile.native.jfr DOCKER_IMAGE_TAG=jfr docker compose build token-sheriff-integration-tests

# Run JFR profiling tests
./mvnw clean verify -Pjfr -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests

# Extract JFR recordings (automatic via Maven)
ls -la token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests/target/jfr-results/

== Multi-IDP Testing

The integration tests support multiple OIDC providers to verify broad compatibility. Additional providers are managed via Docker Compose profiles.

=== Dex (Phase 1)

https://dexidp.io/[Dex] is a lightweight, OpenID Certified OIDC provider (~30MB, 2s startup) used for multi-IDP testing.

* **Port**: `2556` (external HTTPS)
* **Issuer**: `https://dex:5556/dex`
* **Client**: `dex-client` / `dex-secret`
* **User**: `dex-user@example.com` / `dex-password`

[source,bash]
----
# Start with Dex
COMPOSE_PROFILES=multi-idp docker compose up -d

# Verify Dex
curl -k https://localhost:2556/dex/.well-known/openid-configuration
----

Tests are parameterized via `TestProviders` — Dex is automatically included in the provider list when `-Ddex.enabled=true` is set by the multi-idp-tests Maven profile. Providers missing required capabilities are skipped with an INFO log.

See link:../../doc/validation/specification/multi-idp-testing.adoc[Multi-IDP Testing Specification] for the full architecture and provider roadmap.

== Native Compilation

=== Java 25 Builder Image

The module uses the `jdk-25` Mandrel builder image for native compilation to leverage modern JVM improvements:

[source,properties]
----
quarkus.native.builder-image=quay.io/quarkus/ubi9-quarkus-mandrel-builder-image:jdk-25
----

**Key Benefits:**

* **JEP 491 Support**: "Synchronize Virtual Threads without Pinning" - eliminates carrier thread pinning when virtual threads execute synchronized blocks
* **Virtual Thread Performance**: Improved concurrency handling for JWT validation operations under high connection loads
* **Modern Optimizations**: Enhanced native image compilation with latest GraalVM/Mandrel improvements

The builder image handles native compilation in a Docker container, so the local JDK version (Java 21+) is used only for regular Maven compilation. Native builds automatically use Java 25 via the specified builder image.

=== Maven Clean Integration

The module integrates Docker cleanup with Maven's clean phase to prevent file lock issues during native builds:

[source,bash]
----
# Standard clean command now stops Docker containers first
./mvnw clean -pl token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests

# What happens:
# 1. Executes stop-integration-container.sh --clean (pre-clean phase)
# 2. Stops and removes all Docker containers
# 3. Cleans Docker images and volumes
# 4. Deletes target directory (standard clean)
----

This ensures reliable cleanup of native executables and build artifacts without "file in use" errors.

== Test Specs

Tests use `@ParameterizedTest` with `@MethodSource` to run against multiple OIDC providers. Each spec declares required capabilities — providers are filtered by `TestProviders`.

* **token/TokenValidationSpecIT**: Access/ID/refresh token validation (parameterized over all providers with matching capabilities)
* **token/WellKnownRetryConfigSpecIT**: Configured retry settings reach well-known discovery (reads the retry probe, see <<_retry_probe>>)
* **bearer/BearerAuthSpecIT**: Bearer token producers and interceptors (Keycloak-only — requires ROLES, GROUPS, CUSTOM_SCOPES)
* **security/DpopSpecIT**: DPoP RFC 9449 validation (parameterized over DPoP-capable providers)
* **security/JweDecryptionSpecIT**: JWE RFC 7516 decryption (parameterized over JWE-capable providers)
* `client/**`: Client-engine specs against a real Keycloak — discovery (`DiscoverySpecIT`), client authentication with the `client_credentials` grant (`ClientAuthSpecIT`), authorization-code + PKCE (`AuthCodePkceSpecIT`), mix-up defence (`MixUpSpecIT`), PAR (`ParSpecIT`), userinfo (`UserInfoSpecIT`), DPoP-bound tokens (`DpopBoundSpecIT`), RP-initiated logout (`LogoutSpecIT`), step-up (`StepUpSpecIT`), the full-flow E2E (`FullFlowE2EIT`), and the refresh specs (`Refresh*SpecIT`) — among them refresh with rotation through the production `RefreshFlow` (`RefreshProductionPathSpecIT`) and the refusal of an unknown and of a revoked refresh token (`RefreshErrorPathSpecIT`)
* **health/HealthCheckIntegrationIT**: Health endpoint validation
* **health/HealthCheckResponsivenessIT**: Health endpoint responsiveness testing
* **api/ApiValidationSpecIT**: API input validation (provider-independent)
* **api/TokenRequestSpecIT**: Token request deserialization (provider-independent)

=== Key infrastructure classes

* **TestRealm**: Provider configuration + token acquisition + capability declaration
* **TestProviders**: Provider registry with capability-based filtering and INFO logging

=== Execution Model

All integration-test classes run in one failsafe JVM (`forkCount=1`, `reuseForks=true`, set in this module's `pom.xml`). The classes are HTTP clients of one already running application; none boots Quarkus in the test JVM.

* **Class order**: classes are ordered by `@Order` (`ClassOrderer$OrderAnnotation`, set in the failsafe configuration). `TokenValidationSpecIT` carries `@Order(Integer.MAX_VALUE)` and runs last, because it asserts a cumulative count on the application.
* **Concurrency**: `src/test/resources/junit-platform.properties` enables parallel execution with a fixed parallelism of 2 and `same_thread` as the default for classes and methods. `RefreshProductionPathSpecIT` is the one class that opts in with `@Execution(CONCURRENT)`, so that its wait for a real access token to expire overlaps the other classes. It talks to Keycloak only and never to the application under test.

[#_retry_probe]
=== Retry Probe

`WellKnownRetryConfigSpecIT` does not talk to the application under test. It reads the retry probe: a second container of the same native image (compose service `token-sheriff-retry-probe`, compose profile `retry-probe`, external port `10444`).

* The probe's `keycloak` issuer points its well-known URL at a port on which nothing listens, so discovery fails on every attempt. Its `integration` issuer keeps a working JWKS URL.
* The probe runs with `sheriff.token.retry.max-attempts=3` (the default is 5) and `sheriff.token.retry.initial-delay-ms=200`.
* The spec counts the discovery attempts from the probe's log (`target/retry-probe/quarkus.log`): the `HTTP-112` lines of the HTTP retry adapter, one per failed attempt that is followed by another, plus the single `HTTP-111` give-up line. Their sum must equal the configured maximum.
* Before it counts, the spec waits for the probe's `jwks-endpoints` readiness check (`https://localhost:10444/q/health/ready`) to report that loading is over, the `keycloak` issuer `DOWN` and the `integration` issuer `UP`. The answer arrives as HTTP 503, and the spec reads its body. A failing wait prints the HTTP status and the body it received.
* The probe is a separate container because an issuer that never loads turns the readiness check `DOWN`.

The probe's own output is part of every run that starts it: `dump-app-logs.sh` writes the probe's container log and its log file to `target/app-logs-retry-probe-<timestamp>.txt` and prints the warning, error and retry lines, the container state and the log file to the build output.

The `integration-tests`, `multi-idp-tests` and `jfr` Maven profiles activate the compose profile. `start-integration-container.sh` holds the probe back until Keycloak is ready, and starts it only when `COMPOSE_PROFILES` contains `retry-probe`:

[source,bash]
----
COMPOSE_PROFILES=retry-probe ./scripts/start-integration-container.sh
----

With the `multi-idp` compose profile the script also starts the identity providers first and the application only after the Zitadel key-set check, so that the application loads a published Zitadel signing key.

== Configuration

=== Keycloak Realms

The integration tests use **four Keycloak realms** to validate different JWT configuration patterns:

==== Benchmark Realm (Well-Known Discovery)

* **Realm**: `benchmark`
* **Client**: `benchmark-client` / `benchmark-secret` (confidential client)
* **User**: `benchmark-user` / `benchmark-password`
* **Configuration**: Uses well-known discovery endpoint
* **Purpose**: Tests automatic JWKS resolution via `/.well-known/openid-configuration`

[source,properties]
----
sheriff.token.issuers.keycloak.issuer-identifier=https://keycloak:8443/realms/benchmark
sheriff.token.issuers.keycloak.jwks.http.well-known-url=https://keycloak:8443/realms/benchmark/.well-known/openid-configuration
----

==== Integration Realm (Direct JWKS)

* **Realm**: `integration`
* **Client**: `integration-client` / `integration-secret` (confidential client)
* **User**: `integration-user` / `integration-password`
* **Configuration**: Uses direct JWKS URL
* **Purpose**: Tests explicit JWKS endpoint configuration

[source,properties]
----
sheriff.token.issuers.integration.issuer-identifier=https://keycloak:8443/realms/integration
sheriff.token.issuers.integration.jwks.http.url=https://keycloak:8443/realms/integration/protocol/openid-connect/certs
----

==== Client-Engine Realm (Discovery-Resolved Endpoints)

* **Realm**: `client-engine`
* **Clients**: `integration-client` / `integration-secret`, `dpop-client` / `dpop-secret`, `refresh-fast-client` / `refresh-fast-secret` (35 s access tokens), `private-key-jwt-client` (signed client assertion, no shared secret)
* **User**: `integration-user` / `integration-password`
* **Configuration**: `frontendUrl` is `https://localhost:1443` — the base the test JVM actually reaches
* **Purpose**: Lets the client-engine refresh specs resolve their endpoints from a real `/.well-known/openid-configuration` round trip through the production `DiscoveryResolver`

Because this realm advertises the externally reachable authority, its issuer identity and its endpoint
authority coincide. The `integration` realm cannot serve this purpose: it advertises the Docker-internal
`https://keycloak:8443`, so a discovery round trip against it would resolve endpoints unreachable from
the test JVM.

[source,properties]
----
sheriff.token.issuers.client-engine.issuer-identifier=https://localhost:1443/realms/client-engine
sheriff.token.issuers.client-engine.jwks.http.well-known-url=https://localhost:1443/realms/client-engine/.well-known/openid-configuration
----

==== Single-Use Refresh Realm (AS-Enforced Rotation)

* **Realm**: `single-use-refresh`
* **Client**: `single-use-client` / `single-use-secret` (confidential client)
* **User**: `integration-user` / `integration-password`
* **Configuration**: `revokeRefreshToken: true` with `refreshTokenMaxReuse: 0`; `frontendUrl` is `https://localhost:1443`
* **Purpose**: Serves `RefreshSingleUseSpecIT`, which drives the engine against a server that revokes a refresh token on redemption and refuses any later presentation of it

Both settings are realm-scoped in Keycloak, which is why this is a realm of its own rather than another
client in `client-engine`: enabling them there would change the posture every other client-engine spec
relies on — notably `RefreshErrorPathSpecIT`, which records the opposite, permissive property.

All four realms are automatically imported into Keycloak during container startup via the `docker-compose.yml` configuration.

=== URL Adaptation for Docker Networking

==== Docker Networking Configuration

The integration tests use HTTPS throughout with proper certificate validation:

* **External access**: Tests access Keycloak via `localhost:1443` (Docker HTTPS port mapping)
* **Internal access**: Application container accesses Keycloak via `keycloak:8443` (Docker network HTTPS hostname)
* **Certificate validation**: Self-signed certificates are used with proper truststore configuration

==== Current Configuration

All four realms use consistent HTTPS configuration. The benchmark and integration realms advertise the
Docker-internal authority; the client-engine and single-use-refresh realms advertise the externally
reachable one, which is what makes their endpoints discoverable from the test JVM:

[source,properties]
----
# Benchmark realm with well-known discovery
sheriff.token.issuers.keycloak.issuer-identifier=https://keycloak:8443/realms/benchmark
sheriff.token.issuers.keycloak.jwks.http.well-known-url=https://keycloak:8443/realms/benchmark/.well-known/openid-configuration

# Integration realm with direct JWKS URL
sheriff.token.issuers.integration.issuer-identifier=https://keycloak:8443/realms/integration
sheriff.token.issuers.integration.jwks.http.url=https://keycloak:8443/realms/integration/protocol/openid-connect/certs

# Client-engine realm, advertised on the externally reachable base so the test JVM can discover it
sheriff.token.issuers.client-engine.issuer-identifier=https://localhost:1443/realms/client-engine
sheriff.token.issuers.client-engine.jwks.http.well-known-url=https://localhost:1443/realms/client-engine/.well-known/openid-configuration

# Single-use refresh realm, likewise externally advertised; revokes a refresh token on redemption
sheriff.token.issuers.single-use-refresh.issuer-identifier=https://localhost:1443/realms/single-use-refresh
sheriff.token.issuers.single-use-refresh.jwks.http.well-known-url=https://localhost:1443/realms/single-use-refresh/.well-known/openid-configuration
----

==== Key Points

1. **HTTPS enforcement**: All communication uses HTTPS with certificate validation
2. **Authority per realm**: The benchmark and integration realms use the internal Docker hostname for issuer identifiers and JWKS URLs; the client-engine and single-use-refresh realms use the external `localhost:1443` base, so their discovery documents advertise endpoints the test JVM can connect to
3. **Certificate trust**: Application trusts Keycloak certificates via configured truststore
4. **Token validation**: JWT issuer claims match the configured issuer identifiers

=== HTTPS Setup

Self-signed certificates via `generate-certificates.sh`:

* Truststore: `localhost-truststore.p12` (password: `localhost-trust`)
* Subject: `CN=localhost`
* SAN: `dns:localhost,dns:keycloak,dns:dex,ip:127.0.0.1,ip:0.0.0.0`
