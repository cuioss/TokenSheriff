= Token-Sheriff Quarkus Runtime
:toc: left

Runtime module for Quarkus integration providing JWT token validation with CDI integration, configuration management, health checks, and metrics collection.

== Maven Coordinates

For Maven dependency information, see xref:../README.adoc#_maven_coordinates[Maven Coordinates] in the parent module documentation.

== Core Concepts

=== Configuration Management

* Direct configuration access through MicroProfile Config API
* Support for multiple JWT issuers with individual configurations
* Flexible parser settings for token validation
* HTTP JWKS loader configuration with caching and retry mechanisms

=== CDI Integration

* CDI producers for TokenValidator and BearerTokenResult
* `@BearerAuth` interceptor for declarative endpoint security
* Parameter injection of `BearerTokenResult` via `@BearerToken`
* Integration with Quarkus dependency injection container
* Request-scoped bearer token validation

=== Health Monitoring

* Liveness check that always reports `UP` and exposes the token validator state as data. A JWKS endpoint problem after startup does not affect liveness. An invalid issuer configuration aborts application startup instead, so the container exits and its restart policy applies
* Readiness check for JWKS endpoint connectivity
* See xref:../doc/integration/health-checks.adoc[Health Checks Documentation] for detailed configuration and usage

=== Metrics Collection

* Integration with Micrometer for JWT validation metrics
* Token validation success/failure counters
* Performance metrics for validation operations
* See xref:../doc/integration/metrics-integration.adoc[Metrics Integration Documentation] for comprehensive monitoring setup

=== CDI Producers

==== TokenValidatorProducer
CDI producer for JWT token validators:

* link:src/main/java/de/cuioss/sheriff/token/quarkus/producer/TokenValidatorProducer.java[TokenValidatorProducer]
* Produces one application-scoped `TokenValidator` covering every enabled issuer
* When the `sheriff.token.issuers.*` namespace yields at least one enabled issuer, the `TokenValidator` is built at startup, so an invalid issuer configuration fails application startup instead of the first request
* An application with no enabled issuer under `sheriff.token.issuers.*` starts without building it
* Applications that bring their own `TokenValidator`: the startup check looks at the enabled issuers under `sheriff.token.issuers.*` alone. With none configured there, no `TokenValidator` is touched at startup. With at least one, the startup step resolves whichever bean answers the default-qualified `TokenValidator` injection and forces its creation; when the application's bean replaces the extension's producer, that is the application's bean, and it is created at startup rather than on first use

==== BearerTokenProducer
CDI producer for bearer token validation:

* link:src/main/java/de/cuioss/sheriff/token/quarkus/producer/BearerTokenProducer.java[BearerTokenProducer]
* Produces BearerTokenResult instances for injection
* Handles token extraction from HTTP requests
* Supports scope, role, and group validation

== Usage Examples

=== Basic Configuration

[source, yaml]
----
sheriff:
  token:
    issuers:
      my-issuer:
        enabled: true
        issuer-identifier: "https://auth.example.com"
        jwks:
          http:
            url: "https://auth.example.com/.well-known/jwks.json"
            refresh-interval-seconds: 300
----

NOTE: An issuer is only considered when it carries `enabled: true`. An issuer without it is ignored.

=== Multiple Issuers

[source, yaml]
----
sheriff:
  token:
    issuers:
      issuer-one:
        enabled: true
        issuer-identifier: "https://auth1.example.com"
        jwks:
          http:
            well-known-url: "https://auth1.example.com/.well-known/openid-configuration"
      issuer-two:
        enabled: true
        issuer-identifier: "https://auth2.example.com"
        jwks:
          file-path: "classpath:keys/public-key.pem"
----

=== CDI Usage

[source, java]
----
@Inject
TokenValidator tokenValidator;

public void processRequest(String jwtString) {
    try {
        AccessTokenContent token = tokenValidator.createAccessToken(AccessTokenRequest.of(jwtString));
        Optional<String> subject = token.getSubject();
        List<String> roles = token.getRoles();
        // Process valid token
    } catch (TokenValidationException e) {
        // Handle validation failure
        LOGGER.error("Token validation failed: %s", e.getMessage(), e);
    }
}
----

# Algorithm preferences
sheriff.token.issuers.my-issuer.algorithm-preferences=RS256,RS384,RS512
----

=== Maximum Key Staleness (opt-in)

`sheriff.token.issuers.<name>.jwks.http.max-staleness-seconds` bounds, in seconds, how long an issuer's
installed keys may go without a successful refresh. It is off by default: unset, installed keys are served
while background refreshes keep failing, and the issuer stays usable.

When set, the issuer's JWKS loader leaves `OK` once the installed keys have gone longer than the bound
without a successful refresh. The issuer then stops resolving and its tokens are rejected until a refresh
succeeds again; no key is dropped, so recovery is immediate. The bound is checked only when a background
refresh cycle fails, so it is not an immediate rejection deadline: tokens can still resolve after the
configured duration until the next failed cycle (or while a slow refresh is still running). Choose a bound
of at least several refresh intervals, so a single failed refresh does not take the issuer out.

[source, properties]
----
# Leave OK after 1 hour without a successful refresh (refresh every 10 minutes)
sheriff.token.issuers.my-issuer.jwks.http.refresh-interval-seconds=600
sheriff.token.issuers.my-issuer.jwks.http.max-staleness-seconds=3600
----

The key applies only to issuers that load their JWKS over HTTP (`jwks.http.url` or
`jwks.http.well-known-url`). Application startup fails for an unparseable or non-positive value, for a value
combined with `jwks.http.refresh-interval-seconds=0`, and for a value on an issuer configured with
`jwks.file-path` or `jwks.content`. See
xref:../../doc/adr/0017-A_JWKS_loader_reports_OK_only_with_usable_keys_and_retries_only_transient_discovery_failures.adoc[ADR-0017]
and
xref:../../doc/adr/0026-Orphaned_or_unresolvable_extension_configuration_fails_startup_instead_of_being_ignored.adoc[ADR-0026].

=== Unknown-kid Refresh and Initial-load Retry (opt-in)

Two further per-issuer keys sit next to `max-staleness-seconds`. Both are off by default, so an issuer
without them behaves exactly as before.

* `sheriff.token.issuers.<name>.jwks.http.unknown-kid-refresh-window-seconds` — unset, a token whose `kid`
  the installed key set does not hold is rejected without any fetch. Set to a whole number of seconds from
  `5` to `3600`, such a miss schedules at most one background JWKS fetch per window for this issuer. The
  token that triggered the fetch is still rejected; a later token with the same `kid` resolves once the
  fetched key set, holding that `kid`, has been installed.
* `sheriff.token.issuers.<name>.jwks.http.initial-load-retry` — `false` by default, in which case a failed
  initial JWKS load is retried only at the refresh interval. `true` retries it after 1 second, the delay
  doubling up to 30 seconds and never above the refresh interval, until keys are installed.

[source, properties]
----
# Allow at most one background JWKS fetch per 30 seconds for an unknown kid
sheriff.token.issuers.my-issuer.jwks.http.unknown-kid-refresh-window-seconds=30
# Recover quickly when the IdP is not reachable at application startup
sheriff.token.issuers.my-issuer.jwks.http.initial-load-retry=true
----

The window is a refresh rate limit, not a recovery deadline: tokens carrying invented `kid` values can claim
successive windows, and the fetched key set is installed only if it holds the requested `kid`, so a
legitimate rotation can be deferred until the periodic refresh picks it up.

Like `max-staleness-seconds`, both keys apply only to issuers that load their JWKS over HTTP. Application
startup fails for an unparseable or out-of-range value and for a value on an issuer configured with
`jwks.file-path` or `jwks.content`. Combined with `jwks.http.refresh-interval-seconds=0`, any window value and
`initial-load-retry=true` fail startup as well; `initial-load-retry=false` is valid with a zero refresh
interval. See
xref:../../doc/adr/0030-An_opt-in_unknown-kid_refresh_claims_one_window_per_loader_and_installs_only_a_key_set_holding_the_kid.adoc[ADR-0030]
and
xref:../../doc/adr/0026-Orphaned_or_unresolvable_extension_configuration_fails_startup_instead_of_being_ignored.adoc[ADR-0026].

== Best Practices

=== Configuration Management

* Use YAML format for complex configurations with multiple issuers
* Set appropriate cache TTL values based on key rotation frequency
* Configure reasonable timeout values for JWKS endpoints
* Enable health checks in production environments

=== Security Considerations

* Validate all required JWT claims (audience, issuer, expiration)
* Use appropriate leeway values for clock skew tolerance
* Restrict allowed signing algorithms to secure options
* Regularly monitor JWKS endpoint availability

=== Performance Optimization

* Configure JWKS caching to reduce network calls
* Set appropriate refresh intervals for key rotation
* Monitor validation metrics to identify performance issues
* Use connection pooling for JWKS HTTP clients

=== Error Handling

* Implement proper fallback mechanisms for JWKS failures
* Log validation failures with appropriate detail levels
* Monitor health check status for early problem detection
* Handle network timeouts gracefully

== Technical Details

=== Thread Safety

* All CDI beans are thread-safe and can be used concurrently
* JWKS caching uses thread-safe data structures
* Metrics collection is atomic and thread-safe
* Health checks handle concurrent execution appropriately

=== Performance Characteristics

* JWKS caching reduces validation latency significantly
* Token validation is CPU-intensive but scales well
* Memory usage scales with number of cached keys
* Network I/O is minimized through intelligent caching

=== Dependencies

* Requires Quarkus 3.x framework
* Integrates with SmallRye Config for configuration management
* Uses Micrometer for metrics collection
* Depends on SmallRye Health for health check integration
* Compatible with GraalVM native image compilation
* The exception mappers (`application/problem+json` rendering) and the access-log filter are registered for RESTEasy Classic (`quarkus-resteasy`) only. Applications on Quarkus REST (RESTEasy Reactive) do not get the `application/problem+json` mapping or the access-log filter automatically.

=== Native Image Support

* Full GraalVM native image compatibility
* Automatic reflection and runtime initialization configuration
* See xref:../doc/configuration/native-image-configuration.adoc[Native Image Configuration] for detailed configuration and testing information
