= Test-to-Implementation Mapping
:toc: left
:toclevels: 3
:toc-title: Table of Contents
:sectnums:
:source-highlighter: highlight.js

This document maps each production package of the production modules to the test
classes that exercise it. It also lists the cross-cutting guards that check the code base
as a whole, and the integration-test specifications per feature area.

Use it to find where a behaviour is tested before you change it, and to see which test
class a new test belongs in. The mapping names test classes only; it makes no statement
about coverage figures. The benchmark modules under `benchmarking/` are not production modules
and are not mapped.

Most test classes live in the same package as the production code they test, under
`src/test/java`. Where a test class sits in a different test package, its row names that
package. Where a production package has no test class of its own, the row says so.

[#refresh-path-coverage-gate]
=== Refresh-path coverage gate

`token-sheriff-client/pom.xml` binds the `refresh-path-coverage-check` execution: a JaCoCo `check` rule
with element `CLASS`, scoped by an explicit `<includes>` list to the classes that own the refresh path,
with floors `BRANCH >= 0.80` and `INSTRUCTION >= 0.90`
(xref:../adr/0003-Scope_refresh-path_coverage_gates_by_class_granularity_not_module-wide_threshold.adoc[ADR-0003]).
It sits in the module's always-active `<build><plugins>`, because the CI lane is an externally owned
reusable workflow that cannot pass a profile flag. The `<includes>` list is the authoritative set of
guarded classes and is maintained by hand, in dotted FQCN form (a nested class is `Outer.Inner`, never
`Outer$Inner`).

An include entry that matches no class makes the rule evaluate zero classes and report success
(JaCoCo's `BundleChecker` invokes no limit), so a green build is no evidence the rule is bound.
`RefreshPathCoverageGuardTest` fails the build on both drift directions: an *inert* entry (a listed
FQCN that binds to no class) and a *missing* sibling (a refresh-path class absent from the list). The
missing-sibling leg demands a class only when its package is a guarded package *and* its first
camel-case word is one the list already uses; a refresh-path class failing either condition must be
added by hand.

The gate complements the other two coverage instruments: the opt-in `-Pcoverage` `BUNDLE` gate
inherited from `cui-java-parent` (module-wide baseline, local only) and the SonarCloud new-code gate
(changed lines only, blind to coverage removed from existing lines). See
xref:../client/specification/test-strategy.adoc[Client test strategy] § Coverage gates.

[#integration-test-skip-binding]
=== Integration-test skip binding

A module's Failsafe tier is switched off by binding its own skip property to `skipTests` in the POM
`<properties>` — `<ownSkipProperty>${skipTests}</ownSkipProperty>` — with an explicit literal default
`<skipTests>false</skipTests>`; never in the Failsafe `<configuration>` block. A `<properties>` default
yields to a command-line `-D` of the same key, a `<configuration>` value does not, and some Failsafe
versions do not treat their skip property as an alias of `skipTests`. The binding keeps three lanes
correct:

* `-DskipTests`: the module's own flag interpolates to the same value, the integration-test JVM never
  starts and writes no coverage data, so a downstream coverage gate sees honestly absent data.
* An explicit `-D` of the module's own skip property: wins over the property default, so the
  integration tier alone can be forced on or off; the gate is then graded on unit coverage only.
* Neither flag: both properties keep their literal defaults, the tier runs and every coverage gate is
  enforced.

[#keeping-current]
== How to keep this current

Update this mapping in the same pull request that adds, moves, renames or splits a test
class. A test class that is not listed here, or a listed class that no longer exists, is a
defect in this document. The same holds for the fixtures that are not test classes, listed after
each module table.

The mapping is kept by hand. Its check is a search of this document for every test class and
every fixture the pull request adds, moves, renames or splits. Each must be found in one place:

* a guard class, one that checks the code base as a whole rather than one package, in the
  xref:#cross-cutting-guards[Cross-cutting guards] section, in the row of its module;
* an integration-test specification of `token-sheriff-quarkus-integration-tests`, or one of its
  support classes, in the xref:#integration-tests[Integration-test specifications] section;
* every other test class and fixture in the section of its module.

Each entry names its test package where that differs from the production package. After a rename
or a move, the search for the old name must find no entry.
