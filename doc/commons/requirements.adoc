== Overview

Functional and non-functional requirements for the `commons` base layer — the
`de.cuioss.sheriff.token.commons.*` packages inside `token-sheriff-validation`. Commons
gathers the four cross-cutting concerns every capability sits on: *IdP transport*, the
*error model*, *security events* and *metrics*. It *moves bytes, raises typed errors,
counts events and exposes metrics; it never interprets a token's trust* — that is the
validation layer's job.

Requirement IDs use the `COMMONS-N` scheme, grouped by concern. IDs are stable identifiers referenced across documentation and the
xref:threat-model.adoc[threat model]; they are not sequential across groups.

== Transport requirements

_Validation-side outbound IdP HTTP and the shared transport primitives. See xref:specification/transport.adoc[Transport specification] and
xref:threat-model.adoc[Threat Model]._

[#COMMONS-1]
=== COMMONS-1: Outbound IdP HTTP transport

Commons owns the validation-side outbound HTTP to an OpenID Provider — discovery and
JWKS — and provides the hardened transport primitives (built on `cui-http`) it is
performed with. The client capability builds its *own* back-channel HTTP (token, userinfo,
revocation, PAR) on those primitives and applies its own in-module egress control
(xref:../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]); it
does not route those fetches through a commons transport service.

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (single hardened HTTP surface).

[#COMMONS-2]
=== COMMONS-2: TLS enforcement

All outbound IdP requests MUST use TLS 1.2 or higher with certificate validation. Plain
HTTP endpoints MUST be rejected by default. TLS configuration is centralized (via `cui-http`'s
`SecureSSLContextProvider`), not per-caller.

*Carve-out — cleartext opt-in.* Each side has one explicit, default-off switch that admits
cleartext `http://` endpoints, intended for local development and integration tests, never
production: per issuer on the validation side (`allowInsecureHttp(true)` on `HttpJwksLoaderConfig` /
`WellKnownConfig`, `sheriff.token.issuers.<name>.jwks.http.allow-insecure-http`), and client-wide on
the client side (`ClientConfiguration.allowInsecureHttp`, `sheriff.client.allow-insecure-http`). With
the switch set, an `http://` endpoint is fetched without TLS, so what it returns is open to
interception and tampering; the TLS requirements still apply to every `https://` endpoint. The client
switch does not relax the refusal of a non-`https` endpoint advertised by an `https` issuer's
discovery document
(xref:../adr/0028-Discovery_refuses_a_non-https_endpoint_advertised_by_an_https_issuer_regardless_of_allowInsecureHttp.adoc[ADR-0028]).

*Carve-out — hostname matching.* Certificate validation decomposes into chain trust, expiry,
algorithm constraints, and hostname matching. The first three are unconditional and admit no
opt-out. Hostname matching alone is a per-configuration, default-ON knob that a deployment MAY
relax by explicit opt-in; when it is relaxed, the remaining checks stay fully enforced, so an
untrusted or expired certificate is still rejected. The knob exists for development and test
topologies serving SAN-mismatched certificates and MUST NOT be used in production — a deployment
that opts out accepts a narrowed mitigation. It is reachable from two configuration surfaces:
`sheriff.token.issuers.<name>.jwks.http.verify-hostname` (per-issuer, validation) and
`sheriff.client.verify-hostname` (client-wide, client engine). See
xref:../adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008].

*Client back-channel origin.* When the client engine's optional back-channel origin
(`sheriff.client.back-channel-origin`, xref:../client/requirements.adoc#CLIENT-24[CLIENT-24]) is set,
back-channel calls whose advertised endpoint shares the issuer's origin are sent to that configured
origin with path and query kept, and every other endpoint is contacted unchanged. The TLS
requirements above — including hostname matching under `sheriff.client.verify-hostname` — then
apply to the back-channel host actually contacted, so its certificate is validated against its own
name. The setting relaxes no part of certificate validation and leaves the issuer identity and the
`issuer` / `iss` checks unchanged; the validation-side JWKS URL is configured separately and is not
rewritten. See xref:specification/transport.adoc#client_back_channel_origin[Transport specification].

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §2.6], https://www.rfc-editor.org/rfc/rfc8414[RFC 8414 §2] (metadata retrieved over TLS).

[#COMMONS-3]
=== COMMONS-3: SSRF defence for advertised URLs

Any URL taken from an IdP-controlled source (`jwks_uri`, discovery endpoints, `userinfo`,
or any endpoint advertised via discovery) MUST be constrained before it is fetched:
scheme restricted to HTTPS unless the cleartext opt-in of
xref:#COMMONS-2[COMMONS-2] is set, and the host subject to a host-address egress policy
(`EgressPolicy`) that blocks loopback, link-local (including cloud metadata), site-local,
unique-local, carrier-grade NAT, wildcard, broadcast and multicast addresses by default.

Two independent `EgressPolicy` instances enforce this:

* *Validation side* — the well-known discovery and JWKS fetches (`HttpWellKnownResolver`,
  `HttpJwksLoader`), configured per issuer.
* *Client side* — every discovery and back-channel call of the client engine (discovery, token,
  PAR, userinfo, revocation), configured on `ClientConfiguration`. It checks the URL *actually
  contacted*, after the back-channel origin rewrite, and the client back channel keeps its own path
  structure and scheme checks besides.

The secure default can refuse an endpoint a deployment configured or an issuer advertised on an
internal address. The relaxations are explicit: on the client, `allowLoopbackEgress`
(`sheriff.client.allow-loopback-egress`) lifts the loopback refusal only, and `allowedEgressHosts`
(`sheriff.client.allowed-egress-hosts`) names hosts that bypass the address-range check entirely; the
validation side has its own per-issuer settings. The policy resolves the host immediately before the
fetch, so a DNS answer that changes before the HTTP client connects is not seen (the DNS-rebinding
limit).

*Allow-list entries are bare hosts, refused fail-closed.* Every egress allow-list entry, on either
side, MUST be a bare host as `URI.getHost()` reports it: an ASCII host name of letter-digit-hyphen
labels whose final label, when there is more than one, starts with a letter, optionally ending in
one terminal root dot, a dotted
IPv4 literal, or an IPv6 literal, bare or bracketed. Every other entry MUST be refused when the
configuration is built — never stored, never silently ignored — with a fixed text that does not
contain the entry. The refused classes are:

* `null`, and a blank entry;
* a port in any form (`keycloak:8080`, `[::1]:443`, any other single-colon form);
* a scheme or other URL syntax: `/`, `@`, `?` or `#` (`https://keycloak`, `user@keycloak`);
* a name with `%`, which includes a zoned IPv6 literal (`[fe80::1%eth0]`, `fe80::1%eth0`): for
  `http://[fe80::1%eth0]/` `URI.getHost()` reports `[fe80::1%eth0]`, but the zone id names an
  interface of the local machine and an allow-list entry bypasses the link-local refusal, so `%` is
  refused in every entry;
* whitespace, and a control character;
* a non-ASCII character;
* an underscore, or any other character outside letter-digit-hyphen labels (`idp_internal`);
* a dotted name whose final label does not start with a letter (`idp.123`, `idp.1example`), for
  which `URI.getHost()` reports no host;
* a malformed IPv6 literal (`::g`, `[::1`, `[10.0.0.1]`).

The one rule
is `commons.transport.EgressHostValidator`; `EgressPolicy.EgressPolicyBuilder.allowedHost`,
`WellKnownConfig.WellKnownConfigBuilder.allowedEgressHost`,
`HttpJwksLoaderConfig.HttpJwksLoaderConfigBuilder.allowedEgressHost` and the client's
`ClientConfiguration` all apply it. All four builders store an admitted entry in the canonical form
`EgressHostValidator.requireBareHost` returns — lower-cased, a bare IPv6 literal in bracketed form — so
a bare IPv6 entry matches the bracketed host of an IPv6 URL, and `ClientConfiguration` reports,
compares and prints its list in that form; matching stays case-insensitive. Under
Quarkus a port-carrying element of `sheriff.token.issuers.<name>.jwks.http.allowed-egress-hosts`
fails startup naming the property; on this issuer path blank CSV elements are dropped and the
whitespace around an element is trimmed before the rule runs, so `keycloak, dex` admits both hosts. The
client path does not trim: a port-carrying element, or one with surrounding whitespace, of
`sheriff.client.allowed-egress-hosts` fails the client mapping, so `keycloak, dex` fails it there, while
the configuration reader drops empty CSV elements before the rule runs.

* Source: https://owasp.org/www-community/attacks/Server_Side_Request_Forgery[OWASP SSRF], https://github.com/advisories/GHSA-7vw6-5q2f-7w5r[CVE-2026-1180], https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4.10].

[#COMMONS-4]
=== COMMONS-4: Response resilience and DoS bounds

Every outbound fetch MUST apply a connect/read timeout, a response-size limit, and bounded
retry/backoff. Large or slow metadata, JWKS or userinfo responses MUST NOT be able to
exhaust memory or block a caller indefinitely.

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (availability), https://www.rfc-editor.org/rfc/rfc7230[RFC 7230] (message framing bounds).

[#COMMONS-17]
=== COMMONS-17: One bounded response-body handler

The response-size limit of xref:#COMMONS-4[COMMONS-4] MUST be enforced by one public handler,
`commons.transport.BoundedBodyHandler`, for the validation-side discovery and JWKS reads and for the
client's back-channel reads alike. It counts bytes while the body streams, never accepts more than the
ceiling into the assembled body, and offers two policies:

* *Fail* — a response advertising a `Content-Length` above the ceiling is refused before a byte of its
  body is read; a body crossing the ceiling while streaming is refused at the crossing. Both fail the
  read with an `IOException` whose message names the ceiling and its `boundOrigin`.
* *Truncate* — the body is read up to the ceiling and the result carries exactly the first ceiling
  bytes with an explicit truncation signal.

The handler bounds its own work as well as the bytes: the body read so far is kept in one array that
grows by doubling, so the objects a body costs grow with the logarithm of its size, not with the number of
buffers it arrives in, and an empty buffer costs nothing. The array never exceeds the ceiling and is at most
twice the bytes received, or the first allocation (1024 bytes, or the ceiling when that is smaller) when
that is larger. During a growth step the old and the new array are both live, so the memory held while the
body streams peaks below twice the ceiling plus the
buffers of the delivery in flight; assembling and, for the string variant, decoding the result at
completion peaks at a small constant multiple of the ceiling. Under the fail policy, when the handler
observes a `Content-Length` header that is not a valid number, it cancels the subscription without
requesting a byte, and the body future fails with an `IOException` carrying a fixed message that does not
echo the header value.

That guarantee is the handler's own. Whether the surrounding client reaches the handler, and whether it
parses the header itself first, is the client's behaviour: the JDK HTTP/1.1 client (observed on JDK 25)
parses `Content-Length` itself after the handler returned, so there the caller of `HttpClient.send`
receives the JDK's own `IllegalArgumentException` (cause `NumberFormatException`) carrying the raw header
value, and the handler's fixed message is not delivered. The handler has no hook before that parse, so the
mapping belongs to the caller of `send`. The client's discovery, PAR, userinfo and revocation clients send
through `BackChannelHttp.send`, and the token endpoint client through its own send; each catches that
`IllegalArgumentException` and fails the call with a `TransportException` whose message is the endpoint's
failure context and the fixed text `BackChannelHttp.MALFORMED_RESPONSE` (when its body handler observed a
success status, the token endpoint reports it as its post-redemption failure), neither chaining the JDK's exception nor echoing its
message. Request-side and response-side faults are told apart by the documented `HttpClient.sendAsync`
contract: an `IllegalArgumentException` thrown synchronously, for a request the client refuses before
sending, is a request-side fault and propagates unchanged; one that completes the exchange exceptionally is
mapped, including for a `204` or other no-body reply whose `Content-Length` the JDK parses before any body
handler runs (the token endpoint, never seeing that status, reports it as a pre-redemption failure). The
validation-side discovery and JWKS reads hand the handler to cui-http, whose adapter performs
the send, so this repository has no send call there to map. A caller therefore treats the message of any
exception that comes out of an HTTP exchange as remote content and sanitises it before logging.

The ceiling is accepted from 0 to `Integer.MAX_VALUE - 8` bytes; any other value is refused when the
handler is created. The handler logs nothing. See
xref:specification/transport.adoc#bounded_response_body[Transport specification] and
xref:../adr/0031-Bearer_extraction_scope_challenge_sanitiser_escape_and_bounded_body_reads_are_public_commons_helpers.adoc[ADR-0031].

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (availability), https://www.rfc-editor.org/rfc/rfc9110#section-8.6[RFC 9110 §8.6] (`Content-Length`).

[#COMMONS-5]
=== COMMONS-5: Discovery (`.well-known`)

Commons fetches and parses OpenID Provider metadata from
`.well-known/openid-configuration` (OIDC Discovery) and OAuth authorization-server
metadata (RFC 8414). The advertised `issuer` MUST be validated against the configured
issuer; advertised endpoint URLs are subject to xref:#COMMONS-3[].

* Source: https://openid.net/specs/openid-connect-discovery-1_0.html[OpenID Connect Discovery 1.0 §4.3], https://www.rfc-editor.org/rfc/rfc8414[RFC 8414 §3.3].

[#COMMONS-6]
=== COMMONS-6: JWKS retrieval

Commons retrieves JWKS documents (RFC 7517) over the hardened transport, subject to
xref:#COMMONS-2[], xref:#COMMONS-3[] and xref:#COMMONS-4[], and caches them (xref:#COMMONS-8[]). Key
*material parsing* is a transport-format concern; *trust decisions* about the resulting
keys remain in validation.

* Source: https://www.rfc-editor.org/rfc/rfc7517[RFC 7517] (reused from validation bibliography).

[#COMMONS-7]
=== COMMONS-7: Extended IdP endpoints (client-facing)

Commons defines the transport contract for the extended IdP endpoints: token (RFC 6749),
userinfo (OIDC Core), revocation (RFC 7009), introspection (RFC 7662), end-session /
RP-initiated logout, and PAR (RFC 9126). Each is exercised by a dedicated MockWebServer
dispatcher in the `generators` test artifact (default + adversarial modes), so the contract
is testable independently of the client engine. The client drives token, userinfo,
revocation and PAR over its own back channel; end-session is a front-channel redirect the
client builds; introspection has a dispatcher only and no client flow.

* Source: https://www.rfc-editor.org/rfc/rfc6749[RFC 6749], https://www.rfc-editor.org/rfc/rfc7009[RFC 7009], https://www.rfc-editor.org/rfc/rfc7662[RFC 7662], https://www.rfc-editor.org/rfc/rfc9126[RFC 9126], https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OIDC RP-Initiated Logout 1.0].

[#COMMONS-8]
=== COMMONS-8: Caching of discovery and JWKS

Discovery documents and JWKS are cached with a bounded lifetime to avoid re-fetching on
every validation. Cache refresh MUST re-apply xref:#COMMONS-2[]–xref:#COMMONS-4[].

* Source: https://openid.net/specs/openid-connect-discovery-1_0.html[OpenID Connect Discovery 1.0 §4.3] (caching guidance).

== Error-model requirements

_See xref:specification/error-model.adoc[Error-model specification]._

[#COMMONS-9]
=== COMMONS-9: Typed exception hierarchy

Library code (the `commons` and `validation` packages, and the client engine — pure
Java) MUST signal failure through a typed exception hierarchy defined in `commons.error`.
Library code MUST NOT produce HTTP problem documents — that is not its layer.

* Source: https://www.rfc-editor.org/rfc/rfc9457[RFC 9457 §3] (problem details are an HTTP-edge concern).

[#COMMONS-10]
=== COMMONS-10: RFC 9457 rendering at every HTTP edge

Every HTTP edge — `token-sheriff-validation-quarkus`, `token-sheriff-client-quarkus`,
and any future non-Quarkus/RESTEasy edge (e.g. a portal adapter) — MUST map the typed
exceptions to `application/problem+json` per RFC 9457. Existing validation rejection
responses are retrofitted to this contract.

* Source: https://www.rfc-editor.org/rfc/rfc9457[RFC 9457].

[#COMMONS-11]
=== COMMONS-11: Inbound IdP error normalization

Commons MUST normalize inbound IdP error responses (OAuth `error` / `error_description`
per RFC 6749 §5.2) into the typed model the edges render — one contract, both directions.

* Source: https://www.rfc-editor.org/rfc/rfc6749#section-5.2[RFC 6749 §5.2] (reused from validation bibliography).

[#COMMONS-12]
=== COMMONS-12: No internal-detail leakage

Rendered problem documents MUST carry only a safe `type` / `title` / `detail`, and MUST NOT
leak stack traces, internal identifiers, upstream URLs, or credential material.

* Source: https://www.rfc-editor.org/rfc/rfc9457#section-3[RFC 9457 §3] (member semantics), https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (information disclosure).

[#COMMONS-16]
=== COMMONS-16: Printable-ASCII rendering of untrusted text

Untrusted text bound for a sink that must carry printable ASCII only MUST be rendered by the one
commons-layer sanitiser, `ErrorTextSanitizer`, through its printable-ASCII form
`escapeNonPrintableAscii(value, maxLength, truncationMarker)`: every character outside U+0020 to
U+007E, and the backslash itself, is written as an upper-case backslash-`u` four-digit escape, the
value is cut to `maxLength` source characters before escaping, and a cut is marked. No second
sanitiser is introduced
(xref:../adr/0022-A_flow_context_is_single-use_and_untrusted_text_is_sanitised_by_one_commons-layer_utility.adoc[ADR-0022]).
See xref:specification/error-model.adoc#printable_ascii_escape[Error-model specification].

* Source: https://cwe.mitre.org/data/definitions/117.html[CWE-117] (improper output neutralization for logs).

== Security-event requirements

_See xref:specification/observability.adoc[Observability specification]._

[#COMMONS-13]
=== COMMONS-13: Shared security-event surface

`SecurityEventCounter` and the security-event types live in `commons.events` so validation
and the client share one event surface. The counter MUST remain thread-safe and
free of any Micrometer dependency; Quarkus extensions expose it as before.

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (security monitoring).

[#COMMONS-14]
=== COMMONS-14: Event categorization

Each security event MUST carry a category (structure / signature / semantic) usable by an
edge to select a response. Event categories MUST NOT depend on any validation-layer type
(the ArchUnit boundary — see xref:architecture.adoc#archunit[Architecture]).

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4].

== Metrics requirements

[#COMMONS-15]
=== COMMONS-15: Metric identifiers defined once

Metric identifiers / contracts (`sheriff.token.*`) are defined once in `commons.metrics`.
Each Quarkus extension wires them to Micrometer; the identifiers themselves carry no
Micrometer dependency.

* Source: https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4] (observability), project metric-naming convention (`sheriff.token.*`).
