== Overview

_Realizes xref:../requirements.adoc#COMMONS-1[COMMONS-1]–xref:../requirements.adoc#COMMONS-8[COMMONS-8].
See xref:../threat-model.adoc[Threat Model] and xref:../architecture.adoc[Architecture]._

`commons.transport` owns the validation-side outbound HTTP to an OpenID Provider —
discovery and JWKS — and the shared transport primitives (TLS enforcement, SSRF egress
policy, timeouts, response-size limits, retry/backoff, the `cui-http` client, and
discovery / JWKS caching). It *moves bytes* — it never decides whether a token is
trustworthy. The client engine builds its *own* back-channel HTTP (token, userinfo,
revocation, PAR) on these primitives
(xref:../../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]).

== Endpoints

[cols="1,2,2,1", options="header"]
|===
| Endpoint | Purpose | Standard | Status

| Discovery | OP metadata (`.well-known/openid-configuration`, RFC 8414 metadata) | https://openid.net/specs/openid-connect-discovery-1_0.html[OIDC Discovery 1.0], https://www.rfc-editor.org/rfc/rfc8414[RFC 8414] | Relocated from validation
| JWKS | Signing-key retrieval | https://www.rfc-editor.org/rfc/rfc7517[RFC 7517] | Relocated from validation
| Token | Token issuance / exchange | https://www.rfc-editor.org/rfc/rfc6749[RFC 6749] | Contract + dispatcher (client-facing)
| UserInfo | Claims about the authenticated end-user | https://openid.net/specs/openid-connect-core-1_0.html[OIDC Core] | Contract + dispatcher
| Revocation | Token revocation | https://www.rfc-editor.org/rfc/rfc7009[RFC 7009] | Contract + dispatcher
| Introspection | Token status / metadata | https://www.rfc-editor.org/rfc/rfc7662[RFC 7662] | Contract + dispatcher
| End-session | RP-initiated logout | https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OIDC RP-Initiated Logout 1.0] | Contract + dispatcher
| PAR | Pushed authorization requests | https://www.rfc-editor.org/rfc/rfc9126[RFC 9126] | Contract + dispatcher
|===

Discovery and JWKS are *relocated existing code* (`wellknown`, `jwks.http`); the remaining
six are *transport contracts* the OIDC client engine drives with its own back-channel HTTP.
All eight are exercised by dispatchers in the `generators` test artifact.

== Security controls

=== TLS enforcement (COMMONS-2)

Every outbound request uses TLS 1.2+ with certificate validation, configured centrally via
`cui-http`'s `SecureSSLContextProvider`. Plain-HTTP endpoints are rejected. Mitigates
xref:../threat-model.adoc#T-TLS[T-TLS].

Certificate validation is unconditional in its chain-trust, expiry and algorithm-constraint
components. Hostname matching is the one qualified part: it is ON by default and a deployment may
relax it by explicit opt-in, per the carve-out in
xref:../requirements.adoc#COMMONS-2[COMMONS-2]. Relaxing it narrows hostname matching *only* — an
untrusted or expired certificate is still rejected — and it is reachable from two configuration
surfaces: `sheriff.token.issuers.<name>.jwks.http.verify-hostname` (per-issuer, covering that
issuer's JWKS and well-known fetches) and `sheriff.client.verify-hostname` (client-wide, covering
every back-channel call the client engine makes). Both exist for SAN-mismatched development and
test topologies, never production; see
xref:../../adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008].

=== [[client_back_channel_origin]] Client back-channel origin

The client engine accepts one further, optional transport knob next to `sheriff.client.verify-hostname`:
the *back-channel origin* — `ClientConfiguration.backChannelOrigin`, under Quarkus
`sheriff.client.back-channel-origin`. It serves split-horizon deployments, in which the issuer
identity is a public URL but the application reaches the authorization server only under an internal
address. It changes *where* back-channel calls are sent, never *who* the issuer is
(xref:../../client/requirements.adoc#CLIENT-24[CLIENT-24]).

* *Configuration.* Absent by default; when absent, every endpoint is contacted at its advertised URL.
  A provided value MUST be a bare absolute `http`/`https` origin (`scheme://host[:port]`) with no
  user-info, path, query or fragment; a single trailing `/` is accepted and normalised away. Any
  other value is refused when the configuration is built.
* *Rewrite seam.* The rewrite happens in exactly one place, `BackChannelHttp.validatedHandler`, the
  seam every client back-channel call already passes through. The endpoint clients compute no URL
  past it.
* *Origin comparison.* An advertised endpoint is rewritten when its origin equals the issuer
  origin, compared on lower-cased scheme, lower-cased host and effective port — an absent port is the
  scheme default (`443` for `https`, `80` for `http`), so `https://idp` and `https://idp:443` are the
  same origin. An endpoint on any other origin is contacted unchanged.
* *Path and query preservation.* A rewritten request keeps the advertised raw path and raw query
  verbatim; only scheme, host and port are taken from the back-channel origin.
* *Configuration-only derivation.* Both origins in the comparison — the issuer and the back-channel
  origin — come from configuration. The advertised URL can decide only *whether* it is rewritten,
  never *where to*, so the rewrite adds no SSRF primitive: no request input or discovery data can
  steer a call to a third origin.
* *Order of controls.* The client's egress path validation
  (xref:../../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]) runs on
  the advertised URL before the rewrite; the scheme policy (`allowInsecureHttp`), the per-client trust
  (`sslContext`) and hostname verification are then evaluated against the rewritten target, i.e. the
  host actually contacted. With `https://`, the back-channel host's certificate is therefore
  validated against the back-channel host name.

[cols="1,2", options="header"]
|===
| Retargeted (when the endpoint shares the issuer origin) | Not retargeted

| Discovery (`.well-known/openid-configuration`), token, PAR, userinfo, revocation
| Front-channel URLs sent to the browser (authorization request, end-session); validation-side
  JWKS retrieval, whose URL is configured separately on `HttpJwksLoaderConfig`; introspection and
  device authorization, which the client engine does not implement
|===

The setting leaves the published data and every identity check untouched: the resolved provider
metadata keeps the advertised public endpoint URLs, the discovery-document `issuer` and the token
`iss` are still compared exactly against the configured issuer, and a DPoP proof carries the public
advertised URL as its `htu` claim, not the rewritten one.

=== SSRF defence (COMMONS-3)

Any URL from an IdP-controlled source (`jwks_uri`, discovery, `userinfo`, or any advertised
endpoint) is constrained before it is fetched:

* scheme restricted to HTTPS;
* host subject to an allow-list / egress policy;
* internal / link-local / loopback ranges blocked.

The advertised `issuer` is validated against the configured issuer before advertised URLs
are trusted. Mitigates xref:../threat-model.adoc#T-SSRF[T-SSRF] and
xref:../threat-model.adoc#T-DISCOVERY[T-DISCOVERY].

=== Resilience / DoS bounds (COMMONS-4)

Each fetch applies a connect/read timeout, a response-size limit, and bounded
retry/backoff. No unbounded buffering of response bodies. Mitigates
xref:../threat-model.adoc#T-DOS[T-DOS].

=== Caching (COMMONS-8)

Discovery documents and JWKS are cached with a bounded lifetime; refresh re-applies the TLS,
SSRF and resilience controls above.

== Boundary with validation

Transport delivers *bytes and parsed transport structures* (metadata documents, JWK sets).
Whether a key is *trusted* for a given issuer, and every token-trust decision, stays in the
validation layer. Transport therefore depends only on `cui-http`, `cui-tooling`, and
commons-internal types (the xref:../architecture.adoc#archunit[ArchUnit boundary]).

== [[adversarial_dispatchers]] Test doubles: the dispatcher artifact

The `generators`-classifier test artifact ships MockWebServer dispatchers implementing
`ModuleDispatcherElement` (from `cui-test-mockwebserver-junit5`). Commons extends it with a
dispatcher per new endpoint, each following the existing pattern
(`returnDefault()` / `returnError()` / … + `assertCallsAnswered(int)`) and adding an
*adversarial* mode for the threat catalog:

[cols="1,2,2", options="header"]
|===
| Dispatcher | Default mode | Adversarial mode

| `TokenDispatcher` | Valid grant responses | RFC 6749 §5.2 errors, malformed / oversized bodies
| `UserInfoDispatcher` | Valid userinfo | Tampered claims, `sub` mismatch
| `RevocationDispatcher` | RFC 7009 success (200, empty) | Error responses, oversized body
| `IntrospectionDispatcher` | RFC 7662 `active` responses | Tampered / inconsistent metadata
| `EndSessionDispatcher` | RP-initiated logout redirect | Open-redirect / mismatched `post_logout_redirect_uri`
| `ParDispatcher` | RFC 9126 `request_uri` responses | Error responses, oversized body
| `WellKnownDispatcher` (existing) | Valid metadata | Mismatched `issuer`, attacker `jwks_uri`, slow / oversized
| `JwksResolveDispatcher` (existing) | Valid JWKS | Internal-range redirect, oversized JWKS
|===

The token, userinfo, revocation, introspection, end-session, and PAR doubles are driven
by the client engine; `WellKnownDispatcher` and `JwksResolveDispatcher` back the
validation-side Discovery/JWKS coverage. All are unit-test doubles for MockWebServer
adversarial coverage.
