== Overview

_Realizes xref:../requirements.adoc#COMMONS-1[COMMONS-1]–xref:../requirements.adoc#COMMONS-8[COMMONS-8]
and xref:../requirements.adoc#COMMONS-17[COMMONS-17].
See xref:../threat-model.adoc[Threat Model] and xref:../architecture.adoc[Architecture]._

`commons.transport` owns the validation-side outbound HTTP to an OpenID Provider —
discovery and JWKS — with its TLS enforcement, SSRF egress policy, timeouts, response-size
limits, retry/backoff and discovery / JWKS caching, built on the `cui-http` client. It *moves
bytes* — it never decides whether a token is trustworthy. The client engine builds its *own*
back-channel HTTP (discovery, token, userinfo, revocation, PAR)
(xref:../../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]). It
reuses the commons host-address egress policy type (`EgressPolicy`) as an instance of its own,
configured on `ClientConfiguration`, and adds its path-structure and scheme checks; it has no
retry/backoff and no discovery cache.

== Endpoints

[cols="1,2,2,1", options="header"]
|===
| Endpoint | Purpose | Standard | Status

| Discovery | OP metadata (`.well-known/openid-configuration`, RFC 8414 metadata) | https://openid.net/specs/openid-connect-discovery-1_0.html[OIDC Discovery 1.0], https://www.rfc-editor.org/rfc/rfc8414[RFC 8414] | Implemented (validation side)
| JWKS | Signing-key retrieval | https://www.rfc-editor.org/rfc/rfc7517[RFC 7517] | Implemented (validation side)
| Token | Token issuance / exchange | https://www.rfc-editor.org/rfc/rfc6749[RFC 6749] | Contract + dispatcher (client-facing)
| UserInfo | Claims about the authenticated end-user | https://openid.net/specs/openid-connect-core-1_0.html[OIDC Core] | Contract + dispatcher
| Revocation | Token revocation | https://www.rfc-editor.org/rfc/rfc7009[RFC 7009] | Contract + dispatcher
| Introspection | Token status / metadata | https://www.rfc-editor.org/rfc/rfc7662[RFC 7662] | Contract + dispatcher
| End-session | RP-initiated logout | https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OIDC RP-Initiated Logout 1.0] | Contract + dispatcher
| PAR | Pushed authorization requests | https://www.rfc-editor.org/rfc/rfc9126[RFC 9126] | Contract + dispatcher
|===

Discovery and JWKS are implemented by the validation-side transport code (`wellknown`,
`jwks.http`); the remaining six are *transport contracts*. The client engine drives token,
userinfo, revocation and PAR over its own back channel, builds the end-session redirect on the
front channel, and implements no introspection flow. All eight have dispatchers in the
`generators` test artifact. The dispatchers for the six transport contracts are smoke-tested
directly through a plain `HttpClient` (`EndpointDispatchersTest`), not through the client engine;
only the token, userinfo and PAR dispatchers are additionally driven by the client engine's own
tests. The client's revocation tests use a dispatcher of their own, and the introspection and
end-session dispatchers are never reached by the engine, which issues no introspection request and
no end-session HTTP call.

== Security controls

=== TLS enforcement (COMMONS-2)

Every outbound request uses TLS 1.2+ with certificate validation, configured centrally via
`cui-http`'s `SecureSSLContextProvider`. Plain-HTTP endpoints are rejected by default; each side
admits them only behind its explicit, default-off cleartext opt-in (per issuer on the validation
side, `sheriff.token.issuers.<name>.jwks.http.allow-insecure-http`; client-wide on the client,
`sheriff.client.allow-insecure-http`), intended for local development and tests, never production.
An `https` issuer's discovery document may still advertise only `https` endpoints to the client,
whatever the client opt-in says (xref:#discovery_endpoint_schemes[]).
Mitigates xref:../threat-model.adoc#T-TLS[T-TLS].

Certificate validation is unconditional in its chain-trust, expiry and algorithm-constraint
components. Hostname matching is the one qualified part: it is ON by default and a deployment may
relax it by explicit opt-in, per the carve-out in
xref:../requirements.adoc#COMMONS-2[COMMONS-2]. Relaxing it narrows hostname matching *only* — an
untrusted or expired certificate is still rejected — and it is reachable from two configuration
surfaces: `sheriff.token.issuers.<name>.jwks.http.verify-hostname` (per-issuer, covering that
issuer's JWKS and well-known fetches) and `sheriff.client.verify-hostname` (client-wide, covering
every HTTPS back-channel call the client engine makes; a cleartext `http` target carries no TLS
and so no hostname check). Both exist for SAN-mismatched development and
test topologies, never production; see
xref:../../adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008].

The mechanism is the upstream `cui-http` knob `HttpHandlerBuilder.verifyHostname(boolean)`; this
project implements no trust manager. It is exposed on the three builders that own outbound transport —
`HttpJwksLoaderConfigBuilder` and `WellKnownConfigBuilder` (validation) and `ClientConfiguration`
(client) — and defaults to `true` on each. The validation side forwards it on both the direct-JWKS and
the well-known branch; the client forwards it at the single `BackChannelHttp.validatedHandler()` seam,
so every endpoint client inherits one posture. The relaxation applies only to the context derived from
the JVM default trust store, so it cannot be combined with a caller-supplied `SSLContext` (refused at
build time on the client, xref:../../client/requirements.adoc#CLIENT-23[CLIENT-23]); a test that needs
both relaxed matching and private trust material steers the default trust store through
`javax.net.ssl.trustStore` and restores it afterwards. The knob needs `cui-http` 2.2 or newer, inherited
from `cui-java-bom` with no reactor override. No build-level version guard exists:
`HttpHandlerVerifyHostnameContractTest` compiles only against a `cui-http` exposing the knob and pins
its default, its builder round trip and the mutual exclusion, and each module carries a control proving
an untrusted issuer is still refused with the knob off.

=== [[discovery_endpoint_schemes]] Advertised endpoint schemes of an `https` issuer

When the client's configured issuer is `https`, every endpoint the client's provider metadata models
that the discovery document advertises must be `https` too; a non-`https` value fails discovery, and
`allowInsecureHttp` does not relax this, because that switch exists for the operator's own topology (an
`http` issuer, or an `http` back-channel origin), not for a downgrade chosen by the document.

* The checked set is the endpoint map built by `DiscoveryResolver.validateEndpointSchemes`; an
  advertised field outside it is neither read nor checked, and a field the client starts to call must
  join it.
* An absent endpoint is fine; a present value that is not an `https` URL, including a blank one, is a
  violation.
* The refusal names the endpoint label only; the advertised URL is untrusted content and is not echoed.
* The check does not apply to an `http` issuer admitted by `allowInsecureHttp`.

The guarantee is about the advertised scheme, not the connection made: with `allowInsecureHttp` and an
`http` back-channel origin, a same-origin `https` endpoint is retargeted and contacted over `http`, by the
operator's explicit choice (xref:#client_back_channel_origin[]).

=== [[client_back_channel_origin]] Client back-channel origin

The client engine accepts one further, optional transport knob next to `sheriff.client.verify-hostname`:
the *back-channel origin* — `ClientConfiguration.backChannelOrigin`, under Quarkus
`sheriff.client.back-channel-origin`. It serves split-horizon deployments, in which the issuer
identity is a public URL but the application reaches the authorization server only under an internal
address. It changes *where* back-channel calls are sent, never *who* the issuer is
(xref:../../client/requirements.adoc#CLIENT-24[CLIENT-24]).

* *Configuration.* Absent by default; when absent, every endpoint is contacted at its advertised URL.
  A provided value MUST be a bare absolute `http`/`https` origin (`scheme://host[:port]`) with no
  user-info, path, query or fragment; a single trailing `/` is accepted and normalised away. Any
  other value is refused when the configuration is built.
* *Rewrite seam.* The rewrite happens in exactly one place, `BackChannelHttp.validatedHandler`, the
  seam every client back-channel call already passes through. The endpoint clients compute no URL
  past it.
* *Origin comparison.* An advertised endpoint is rewritten when its origin equals the issuer
  origin, compared on lower-cased scheme, lower-cased host and effective port — an absent port is the
  scheme default (`443` for `https`, `80` for `http`), so `https://idp` and `https://idp:443` are the
  same origin. An endpoint on any other origin is contacted unchanged.
* *Path and query preservation.* A rewritten request keeps the advertised raw path and raw query
  verbatim; only scheme, host and port are taken from the back-channel origin.
* *Configuration-only derivation.* Both origins in the comparison — the issuer and the back-channel
  origin — come from configuration. The advertised URL can decide only *whether* it is rewritten,
  never *where to*, so the rewrite adds no SSRF primitive: no request input or discovery data can
  steer a call to a third origin.
* *Order of controls.* The client's egress path validation
  (xref:../../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]) runs on
  the advertised URL before the rewrite; the scheme policy (`allowInsecureHttp`), the host-address
  egress policy, the per-client trust (`sslContext`) and hostname verification are then evaluated
  against the rewritten target, i.e. the host actually contacted — so an internal back-channel
  origin must be listed in `allowedEgressHosts`. With `https://`, the back-channel host's certificate is therefore
  validated against the back-channel host name. The issuer-scheme check at discovery is separate
  and still applies to the configured issuer: an `http` issuer requires `allowInsecureHttp`
  whatever the scheme of the back-channel origin.

[cols="1,2", options="header"]
|===
| Retargeted (when the endpoint shares the issuer origin) | Not retargeted

| Discovery (`.well-known/openid-configuration`), token, PAR, userinfo, revocation
| Front-channel URLs sent to the browser (authorization request, end-session); validation-side
  JWKS retrieval, whose URL is configured separately on `HttpJwksLoaderConfig`; introspection and
  device authorization, which the client engine does not implement
|===

The setting leaves the published data and every identity check untouched: the resolved provider
metadata keeps the advertised public endpoint URLs, the discovery-document `issuer` and the token
`iss` are still compared exactly against the configured issuer, so the issuer identity stays public.

A DPoP proof is the one transport artefact that follows the contacted URL: its `htu` claim is the
target URI of the request it travels with (RFC 9449 §4.2), so on a rewritten call it names the
rewritten target — the back-channel origin with the advertised path — not the advertised public URL.
`BackChannelHttp.validatedHandler` returns a handler whose URI is that target, and the token and
userinfo clients sign it as `htu`
(xref:../../adr/0015-DPoP_htu_names_the_back-channel_URL_actually_contacted.adoc[ADR-0015]).

=== SSRF defence (COMMONS-3)

Any URL from an IdP-controlled source (`jwks_uri`, discovery, `userinfo`, or any advertised
endpoint) is constrained before it is fetched:

* scheme restricted to HTTPS, unless the cleartext opt-in of COMMONS-2 is set;
* host subject to a host-address egress policy (`EgressPolicy`) that refuses loopback,
  link-local (including the `169.254.0.0/16` cloud-metadata range), site-local, IPv6 unique-local,
  carrier-grade NAT, wildcard, broadcast and multicast addresses by default.

Two independent policy instances apply it. The validation side applies one to the well-known
discovery and JWKS fetches (`HttpWellKnownResolver`, `HttpJwksLoader`), configured per issuer. The
client engine applies its own, configured on `ClientConfiguration`, to every discovery and
back-channel call (discovery, token, PAR, userinfo, revocation), on the URL actually contacted —
after the back-channel origin rewrite — and keeps its path-structure and scheme checks besides.
The secure default can refuse an endpoint a deployment configured or an issuer advertised on an
internal address. On the client the relaxations are explicit and named:
`allowLoopbackEgress` (`sheriff.client.allow-loopback-egress`) lifts the loopback refusal only, and
`allowedEgressHosts` (`sheriff.client.allowed-egress-hosts`) lists hosts that bypass the
address-range check entirely, which a split-horizon deployment uses for its back-channel origin. The
policy resolves the host immediately before the fetch; a DNS answer that changes before the HTTP
client connects is not seen.

The advertised `issuer` is validated against the configured issuer before advertised URLs
are trusted. Mitigates xref:../threat-model.adoc#T-SSRF[T-SSRF] and
xref:../threat-model.adoc#T-DISCOVERY[T-DISCOVERY].

==== [[egress_host_validator]] Allow-list entries: `EgressHostValidator`

An allow-list entry names a host exactly as `URI.getHost()` reports it, and one public rule,
`commons.transport.EgressHostValidator`, decides whether an entry is such a bare host:

* `refusal(String)` returns empty for an admitted entry and otherwise one fixed refusal text, which
  never contains the entry;
* `requireBareHost(String)` throws `IllegalArgumentException` carrying that text, and otherwise
  returns the canonical form the policy matches against — lower-cased, a bare IPv6 literal wrapped in
  brackets, because `URI.getHost()` reports an IPv6 host bracketed.

[cols="1,2", options="header"]
|===
| Admitted | Refused

| An ASCII host name of dot-separated letter-digit-hyphen labels (each 1 to 63 characters, not
  starting or ending with `-`, at most 253 in total) whose final label, when it has more than one, starts with a letter, with
  at most one terminal root dot, which the canonical form keeps; a dotted IPv4 literal without a
  terminal dot; a bare IPv6 literal, validated without DNS; a bracketed IPv6 literal
| `null`; blank; a port in any form (`keycloak:8080`, a bracketed IPv6 literal followed by a port,
  any other single-colon form);
  whitespace; control characters; non-ASCII characters; the URL syntax characters `/`, `@`, `?`, `#`
  and `%`; an invalid IPv6 literal or host name
|===

Every builder that takes an entry applies the rule at its setter and fails closed: a refused entry is
never stored and never silently ignored.

* `EgressPolicy.EgressPolicyBuilder.allowedHost` stores `requireBareHost(entry)`;
* `WellKnownConfig.WellKnownConfigBuilder.allowedEgressHost` and
  `HttpJwksLoaderConfig.HttpJwksLoaderConfigBuilder.allowedEgressHost` refuse at the setter rather than
  in `build()`, so the fixed text is the first-class message and the entry appears nowhere in the
  cause chain;
* the client's `ClientConfiguration` refuses each `allowedEgressHosts` entry through `refusal`, naming
  the entry's zero-based index but never the entry, and reports, compares and prints its list in the
  canonical form;
* under Quarkus, `IssuerConfigResolver` turns a refused element of
  `sheriff.token.issuers.<name>.jwks.http.allowed-egress-hosts` into an `IllegalStateException` naming
  the property key and the bare-host rule, with the fixed text chained as its cause; on this issuer path
  blank CSV elements are dropped and the whitespace around an element is trimmed before the rule runs,
  so `keycloak, dex` admits both hosts;
* the client path does not trim: an element of `sheriff.client.allowed-egress-hosts` that carries a
  port or surrounding whitespace fails the client mapping, so `keycloak, dex` fails there, while the
  configuration reader drops empty CSV elements before the rule runs.

`EgressPolicy.check` matches a listed host case-insensitively; it bypasses the address-range check,
and a bare IPv6 entry, stored bracketed, matches the bracketed host of an IPv6 URL.

=== [[resilience_bounds]] Resilience / DoS bounds (COMMONS-4)

Each fetch applies a connect/read timeout, a response-size limit, and bounded
retry/backoff. No unbounded buffering of response bodies.

[cols="1,2,2", options="header"]
|===
| Bound | What sets it (cui-http 3.2) | Phase it covers

| Connect timeout
| `HttpHandler` builds its `HttpClient` with `HttpClient.Builder.connectTimeout`
| Establishing the connection

| Read timeout
| `HttpHandler.requestBuilder()` sets it as the request timeout, `HttpRequest.Builder.timeout`; the
  validation side's `ETagAwareHttpAdapter` and the client's back-channel calls build every request through
  it
| The wait until the response headers arrive; the body read too on some JDKs (observed on the
  client back-channel path: not on JDK 21 and 25, yes on JDK 27)

| Response-size limit
| `BoundedBodyHandler`: `ParserConfig.maxHttpResponseSize` for the validation-side discovery and JWKS
  reads, `ClientConfiguration.discoveryDocumentMaxSize` for the client's discovery, the JWT payload ceiling
  `ParserConfig.maxPayloadSize` for the client's token, PAR, userinfo and revocation calls
| The body read, in size, on every JDK

| Retry/backoff
| `ResilientHttpAdapter` on the validation side, with the delays of its `RetryConfig`; it sets no
  timeout
| Between attempts
|===

`HttpHandler` sets no other timeout. Whether the request timeout also bounds the body read that follows
the headers depends on the JDK: on the client back-channel path it was observed not to on JDK 21 and 25, so
a host that sends the headers and then stalls the body keeps the calling thread waiting; on JDK 27 it was
observed to, so such a call ends with the request-timeout failure or with the JDK's own failure for the body
it cut short. The validation-side discovery and JWKS
reads use the same JDK client and the same cui-http request timeout, but were not run themselves. The
transport relies on the size bound of the body read, which applies on every JDK, not on a time bound. Mitigates xref:../threat-model.adoc#T-DOS[T-DOS] within that
limit.

=== [[bounded_response_body]] Bounded response body (COMMONS-17)

The response-size limit is enforced by one public handler, `commons.transport.BoundedBodyHandler`,
which every bounded read uses: the validation-side discovery and JWKS converters
(`WellKnownConfigurationConverter`, `JwksHttpContentConverter`) and the client's back-channel reads
(`BackChannelHttp.bodyHandler()`). It counts bytes while the body streams and acts the moment the running
total would exceed the ceiling, so the full body is never materialised first.

[cols="1,2", options="header"]
|===
| Aspect | Rule

| Factory methods
| `ofString(Charset, long maxBytes, String boundOrigin)` reads under the fail policy and decodes with the
  given charset; it is the form all three callers use. `ofBytes(long maxBytes, OverLimitPolicy, String
  boundOrigin)` returns an immutable `BoundedBodyHandler.BoundedBody` (`bytes()` returns a copy, `truncated()`,
  `asString(Charset)`; its `toString` shows the length, never the content).

| Ceiling
| Inclusive; a body strictly larger is over the limit. Accepted from 0 to `MAX_CEILING`
  (`Integer.MAX_VALUE - 8`, the largest array the result can hold); a negative or larger ceiling is refused
  with `IllegalArgumentException` when the handler is created. `charset`, `policy` and `boundOrigin` must
  not be `null`.

| `FAIL` policy — pre-check
| A response that advertises a `Content-Length` above the ceiling is refused before a byte of its body is
  read: the subscription is cancelled in `onSubscribe`. A `Content-Length` that is not a valid number
  cancels the subscription the same way, and the read fails with an `IOException` carrying a fixed
  message that does not echo the header value.

| `FAIL` policy — streaming
| A body that crosses the ceiling while streaming — one that lied about its `Content-Length` or advertised
  none — cancels the subscription, releases the buffered bytes and fails the read.

| `TRUNCATE` policy
| The advertised `Content-Length` is not checked. The body is read up to the ceiling, the subscription is
  cancelled at the first crossing, and the result holds exactly the first `maxBytes` bytes with
  `truncated()` `true`. A body of exactly the ceiling is not truncated.

| Memory bound
| While the body streams, both policies keep the bytes read so far in one array that grows by doubling,
  and ignore every chunk that arrives after the first crossing. The array never exceeds the ceiling and is
  at most twice the bytes received, or the first allocation (1024 bytes, or the ceiling when that is
  smaller) when that is larger. During a growth step the
  old and the new array are both live, so the memory held while streaming peaks below twice the ceiling
  plus the buffers of the delivery in flight; the object count grows with the logarithm of the body size. Completion is not covered by that
  bound: the held bytes are assembled into the result and, for the string variant, decoded into a string
  before they are released, so the transient peak there is a small constant multiple of the ceiling (see
  xref:../requirements.adoc#COMMONS-17[COMMONS-17]).

| Failure message
| The read completes exceptionally with an `IOException` reading
  `Response body exceeds maximum allowed size of N bytes (boundOrigin)`. The `boundOrigin` names the setting
  that produced the ceiling and whether it is settable, for example
  `ParserConfig.maxHttpResponseSize` on the validation side and the client's fixed `ParserConfig.maxPayloadSize`
  bound, so a reader of the failure can tell a tunable bound from a fixed one.

| Logging and threading
| The handler logs nothing. It is immutable and may be shared across requests; each response gets a fresh
  subscriber.
|===

See
xref:../../adr/0031-Bearer_extraction_scope_challenge_sanitiser_escape_and_bounded_body_reads_are_public_commons_helpers.adoc[ADR-0031]
for the decision that made this the one handler of both sides.

==== [[client_exchange_failures]] Malformed framing and exchange failures on the client back channel

The handler's fixed message for a non-numeric `Content-Length` is its own guarantee; whether the
surrounding HTTP client reaches the handler is the client's behaviour. The JDK HTTP/1.1 client parses
`Content-Length` itself, after the handler returned and, for a `204` or other no-body reply, before any
body handler runs. It refuses a value that is not a number with the parser's `NumberFormatException`,
which carries the raw header value: the `HttpClient.sendAsync` future completes with that exception,
`HttpClient.send` wraps it in an `IllegalArgumentException`, and from JDK 27 on it sits under a
`ProtocolException` in the cause chain (the JDK 27 form rests on the JDK 27 leg of the CI build). The
handler has no hook before that parse, so the mapping belongs to the caller that sends.

The client's discovery, PAR, userinfo and revocation clients send through `BackChannelHttp.send`, the
token endpoint client through its own send; both wait on `HttpClient.sendAsync` through
`BackChannelHttp.exchange`:

* *Malformed framing.* `BackChannelHttp.isMalformedFraming` recognises the refusal in each form (the
  `NumberFormatException` itself, an `IllegalArgumentException` with one in its cause chain, a
  `ProtocolException` caused by one anywhere in the chain). The call fails with a `TransportException`
  whose message is the endpoint's failure context and the fixed text `BackChannelHttp.MALFORMED_RESPONSE`,
  neither chaining the JDK's exception nor echoing its message. The token endpoint reports it as its
  post-redemption failure when its body handler observed a success status, and as a pre-redemption
  failure when it never saw the status, as for a `204`.
* *Cause unwrapping.* Each failure is decided on its cause, unwrapped from the `ExecutionException` of
  the wait and any nested `CompletionException` or `ExecutionException`, for at most `MAX_CAUSE_DEPTH`
  levels, so a cyclic or over-deep wrapper chain cannot loop.
* *Every other failure* reaches the caller as an `IOException` or an `Error`: an `IOException` or `Error`
  cause is rethrown as reported; a cancelled wait, and a future failed with a wrapped
  `CancellationException`, is an `IOException` with the fixed text "the HTTP exchange was cancelled";
  every other cause, checked or runtime, an `IllegalArgumentException` of another cause and a wrapper
  left at the unwrap bound included, is an `IOException` with the fixed text "the HTTP exchange failed"
  and no chained cause, because a response-side failure message can carry remote content. The
  wrapped-cancellation, nested-wrapper, checked-cause and runtime-cause mappings are defensive: no JDK
  path producing them is known. Each client classifies them through its `IOException` handling, and the
  token endpoint reports one seen after a recorded success status as its post-redemption failure.
* *Request-side faults.* An `IllegalArgumentException` thrown synchronously by `HttpClient.sendAsync`,
  for a request the client refuses before sending, is a request-side fault and reaches the caller as
  thrown.

The wait has no bound of its own; the request timeout and the size ceiling of
xref:#resilience_bounds[] bound it. The validation-side discovery and JWKS reads hand the handler to
cui-http, whose adapter performs the send, so this repository has no send call there to map. A caller
therefore treats the message of any exception that comes out of an HTTP exchange as remote content and
sanitises it before logging.

=== Caching (COMMONS-8)

Discovery documents and JWKS are cached with a bounded lifetime; refresh re-applies the TLS,
SSRF and resilience controls above.

== Boundary with validation

Transport delivers *bytes and parsed transport structures* (metadata documents, JWK sets).
Whether a key is *trusted* for a given issuer, and every token-trust decision, stays in the
validation layer. Transport therefore depends only on `cui-http`, `cui-tooling`, and
commons-internal types (the xref:../architecture.adoc#archunit[ArchUnit boundary]).

== [[adversarial_dispatchers]] Test doubles: the dispatcher artifact

The `generators`-classifier test artifact ships MockWebServer dispatchers implementing
`ModuleDispatcherElement` (from `cui-test-mockwebserver-junit5`). Commons extends it with a
dispatcher per new endpoint, each following the existing pattern
(`returnDefault()` / `returnError()` / … + `assertCallsAnswered(int)`) and adding an
*adversarial* mode for the threat catalog:

[cols="1,2,2", options="header"]
|===
| Dispatcher | Default mode | Adversarial mode

| `TokenDispatcher` | Valid grant responses | RFC 6749 §5.2 errors, malformed / oversized bodies
| `UserInfoDispatcher` | Valid userinfo | Tampered claims, `sub` mismatch
| `RevocationDispatcher` | RFC 7009 success (200, empty) | Error responses, oversized body
| `IntrospectionDispatcher` | RFC 7662 `active` responses | Tampered / inconsistent metadata
| `EndSessionDispatcher` | RP-initiated logout redirect | Open-redirect / mismatched `post_logout_redirect_uri`
| `ParDispatcher` | RFC 9126 `request_uri` responses | Error responses, oversized body
| `WellKnownDispatcher` (existing) | Valid metadata | Mismatched `issuer`, attacker `jwks_uri`, slow / oversized
| `JwksResolveDispatcher` (existing) | Valid JWKS | Internal-range redirect, oversized JWKS
|===

The token, userinfo and PAR doubles are driven by the client engine's tests; the revocation,
introspection and end-session doubles are exercised only by the direct dispatcher smoke tests
(`EndpointDispatchersTest`). The client's revocation tests declare a dispatcher of their own, and
the engine reaches neither the introspection nor the end-session endpoint.
`WellKnownDispatcher` and `JwksResolveDispatcher` back the validation-side Discovery/JWKS
coverage. All are unit-test doubles for MockWebServer adversarial coverage.
