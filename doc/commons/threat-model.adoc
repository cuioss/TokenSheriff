== Overview

_See xref:requirements.adoc[Commons Requirements] and xref:architecture.adoc[Architecture]._

Threat model for the `commons` base layer. Commons is where the system *touches the
network* (outbound IdP HTTP) and where it *renders failures to callers* (RFC 9457 at the
edge), so its threats are transport threats — SSRF, TLS downgrade, response-DoS — and
information-disclosure through error responses. Token-*trust* threats (forged signatures,
claim tampering, replay) belong to the xref:../validation/threat-model.adoc[validation
threat model], not here.

Each entry cites a source, a mitigation, and the covering `COMMONS-N` requirement.

== System context

The commons layer:

* Issues the validation-side outbound HTTP to OpenID Providers (discovery, JWKS). The
  client engine issues its *own* back-channel HTTP
  (xref:../client/architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]) and
  reuses the commons host-address egress policy type as an instance of its own.
* Follows URLs that are partly *IdP-controlled* (advertised via discovery).
* Normalizes inbound IdP error responses and raises typed exceptions.
* Is rendered to end-callers by the HTTP edges as `application/problem+json`.

The relocated `wellknown` and `jwks.http` code is *in scope* — its egress and TLS paths
were audited to the requirements below during the move into commons.

== Threat catalog

[cols="1,2,3,1,1", options="header"]
|===
| ID | Threat | Mitigation | Source | Requirement

| [[T-SSRF]]T-SSRF
| *SSRF via `jwks_uri` / discovery / userinfo / any IdP-advertised URL.* An attacker who
  controls or spoofs IdP metadata points a URL at an internal service (cloud metadata,
  link-local, loopback) to make the server fetch it.
| HTTPS-only scheme restriction (unless the cleartext opt-in of COMMONS-2 is set) and a
  host-address egress policy (`EgressPolicy`) that refuses loopback, link-local (cloud
  metadata), site-local, unique-local, carrier-grade NAT, wildcard, broadcast and multicast
  addresses by default. Two independent instances apply it: the validation side's, on the
  well-known discovery and JWKS fetches (per issuer), and the client engine's own, on every
  discovery and back-channel call (discovery, token, PAR, userinfo, revocation), checked on the
  URL actually contacted after the back-channel origin rewrite. The client back channel also
  keeps its path-structure and scheme checks. Relaxations are explicit only (see the residual
  risks below).
| https://owasp.org/www-community/attacks/Server_Side_Request_Forgery[OWASP SSRF], https://github.com/advisories/GHSA-7vw6-5q2f-7w5r[CVE-2026-1180]
| xref:requirements.adoc#COMMONS-3[COMMONS-3]

| [[T-DISCOVERY]]T-DISCOVERY
| *Malicious endpoints advertised via discovery.* A tampered `.well-known` document
  advertises attacker-controlled `jwks_uri` / `token_endpoint` / `userinfo_endpoint`.
| Validate the advertised `issuer` against the configured issuer; treat every advertised
  URL as untrusted input and subject it to T-SSRF controls before use.
| https://www.rfc-editor.org/rfc/rfc8414[RFC 8414 §3.3], https://openid.net/specs/openid-connect-discovery-1_0.html[OIDC Discovery 1.0 §4.3]
| xref:requirements.adoc#COMMONS-5[COMMONS-5]

| [[T-TLS]]T-TLS
| *TLS downgrade / MITM on any IdP fetch.* Downgrade to plaintext or a forged certificate
  lets an attacker substitute metadata, keys, or token-endpoint responses.
| Enforce TLS 1.2+ with certificate validation on every outbound request; reject plain
  HTTP endpoints by default — cleartext is admitted only behind an explicit, default-off
  opt-in (`allow-insecure-http`, per issuer on the validation side, client-wide on the
  client), and an `https` issuer's discovery document may advertise only `https` endpoints to
  the client whatever that opt-in says. TLS is configured centrally, not per-caller. Chain
  trust, expiry and algorithm constraints are unconditional; *hostname matching is default-ON
  but relaxable by explicit per-configuration opt-in* (see the residual risks below).
| https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §2.6], https://www.rfc-editor.org/rfc/rfc8414[RFC 8414 §2]
| xref:requirements.adoc#COMMONS-2[COMMONS-2]

| [[T-DOS]]T-DOS
| *DoS via large / slow metadata, JWKS or userinfo responses.* A hostile or degraded IdP
  returns a multi-gigabyte body or trickles bytes to exhaust memory / threads.
| Connect/read timeouts, response-size limits, and bounded retry/backoff on every fetch;
  no unbounded buffering.
| https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4], https://www.rfc-editor.org/rfc/rfc7230[RFC 7230]
| xref:requirements.adoc#COMMONS-4[COMMONS-4]

| [[T-LEAK]]T-LEAK
| *Internal-detail leakage in error responses.* An error surface returns a stack trace,
  internal identifiers, upstream URLs, or credential fragments to the caller.
| Library code raises typed exceptions only (no HTTP documents); edges render RFC 9457
  problem documents carrying a safe `type` / `title` / `detail`, never stack traces or
  internal identifiers. Inbound IdP errors are normalized, not passed through verbatim.
| https://www.rfc-editor.org/rfc/rfc9457#section-3[RFC 9457 §3], https://www.rfc-editor.org/rfc/rfc9700[RFC 9700 §4]
| xref:requirements.adoc#COMMONS-9[COMMONS-9], xref:requirements.adoc#COMMONS-10[COMMONS-10], xref:requirements.adoc#COMMONS-11[COMMONS-11], xref:requirements.adoc#COMMONS-12[COMMONS-12]
|===

[#_residual_risks]
=== Residual risks

The transport controls above leave these residual exposures, recorded here rather than implied away:

* *A deployment that opts in to cleartext gives up T-TLS for its `http://` endpoints.* With
  `allow-insecure-http` set (per issuer on the validation side, client-wide on the client), an
  `http://` endpoint is fetched without TLS, so its discovery document, keys or token responses
  are open to interception and tampering. The opt-in is for local development and tests, never
  production.
* *An egress relaxation narrows T-SSRF.* On the client, `sheriff.client.allow-loopback-egress`
  lifts the loopback refusal, and a host listed in `sheriff.client.allowed-egress-hosts` bypasses
  the address-range check wherever it appears, including in an advertised endpoint; the validation
  side has its own per-issuer settings. The policy also resolves the host immediately before the
  fetch, and the HTTP client resolves it again when it connects, so a DNS answer that changes in
  between (DNS rebinding) is not seen.

* *A deployment that opts out of hostname verification accepts a narrowed T-TLS mitigation.*
  Hostname matching is the one qualified part of certificate validation under
  xref:requirements.adoc#COMMONS-2[COMMONS-2]: it is ON by default and relaxable by explicit
  opt-in, via `sheriff.token.issuers.<name>.jwks.http.verify-hostname` (per-issuer) or
  `sheriff.client.verify-hostname` (client-wide). What remains enforced is substantial — chain
  trust, expiry and algorithm constraints all still apply, so an untrusted or expired certificate
  is still rejected — but the mitigation is narrowed: with hostname matching off there is no
  guarantee that the certificate presented belongs to the host actually contacted, so an attacker
  holding any certificate this deployment trusts can impersonate the IdP. The knob exists for
  development and test topologies serving SAN-mismatched certificates; the risk falls entirely on
  the deployment that opts in, which is why the default is ON. See
  xref:../adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008].

The client engine's optional back-channel origin (`sheriff.client.back-channel-origin`, see
xref:specification/transport.adoc#client_back_channel_origin[Transport spec]) adds no further
residual exposure to T-TLS, T-SSRF or T-DISCOVERY. It is operator-configured only, and an advertised
endpoint is retargeted to it only when the endpoint shares the configured issuer's origin, so
advertised discovery data cannot steer a call to a third origin. The issuer identity and the
`issuer` / `iss` checks stay intact, and `sheriff.client.verify-hostname` together with the
configured trust then validates the certificate of the back-channel host — the host actually
contacted. The validation-side JWKS URL is configured separately and is not rewritten.

== Adversarial test coverage

Each transport threat is exercised by the `generators` test artifact's dispatchers in an
*adversarial* mode (see xref:specification/transport.adoc#adversarial_dispatchers[Transport
spec]):

[cols="1,3", options="header"]
|===
| Threat | Adversarial dispatcher behaviour

| T-SSRF | Discovery / JWKS dispatchers advertise redirect or internal-range URLs on the validation side; on the client, `BackChannelEgressPolicyTest` maps the mock server onto a disallowed address for each endpoint kind (discovery, token, PAR, userinfo, revocation) and proves it is never contacted.
| T-DISCOVERY | Discovery dispatcher advertises a mismatched `issuer` / attacker `jwks_uri`.
| T-TLS | Endpoint offered over plain HTTP / with a downgrade is rejected by default, and the client refuses a non-`https` endpoint advertised by an `https` issuer. Coverage is for the default posture (cleartext not allowed, hostname verification ON); the relaxed postures are not exercised adversarially.
| T-DOS | Dispatchers emit oversized / slow-drip bodies.
| T-LEAK | Edge tests assert problem+json carries no stack trace / internal identifier.
|===

== Out of scope (delegated)

Token-trust threats — forged signatures, `alg` confusion, claim tampering, expiry/replay —
are covered by the xref:../validation/threat-model.adoc[validation threat model]. Commons
delivers bytes and raises typed errors; it never decides whether a token is trustworthy.
