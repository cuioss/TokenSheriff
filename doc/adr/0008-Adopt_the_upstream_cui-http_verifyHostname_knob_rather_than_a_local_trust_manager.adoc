== Status

Accepted

== Context

Both library modules make outbound HTTPS calls — JWKS and discovery on the validation side, the
back-channel endpoints on the client. Local development, CI and container networks regularly reach a
service under a name its certificate was not issued for: chain trust can succeed while hostname
matching fails. Without a narrow way to relax only the name check, operators reach for much broader
remedies (trust-all, process-global switches) that look like a production misconfiguration at review
time. In the JDK client a hostname relaxation means trust managers that validate the chain but skip
the name — security-sensitive code whose failure mode, silently dropping chain validation, is invisible
in a diff. The question is whether this project implements that machinery or delegates it.

== Decision

Outbound hostname verification is a configurable, default-ON knob delegated entirely to the upstream
`cui-http` transport, `HttpHandlerBuilder.verifyHostname(boolean)`. This project contributes
configuration surface and validation, never a trust manager. Disabling the knob relaxes hostname
matching only; chain trust, expiry and algorithm constraints stay enforced, and each module proves it
executably. The upstream delegating-trust-manager design is `cui-http` ADR-0007; it is cited, not
restated.

Rejected: a local `X509ExtendedTrustManager` (duplicates and drifts from upstream security code to
avoid a dependency bump); a trust-all `SSLContext` (drops chain validation too); the JVM-wide hostname
property (process-wide blast radius, invisible to configuration review).

== Consequences

* Trust-manager code is reviewed once, upstream, for every consumer; the relaxation is narrow, per
  configuration, and visible at the call site as `verifyHostname(false)`. Default `true` means no
  migration.
* Relaxed hostname matching cannot be combined with a caller-supplied `SSLContext`; a deployment or
  test needing both steers the process-global JVM default trust store instead.
* The project's TLS posture is coupled to an upstream API; `HttpHandlerVerifyHostnameContractTest`
  turns an upstream semantic change into a named failure, so no build-level version guard exists.

The configuration surface, the forwarding seams, the mutual exclusion and the dependency floor are
specified in
xref:../commons/specification/transport.adoc[Transport specification § TLS enforcement].
