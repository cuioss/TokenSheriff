== Status

Accepted

== Context

`ClientConfiguration.backChannelOrigin` sends every back-channel call whose advertised endpoint shares
the issuer's origin to a different origin, while identity (issuer checks, published metadata,
front-channel URLs) stays on the public values. A DPoP proof's `htu` names the URI of the request it is
attached to, and the authorization server refuses a mismatch with `invalid_dpop_proof`. On a rewritten
call `htu` could name the advertised URL or the dialled one, and at most one can match what the server
compares against.

Evidence, gathered against Keycloak 26.8.1 and 26.5.7 with a static `KC_HOSTNAME` and no realm
`frontendUrl`: discovery advertises the static hostname whichever origin is dialled, but the token
endpoint compares `htu` with the URL it was called on — a proof naming the advertised URL on a
rewritten call is refused (`DPoP HTTP URL mismatch`, on the code exchange and on refresh), a proof
naming the dialled URL succeeds, and the advertised URL succeeds only when a `Host` header names the
public authority. RFC 9449 §4.2 defines `htu` as the target URI of the request. The JDK `HttpClient`
lets a caller set `Host` only through the process-wide `jdk.httpclient.allowRestrictedHeaders`
property.

== Decision

A DPoP proof's `htu` names the URL the client actually contacts. Without a mapping that is the
advertised endpoint; when `backChannelOrigin` rewrote the call it is the back-channel origin with the
advertised path. Both DPoP-constrained callers — the token endpoint client (code exchange, client
credentials, refresh, including the `use_dpop_nonce` retry) and the userinfo client — take `htu` from the
URI of the validated handler they send through, so proof and request cannot name different targets.
The rule is unconditional: no `Host` header, no setting. Everything else about `backChannelOrigin` is
unchanged; TLS SNI, hostname verification, the transport policy of
xref:0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]
and the proof all refer to the host dialled.

Rejected: keeping the advertised URL and sending a `Host` header (needs a process-global restricted-header
switch and splits one request across two authorities); a selecting setting (configuration and test
matrix for a branch no known deployment needs); the previous advertised-URL behaviour (fails every
DPoP-constrained request through a mapping against Keycloak and contradicts RFC 9449).

== Consequences

* DPoP-constrained token and userinfo requests work through a mapped back channel; a proof captured on
  the back channel is not replayable as-is against the public endpoint; unmapped deployments see no
  change.
* Breaking change to the documented `backChannelOrigin` contract: the 0.9.7 Javadoc listed `htu` among
  the values that keep the public URL. `htu` is the one identity-adjacent value that follows the
  contacted URL, and the documentation states that exception.
* A server that compares `htu` with its configured public hostname would refuse mapped requests, with
  no switch; an opt-in would need a successor ADR. `DpopBackChannelOriginSpecIT` against the pinned
  Keycloak turns a behaviour change into a named failure.

The rewrite seam and the `htu` derivation are specified in
xref:../commons/specification/transport.adoc#client_back_channel_origin[Transport specification § Client back-channel origin].
