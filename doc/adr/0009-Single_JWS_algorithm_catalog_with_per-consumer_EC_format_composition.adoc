== Status

Accepted

== Context

A JWS algorithm is a cluster of facts — key type, digest, JCA signature name, PSS parameters — that
every signing, verifying or accepting component needs part of. Stated at each site, the copies are not
checked against each other: a mistyped digest selects a different real algorithm and only an
end-to-end test of that algorithm notices. Because these facts govern signature verification and DPoP
proof generation, a silent disagreement is a security defect. One of the facts is not single-valued:
the EC JCA name depends on the wire format (JOSE uses `R || S`, `java.security.Signature` defaults to
DER).

== Decision

Signing-algorithm facts are defined once, in the `JwsAlgorithm` catalog of the validation module, and
every consumer *that signs or verifies* derives from it, across the module boundary. Two deliberate
exceptions: for EC the catalog supplies no JCA name and each consumer composes the name its wire
format needs; and JWK *admission* — which key material a JWKS may offer — keeps its own list, so adding
a signing algorithm never silently widens accepted remote key material. Test inputs are derived from
the catalog only where that widens coverage, and a verification oracle never derives its expectation
from it.

Rejected: per-site copies (silent disagreement); one EC JCA name (silently changes one consumer); deriving
every test input from the catalog (drops negative cases and makes oracles tautological).

== Consequences

* One edit updates every signing consumer, and the remaining per-consumer decisions (EC format, JWK
  admission) are conspicuous.
* A wrong catalog entry now reaches the whole signing path at once, so each entry's values are pinned
  explicitly.
* The EC carve-out invites a well-meant "completion"; both composing call sites state the reason.

The catalog's shape, the EC composition and the test rules are maintained in
xref:../validation/architecture.adoc#jws-algorithm-catalog[Validation Architecture § JWS Algorithm Catalog].
