= ADR-0007: The refresh path binds identity against a retained session subject, not a re-parsed stored ID token
:toc: left
:toclevels: 2
:sectnums:

// adr-metadata
// summary: Session identity is bound by comparing the refreshed principal against a subject retained on the stored session record, checked inside the atomic store transform, rather than by re-parsing a stored ID token on every refresh
// tags: oauth, refresh-token, session-lifecycle, identity-binding, client
// affects: token-sheriff-client
// supersedes:
// end-adr-metadata

== Status

Accepted

== Context

A client that refreshes an OAuth 2.0 token receives a refreshed access token naming a principal.
Nothing in the refresh grant itself guarantees that principal matches the identity the session
was originally established for; an authorization server that mismanages token issuance, or a
client-side bug that mixes up sessions, could hand a refreshed credential belonging to one
session's principal to a different session's caller. A client's refresh path therefore needs a
way to re-confirm, on every refresh, that the principal coming back is the one the session was
bound to — an identity-binding check the token's own ID-token consistency validation does not
provide, because that check compares the refreshed ID token only against the refreshed access
token from the same response, never against the session's original identity.

Two structurally different sources exist for "the session's original identity" to compare
against: a session may have been established with an ID token, whose subject the client could
re-parse from the stored raw ID token bytes at comparison time, or the client could instead
capture the subject once, at the point it is first known, and retain it on the stored session
record for every subsequent comparison. A further structural constraint is that whatever
comparison is chosen must run without a check-then-act gap: any window between reading the
stored identity and writing the confirmed refresh result is a place a concurrent operation could
invalidate the check between the read and the write.

== Decision

The stored session record retains an explicit subject field, captured once when the session is
established or first bound, rather than re-derived by re-parsing a stored raw ID token on each
refresh. The refresh path's identity-binding comparison runs inside the same atomic
retrieve-transform-store operation that already applies the refresh result to the stored record
— the single fail-closed transform seam that also enforces the session's binding-downgrade
refusal — so the comparison and the write that would otherwise race against it happen as one
indivisible step. A session stored with no known subject skips the comparison on a refresh rather
than failing closed unconditionally, and its successor adopts the subject the refreshed token
names, when it names one; from that adoption on the session is bound and every later refresh is
compared. A session with a retained subject that disagrees with the refreshed principal, or a
refresh that names no principal for a bound session, fails closed.

== Consequences

=== Positive

* The identity comparison covers every session that carries a retained subject, including a
  session established through a plain OAuth 2.0 grant with no ID token at all — a
  re-parsed-ID-token approach could bind nothing for exactly that class of session. A session
  stored without a subject is covered from the refresh at which it adopts one.
* Running the comparison inside the atomic store transform closes the check-then-act window a
  comparison performed before the transform would leave open: a concurrent operation on the same
  session cannot invalidate a decision already made and not yet written, because the decision and
  the write are the same atomic step.
* The retained subject is a single constant-time equality check per refresh, with no repeated
  parsing of stored token material on the hot path.

=== Negative

* Adding the subject to the stored session record widens its shape, requiring every existing
  construction site of that record — in production code and in tests — to be updated to the wider
  form; there is no way to introduce the field without touching every caller that builds the
  record directly.
* A session established before its principal was known carries no subject, so its first refresh is
  unbound: the comparison is skipped and the successor adopts whichever principal the refreshed
  token names. Binding takes effect only from that adoption; there is no retroactive way to check
  that the adopted principal is the one the session was originally established for. A session
  whose refreshed tokens never name a principal stays unbound for as long as that holds.

=== Risks

* The `null`-subject skip is a deliberate exception to the fail-closed default for a session stored
  without a known principal, and it lasts until a refresh names one: the first such refresh is
  unbound and can adopt whichever principal the refreshed token names. A caller that assumes every
  session is identity-bound from its establishment is trusting an invariant this decision does not
  provide for that subset of sessions.
* Because the record shape change removes the previous construction arity outright rather than
  introducing it alongside a compatibility shim, any relying party that constructs the stored
  session record directly, outside this codebase, breaks on upgrade with no transitional period.

== Alternatives Considered

*Compare the refreshed access token's subject against the subject parsed from the session's
stored raw ID token, at comparison time, rather than retaining a subject field.* Rejected on two
independent grounds. First, it binds nothing for a session established through a plain OAuth 2.0
refresh grant with no ID token — exactly the class of session the retained-subject approach still
covers, because the subject is captured once at binding time from whichever token carried it,
independent of what is available later. Second, re-parsing the stored raw ID token on every
refresh repeats work the client already did once when the session was established, for no benefit
over reading a value captured at that time.

*Perform the identity comparison outside the atomic store transform — for example, immediately
before invoking it — rather than inside the transform passed to the atomic store update.*
Rejected on concurrency grounds: a comparison performed before the atomic update, and only then
followed by the write, leaves a check-then-act window in which a concurrent revoke-and-clear or
store operation on the same session could invalidate the state the comparison examined between
the read and the write. Running the comparison inside the transform itself, alongside the
existing binding-downgrade refusal the same transform already enforces, makes the check and the
write one atomic step instead of two racing ones.

*Fail closed unconditionally, including for a session stored with no known subject, by treating
an absent subject as itself a binding violation.* Considered and rejected as the default handling:
a client that has legitimate sessions with no known subject — because they were never given one,
not because anything is wrong — would have every refresh of such a session refused, which is a
functional regression for a class of session the identity binding was never meant to police. The
null-subject skip is the accepted alternative: such a session's first refresh is unbound and adopts
the principal the refreshed token names, and the session is bound from then on. The unbound first
refresh is documented as a residual risk rather than closed.

Each rejected alternative either fails to cover the full population of sessions the retained-field
approach covers, repeats work the retained-field approach does once, or introduces a race window
the atomic-transform placement closes. The adopted decision is the one shape that covers every
session class once a subject is retained, with or without an ID token, does the comparison work
exactly once per refresh, and runs it inside the same
atomic step that already enforces the session's other fail-closed guard.
