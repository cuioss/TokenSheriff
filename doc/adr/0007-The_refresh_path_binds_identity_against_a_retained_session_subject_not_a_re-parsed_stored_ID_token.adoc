= ADR-0007: The refresh path binds identity against a retained session subject, not a re-parsed stored ID token

== Status

Accepted

== Context

Nothing in a refresh grant guarantees that the refreshed principal is the one the session was
established for, and the ID-token consistency check compares the refreshed ID token only with the
refreshed access token of the same response. The refresh path needs its own identity binding. Two
sources for the session's identity exist: re-parse the stored raw ID token on every refresh, or
capture the subject once and retain it on the stored record. Whatever is compared must not leave a
check-then-act gap between reading the stored identity and writing the refresh result.

== Decision

The stored session record retains an explicit subject, captured once when the session is established
or first bound. The comparison against the refreshed principal runs inside the same atomic
retrieve-transform-store operation that applies the refresh result — the transform that also refuses a
binding downgrade — so check and write are one step. A session stored without a subject skips the
comparison and adopts the subject the refreshed token names; from then on it is bound. A mismatch, or a
refresh naming no principal for a bound session, fails closed.

Rejected: re-parsing the stored ID token (binds nothing for a session without an ID token and repeats
work); comparing before the transform (reopens the race window); failing closed on an absent subject
(refuses every refresh of a legitimately unbound session).

== Consequences

* Every session with a retained subject is bound, with or without an ID token, at the cost of one
  constant-time compare per refresh, and no concurrent operation can invalidate a decision before it is
  written.
* Adding the subject widened the stored record; every direct construction site, including any outside
  this codebase, had to change, with no compatibility shim.
* A session stored without a subject is unbound until a refresh names one, and the first such refresh
  adopts whichever principal it names — a documented residual risk.

The mechanics (`StoredToken.subject`, the compare inside the store transform, adopt-on-first-subject,
the quarantine of a refused rotated refresh) are specified in
xref:../client/specification/token-handling.adoc#_refresh_identity_binding[Token handling § Refresh-path identity binding].
