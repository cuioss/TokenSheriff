== Status

Accepted

== Context

The client resolves every endpoint it calls from the authorization server's OpenID Connect discovery
document: the authorization, token, userinfo, end-session, revocation, introspection and pushed
authorization request endpoints, and the `jwks_uri`. The issuer the operator configures is the one
value the operator chose; every endpoint URL is taken from the document, which the authorization
server controls and which is only as trustworthy as the channel it arrived on.

Two facts meet at this point:

* A TLS issuer gives the document integrity in transit, but it does not make the URLs in the document
  TLS URLs. A document that names a cleartext `http` token endpoint downgrades every later call to
  that endpoint — client credentials, authorization codes and refresh tokens then travel without
  transport protection — while the operator believes the deployment is TLS end to end, because the
  configured issuer is.
* The client has one switch for cleartext, `allowInsecureHttp`. It exists for local and test setups:
  an `http` issuer, or an `https` issuer that the client reaches through an `http` back-channel origin
  inside a trusted network. An operator sets it for one of those reasons. Reading it as permission for
  a TLS issuer's document to advertise cleartext endpoints would turn a switch meant for the
  operator's own topology into a switch that accepts a downgrade chosen by the document.

The structural choice point is whether the scheme of an advertised endpoint is governed by the same
switch as the scheme of the configured issuer, or by the issuer's own scheme.

== Decision

When the configured issuer is `https`, every endpoint the client models and uses that the discovery
document advertises must be `https` as well. A document that advertises a non-`https` value for any of
them is refused, and discovery fails. `allowInsecureHttp` does not relax this check.

* The checked set is the endpoint fields the client's provider metadata models:
  `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`, `jwks_uri`,
  `end_session_endpoint`, `revocation_endpoint`, `introspection_endpoint` and
  `pushed_authorization_request_endpoint`. An advertised field outside that set is neither read nor
  checked.
* An absent endpoint is not a violation. A present value that is not an `https` URL is, including a
  blank value: it fails the check rather than being read as absent.
* The refusal names the endpoint label only. The advertised URL is untrusted document content and is
  not echoed into the log or the exception message.
* When the configured issuer is not `https` — an `http` issuer that `allowInsecureHttp` admitted — the
  check does not apply; the operator has already chosen a cleartext deployment.

`allowInsecureHttp` keeps its existing meaning and no other: it admits an `http` issuer, and an `http`
back-channel origin, for setups the operator controls. The issuer's scheme, not the switch, decides
what the document may advertise.

== Consequences

=== Positive

* A TLS issuer cannot downgrade any endpoint the client calls, whatever the document says and whatever
  the cleartext switch is set to for local reasons.
* The guarantee an operator reads off the configured issuer — TLS issuer, TLS endpoints — holds for
  every endpoint the client uses.
* The refusal happens once, at discovery, before any credential is sent to an advertised endpoint.

=== Negative

* A deployment whose TLS issuer advertises a cleartext endpoint, for example behind a TLS-terminating
  proxy that rewrites only the issuer, cannot be used without correcting the document. Setting
  `allowInsecureHttp` does not help; the back-channel origin rewrite is the supported way to reach an
  internal endpoint over `http`.
* A blank optional endpoint in an otherwise valid `https` document fails discovery, although the client
  might never have called that endpoint.

=== Risks

* An endpoint field the provider metadata does not yet model is not checked. When the client starts to
  call a further advertised endpoint, that field has to join the checked set, or it would be used
  unchecked.

== Alternatives Considered

**Let `allowInsecureHttp` relax the endpoint check too.** One switch for every cleartext decision. It
was rejected because the switch is set for the operator's own topology, and honouring it here lets the
document, which the operator does not control, choose a downgrade the operator never asked for.

**Check only the endpoints a given flow is about to call.** Fewer refusals for documents with an unused
cleartext field. It was rejected because the check would then be spread across every flow, and a flow
added later could call an advertised endpoint without it. One check at discovery covers every endpoint
the client models.

**Ignore a non-`https` optional endpoint instead of refusing the document.** The client would drop the
endpoint and carry on. It was rejected because a TLS issuer that advertises a cleartext endpoint is
misconfigured or tampered with, and silently treating that endpoint as absent changes what the client
can do without telling the operator.

The rejected options share one flaw: each lets a value the authorization server controls weaken a
transport guarantee the operator configured.
