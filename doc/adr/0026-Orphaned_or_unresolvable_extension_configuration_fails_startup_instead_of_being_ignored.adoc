== Status

Accepted

== Context

The extensions read flat properties, and many take effect only together with another one: `dpop.*`
only with `dpop.enabled=true`, a keystore password only with a keystore path, a JWE default key id only
when it names a configured key. A resolver that reads only what it needs ignores the rest, and the
configuration looks complete while a security setting never applies — `dpop.required=true` without
`dpop.enabled` enforces no proof, JWE algorithm preferences without a key leave JWE unconfigured, a
mistyped default key id silently falls back to another key. Nothing reports it.

== Decision

A property that is set but cannot take effect is a configuration error: the resolver throws an
`IllegalStateException` that names the property and states the fix. The validation-side checks run
while the `TokenValidator` is built, which with an enabled issuer happens at startup; the client
extension's discovery-cache check runs from a startup observer. A configuration with no property of a
feature at all stays a valid "not configured".

Rejected: ignoring the property (the operator relied on exactly that one); a startup warning (easy to
miss, and the application runs with a setting believed active); inferring the missing switch (turns a
mistake into a configuration nobody wrote).

== Consequences

* For the validator the extension builds, and for the client discovery cache, a security setting either
  applies or stops the application, and the error names the remedy.
* Configurations that used to start now fail, including harmless leftovers such as `dpop.*` values after
  DPoP was switched off.
* Each dependent property must be listed in its check; a misspelt name is unknown, not orphaned, and is
  not reported. An application-supplied `@Alternative` `TokenValidator` is not covered at startup,
  because the extension's own build does not run for it.

The individual checks, the `@Alternative` behaviour and the known gaps are specified in
xref:../../token-sheriff-quarkus-parent/doc/integration/quarkus-integration.adoc#configuration-validation[Quarkus integration § Configuration validation];
the startup build it relies on in
xref:../../token-sheriff-quarkus-parent/doc/integration/quarkus-integration.adoc#startup-gating[§ Startup gating],
and the issuers it applies to in
xref:../../token-sheriff-quarkus-parent/doc/integration/quarkus-integration.adoc#issuer-discovery[§ Issuer discovery].
