= ADR-0005: A refresh failure quarantines the session after authorization-server redemption, but preserves it before

== Status

Superseded by ADR-0010

The two-state partition below — redeemed versus not — is correct about the redeemed branch, which
ADR-0010 carries forward unchanged. It is incomplete about the other one: a client-error status the
authorization server attributed to the presented credential itself (RFC 6749 §5.2 `invalid_grant`)
redeems nothing, yet leaves the credential dead, and this ADR classifies it with the transient faults
and preserves the session. ADR-0010 splits that branch into a pre-redemption state and a
credential-rejected state.

== Context

A client that refreshes an OAuth 2.0 token sends the presented refresh token to the
authorization server and, on a successful (2xx) response, receives a token response that may
name a rotated successor. Several independent checks can still refuse the refresh after that
response arrives: the refreshed access token can fail identity or binding validation, a
reconciled scope can fail a configured policy, or the response body itself can fail to parse.
Each of these refusals happens on the client side, after the authorization server has already
processed the request.

The structural question this creates is what "processed" means for the presented token. When
the authorization server rotates on redemption, the act of answering 2xx is itself the moment
the presented refresh token stops being valid at the authorization server — independent of
whether the client-side check that follows accepts or refuses the result. A client whose
session-lifecycle logic treats every refusal identically, without regard to whether redemption
already happened, either destroys sessions on refusals that never touched a live credential, or
preserves sessions holding a credential the authorization server has already invalidated. Both
are wrong in different directions, and a single verdict-based rule ("clear the session whenever
the refresh threw") cannot distinguish them, because a transport failure, a malformed response
before parsing, and a validation refusal after a successful redemption all reach the client as
"the refresh failed" without a uniform sign of which class it belongs to.

== Decision

The client's session-lifecycle response to a refused refresh is dispatched on whether the
authorization server has already redeemed the presented refresh token when the refusal fires,
not on which check produced the refusal or on the transport-level success or failure of the
surrounding response.

* **Before redemption** (a connectivity failure, a DNS failure, or a non-2xx response): the
  presented refresh token is still valid at the authorization server. The session and its stored
  token bundle are left intact; nothing is cleared.
* **After redemption** (the authorization server answered 2xx and any subsequent client-side
  check — identity binding, ID-token consistency, scope policy, or response parsing — then
  refuses the refresh): whether the session is cleared depends on whether the presented token is
  burned. It is burned when the authorization server issued a successor (it rotated), and it is
  presumed burned when the response could not be parsed, because rotation then cannot be
  determined even in principle. For a burned presented token the session is cleared unless the
  store holds a bundle whose refresh token is not the refused one: such a bundle (stored by a
  concurrent re-authentication, say, but equally a superseded token stored during an in-flight
  refresh — the check compares the refresh token only and does not check recency) is spared,
  because it is not the burned credential. An empty store, or one that cannot be read, is
  cleared. The clear is attempted, not guaranteed: it removes the store entry and only then the
  rotation family, so a store that throws on the removal lets that exception propagate in place
  of the refusal, leaves the stored bundle in place, and never reaches the family reset. The
  rotation family is therefore reset only when the store entry was removed, and a spared bundle
  keeps its family together with it. When the successor token is known, it is revoked best-effort
  at the authorization server, when the provider advertises a revocation endpoint, whether or not
  the session was cleared; a transport failure of that revocation is logged at debug level and
  otherwise ignored. When the response could not be parsed, no successor is invented to revoke.
  When the authorization server redeemed the token without rotating it (RFC 6749 §6 permits
  omitting a new refresh token), the presented token is still usable: the session is left
  intact, nothing is cleared and nothing is revoked.

The discriminator is observable purely from the transport layer — whether the authorization
server's response reached a successful status — so every refusal that fires downstream of that
observation is decided by the same rule, whichever validation layer produced it: the session is
cleared fail-closed only when the presented token is burned (rotated, or rotation unknown) and
left intact when the server redeemed without rotating. A refusal that fires upstream of that
observation never reaches the rule, so the session-preserving path is the only one it can take.

That is one rule, not one dispatch. The lifecycle manager applies it on several code paths, and
no single method handles every refusal after redemption:

* A refusal raised inside the token exchange is classified and dispatched in one place
  (`handleRefusedExchange`).
* A refreshed ID token that is inconsistent with the refreshed access token, and an identity or
  sender-constraint binding check that refuses the apply, are handled in `doRefresh`'s own
  catches. Each calls the quarantine (`quarantineRejectedRotation`) only when the exchange
  rotated the refresh token (`rotation.rotated()`); when it did not, the presented token is still
  valid, nothing is revoked, and the session is left untouched.
* A superseded token replayed against the rotation family is handled by `revokeReusedFamily`,
  which revokes the replayed token and then the successor.

What these paths share is the disposition they end in: the revocations (`revokeAndClearFailClosed`,
best-effort, in order) and then the attempted fail-closed clear (`clearRefusedSession`), whose
spare rule is stated in the Decision above. A path that has no credential to name, such as the
unparseable response, revokes nothing and still attempts the clear.

== Consequences

=== Positive

* The session-lifecycle response to a refresh refusal is derived from one architectural fact —
  whether the authorization server redeemed the presented token — rather than from an
  enumeration of which validation layer happened to produce the refusal. Every current and future
  post-redemption refusal is decided by the same rule without a per-check carve-out, whichever
  code path raises it, and that rule attempts to clear the session whenever the presented token is
  burned, subject to the spare rule stated in the Decision.
* A transient client-side or network failure that never reaches the authorization server no
  longer destroys a healthy session, closing the reverse failure mode of over-eager clearing.
* When the rotated successor is knowable, it is actively revoked rather than merely discarded,
  removing a live but unused credential from circulation instead of leaving it to expire.

=== Negative

* The discriminator depends on every code path that can refuse a refresh correctly reporting
  whether redemption occurred; a new refusal path added later that bypasses this signal
  reintroduces the pre-redemption/post-redemption ambiguity this decision closes. Because the
  rule is applied on several code paths rather than through one dispatch, a new path must also
  end in the shared revoke-then-attempted-clear disposition; a path that routes around it is not
  caught by any single switch.
* A response that fails to parse cannot report whether rotation occurred, so that branch always
  presumes redemption and attempts the clear, subject to the spare rule stated in the Decision, without a successor to revoke — a strictly more conservative
  outcome than a case where rotation is actually known, but one that forgoes revoking a
  successor the client cannot name.

=== Risks

* A concurrent caller joining an in-flight refresh that fails must observe the same session state
  the failing caller produces; a discriminator that is correct for a single caller but not
  consistently visible to a joiner would reintroduce the ambiguity for concurrent access.
* Because the session and its rotation family are cleared on every post-redemption refusal that
  burned the presented token and whose stored bundle is the refused one, or that has no readable
  stored bundle (only a stored bundle whose refresh token is not the refused one is spared,
  whatever its recency, and it keeps its family; a redeemed-but-not-rotated refusal burned
  nothing and clears nothing), an authorization server that
  rotates on every request and refuses for reasons unrelated to token compromise (misconfigured
  local validation, for example) forces re-authentication more often than a narrower rule would.
  This is accepted as the safer failure direction: the alternative is preserving a session that
  may hold a credential the authorization server no longer honors.

== Alternatives Considered

*Revert the local rotation state when a post-redemption check refuses the refresh, keeping the
presented token as the session's current credential.* This was the first response to the
identity-binding refusal case. Rejected: when the authorization server has rotated on redemption,
it has already invalidated the presented token on its own side regardless of what the client
does locally. Marking the presented token current again locally cures a local bookkeeping
mismatch but leaves the client holding a credential the authorization server has already burned
— the next refresh attempt then either fails outright or trips the authorization server's own
reuse detection. The fix substituted a worse, remote failure for the local one it corrected.

*Clear the session on every non-success (non-2xx or transport-failure) response, without
distinguishing pre- from post-redemption.* Proposed as a correctness sweep after the redemption
discriminator was introduced for the validation-refusal case. Rejected: a connectivity failure or
a non-2xx response means the authorization server never redeemed the presented token, so it
remains valid. Clearing the session on every such failure destroys healthy sessions on transient
or environmental faults with no compromise of the underlying credential, trading a narrow gap for
a much broader one.

*Enumerate each refusal-producing check individually and hand-wire session clearing into each
one.* This is architecturally equivalent to what a naive implementation would produce absent a
unifying rule, and was rejected implicitly by the redemption-based rule itself: a per-check
enumeration must be revisited every time a new refusal path is added, and a path added without
updating the enumeration silently falls back to the session-preserving default — the exact class
of gap the identity-binding and scope-policy refusals each independently exposed before being
folded into the single redemption-based rule.

Each rejected alternative anchors the session-lifecycle decision to something other than whether
the authorization server actually redeemed the token — either ignoring redemption entirely
(clear-on-every-failure), reacting to a symptom of rotation rather than to rotation itself
(revert), or requiring per-check maintenance that a redemption-based rule makes unnecessary
(enumeration). The adopted decision anchors the session response to the one fact that determines
whether the presented credential is still valid anywhere.
