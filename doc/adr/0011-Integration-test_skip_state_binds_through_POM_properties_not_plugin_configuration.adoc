= ADR-0011: Integration-test skip state binds through POM properties, not plugin configuration
:toc: left
:toclevels: 2
:sectnums:

// adr-metadata
// summary: A module's Failsafe integration-test tier is switched off by wiring its skip flag to skipTests via POM properties, never via the Failsafe <configuration> block, so a command-line override keeps precedence
// tags: build, maven, failsafe, integration-tests, coverage, ci
// affects: token-sheriff-client
// supersedes:
// end-adr-metadata

== Status

Accepted

== Context

A multi-module Maven build with a coverage gate faces a structural tension between two things that must both be true at once: a deploy lane that skips tests entirely must also skip every downstream consumer of test output (including a JaCoCo coverage check), and an operator invoking the build from the command line must be able to override that same skip decision without editing any file.

The mechanism Maven exposes for propagating a skip decision is layered, and the layers do not agree on which source wins. A plugin's own `<configuration>` element is fixed at POM-authoring time and always wins over a same-named user property supplied on the command line; a POM `<properties>` entry, by contrast, is itself a user property with a default, so a command-line `-D` for the same key overrides it. Whichever layer a module chooses to wire its integration-test skip flag through therefore decides, permanently, whether an operator's command-line override is honoured or silently discarded — the two mechanisms are not interchangeable defaults with the same externally observable behaviour.

A second, independent fact compounds the problem: some Failsafe versions do not treat their own conventional skip property as an alias for the general test-skip property, so a module that skips its unit-test tier via that general flag does not thereby skip its own integration-test tier — the integration-test JVM still starts, still executes, and still writes coverage data. A downstream class-level or bundle-level coverage gate reading that data is then graded against a coverage sample that is neither the full signal (tests did not really run under intent) nor an honestly absent one (the data file is non-empty) — a poisoned intermediate state that a purely "did the file exist" check cannot distinguish from a legitimate partial run.

Any module that both (a) has an integration-test tier bound to Failsafe and (b) is built on a lane that intentionally skips tests must resolve both of these questions the same way, or its skip behaviour will silently diverge from its sibling modules on some subset of invocation lanes.

== Decision

An integration-test tier's skip state is always wired to the general test-skip flag through a POM `<properties>` entry, never through the plugin's own `<configuration>` block. Concretely, a module binds its own skip property to the general flag as a property default (`<ownSkipProperty>${skipTests}</ownSkipProperty>`), with the general flag itself given an explicit literal default (`<skipTests>false</skipTests>`) so the property chain has something concrete to resolve against rather than an unresolved placeholder.

This keeps three invocation lanes correct simultaneously, because a `<properties>` default and a plugin `<configuration>` value answer to command-line overrides in opposite ways:

* A lane that passes the general skip flag causes the module's own flag to interpolate to the same value, so its integration-test JVM never starts and no coverage data is written for it — coverage gates reading that module correctly see legitimately absent data rather than a poisoned sample.
* An operator who overrides the module's own skip flag directly on the command line still wins, because a command-line user property outranks a POM `<properties>` default. This escape hatch stays live precisely because the general skip flag cannot be relied on alone to reach every plugin's own tier.
* A lane that passes neither flag leaves both properties at their literal defaults, so the integration-test tier runs and every downstream coverage gate is fully enforced.

Binding the same relationship inside the plugin's own `<configuration>` block instead would collapse the second lane: a `<configuration>` value is fixed at POM-authoring time and unconditionally outranks a same-named command-line property, so the command-line override would be silently discarded exactly when an operator most needs it to work.

== Consequences

=== Positive

* The three invocation lanes (default, general-skip, own-tier-skip-override) each resolve to the correct running/not-running state, and the resolution is entirely declarative — no profile-specific logic is needed to keep them apart.
* On the general-skip lane, a coverage gate downstream of the integration-test tier is graded on a sample that is either fully present or legitimately absent, never on a partial sample produced by a tier that ran when the invocation intended it not to.
* The own-tier-skip-override lane is deliberately outside that guarantee, and the distinction is worth stating rather than glossing. Overriding only the integration-test tier leaves the unit tier running, so the gate is graded on unit coverage alone — a partial sample by construction. That is sound rather than a gap: unit coverage is real coverage, and a class that clears the threshold on it has genuinely cleared it. The unsound case this decision closes is the inverse — a tier running *against* the invocation's intent and contributing a sparse sample that neither reflects the tests nor is honestly absent. Guarding the gate on the own-tier flag was rejected for exactly this reason: it would disable a gate on a lane whose coverage is legitimate.
* The command-line override escape hatch is preserved for every module that adopts this wiring, independent of which build plugin version is in use or whether that version's own skip property happens to alias the general flag.

=== Negative

* The binding is a property-chain convention rather than a plugin capability; a reviewer unfamiliar with the precedence relationship between `<properties>` and `<configuration>` can mistake the two forms as equivalent and introduce a regression by moving the binding into `<configuration>` for readability.
* The general skip flag's own default must be stated as an explicit literal in every module that adopts the chain; an unresolved placeholder is not a valid boolean, so omitting the literal default silently breaks the chain rather than falling back to a sensible value.

=== Risks

* A future build-tool upgrade could change which layer wins between a POM property and a command-line user property, which would invert the precedence this decision relies on; the risk is bounded because that precedence is a documented, stable part of the build tool's property-resolution model rather than plugin-specific behaviour.
* A module that adopts this pattern without also auditing its own coverage-gate configuration can still be graded on a poisoned sample if the coverage gate itself does not distinguish an absent-data skip from a present-but-sparse one; this decision addresses the skip-propagation half of that problem, not the gate's own data-shape validation.

== Alternatives Considered

* **Bind the skip flag inside the plugin's own `<configuration>` block.** This is the more discoverable form — a reader looking at the plugin's execution sees the skip wiring in the same place as every other setting for that plugin — but it fails the command-line-override lane unconditionally: a `<configuration>` value always outranks a same-named command-line user property, so the one lane an operator relies on to force a run or a skip from outside the POM stops working. Rejected because it trades a readability improvement for the loss of a load-bearing escape hatch.
* **Rely on the general test-skip flag alone, with no module-local property chain.** This works only when every plugin's own skip property is a true alias of the general flag; it silently fails for any plugin version where that alias does not hold, reproducing the poisoned-coverage-sample failure mode this decision exists to close. Rejected because it depends on plugin-version behaviour that a module cannot control or verify structurally.
* **Add a build profile that toggles the integration-test tier on or off.** A profile changes the module's effective POM shape per invocation, which means the three lanes are no longer expressed as data (property values) but as which profile activated — harder to reason about from `mvn help:effective-pom`, and it reintroduces the same precedence question one layer up (does a command-line flag activate or deactivate the profile the way an operator expects). Rejected as strictly more moving parts for the same outcome the property chain already achieves declaratively.

The alternatives fall into one class: each replaces a single, inspectable property-precedence chain with either a plugin-specific behaviour the module cannot verify (`<configuration>`, the bare general flag) or a second axis of build-shape variation (profiles) that has to be reasoned about on top of the property chain rather than instead of it.
