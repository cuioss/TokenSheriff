== Status

Proposed

== Context

A cache hit skips signature and claim validation, but not everything can be skipped. A DPoP proof is
fresh per request, so it must be checked on every hit, and checking it records the proof's `jti` in
the replay store. Custom validation rules can be stateful and must also run on every hit. Expiry and
maximum token age must be re-checked because their answer changes while the token is cached.

That leaves two questions. Which component performs the time checks on a hit: the cache, or the
pipeline after the cache has returned the token? And in which order do the time checks and the
per-request checks run?

The order matters. On the uncached path the claim validation, which includes expiry and maximum age,
runs before the DPoP proof. A hit that checked the proof first would record the `jti` of a request
that is about to be rejected for an expired token, and a request carrying both an expired token and
a bad proof would be reported as a DPoP failure on a hit but as an expiry on a miss. The reported
reason would then depend on whether the token happened to be cached.

The structural choice point is whether a cache lookup may return an entry that is already invalid,
leaving the caller to notice.

== Decision

The cache never returns an entry that fails its time policy. It rejects such an entry itself, inside
the lookup.

* `AccessTokenCache.get` evaluates a verified hit against the entry's stored time policy (ADR-0020).
  An expired entry is removed and the lookup throws `TOKEN_EXPIRED`; an entry past its maximum token
  age is removed and the lookup throws `TOKEN_AGE_EXCEEDED`. Each rejection is logged and counted.
* Only a hit that passed both checks is returned. The pipeline then re-resolves the issuer, which
  rejects a token whose issuer's JWKS loader is no longer `OK`, then validates the DPoP proof, then
  runs the custom validation rules.
* The resulting order on a hit — time policy, issuer, DPoP, custom rules — matches the order of the
  uncached path, where claim validation precedes the DPoP proof and the custom rules.

== Consequences

=== Positive

* An invalid entry cannot leave the cache, so no caller of the lookup can forget to check it.
* A request with an expired or too-old token is rejected for that reason whether or not the token was
  cached, and the reported event type does not depend on the cache state.
* A request that is rejected for its token's time policy records nothing in the DPoP replay store.
* An expired or too-old entry is evicted at the moment it is found, not only by the next background
  eviction.

=== Negative

* The lookup has a side effect beyond returning a value: it can throw, remove an entry and increment
  security counters. A caller must treat it as a validation step, not as a plain map read.

=== Risks

* The equivalence with the uncached path holds only while both paths keep the same order. A change
  that moved the DPoP check ahead of claim validation on one path and not on the other would make the
  reported reason depend on the cache state again.

== Alternatives Considered

**Return the entry and let the pipeline check expiry and age.** The cache would be a plain store, and
the pipeline would apply the time checks after the lookup. It was rejected because every caller of the
lookup then carries the obligation, and the stored per-entry policy (ADR-0020) would have to be exposed
to the caller to apply it. An omitted check returns an expired token.

**Check the DPoP proof before the time policy on a hit.** The proof is checked first because it is the
per-request part. It was rejected because it inverts the order of the uncached path: the reported
reason for a doubly invalid request would depend on whether its token was cached, and the replay store
would record proofs of requests that are rejected anyway.

**Treat an expired entry as a cache miss.** The lookup would drop the entry and return nothing, and the
full validation would reject the token. The outcome is the same rejection. It was rejected because it
runs a full parse and signature check to reach a verdict the cache already has, and because the
rejection would then be counted by the full path rather than at the point where the expiry was found.

The rejected options share one flaw. Each makes the result of a request with an invalid token depend
on more than the token: on caller discipline, on the cache state, or on a second, redundant validation.
