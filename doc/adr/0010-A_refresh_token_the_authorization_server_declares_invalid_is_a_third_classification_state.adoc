== Status

Accepted

== Context

This decision supersedes the earlier two-state redemption rule, whose record was removed once its
content was carried here; its redeemed-branch disposition is carried forward unchanged in the Decision
below.

The client's response to a refused refresh was decided by one question: had the authorization server
already redeemed the presented token? That partitions failures at the transport layer into two
regions — success status means consumed, anything else means not — and treats everything short of a
success as a transient fault that preserves the session.

That is wrong for one shape. RFC 6749 §5.2 `invalid_grant` on a client-error status is the server
stating that the presented credential is expired, revoked or already redeemed. Nothing was consumed,
so the two-state model preserved the session, leaving the client holding a credential the server had
declared dead; every later refresh failed identically and never attributably. This is a real
deployment shape: a server with single-use refresh tokens refuses a replayed token, and its successor,
exactly this way (RFC 6749 §10.4, OAuth 2.0 Security BCP §4.14.2). Clearing on every non-success
status instead destroys healthy sessions on transient faults. The failure space has three regions,
and the model had two names.

== Decision

A refusal raised inside the token exchange is classified into mutually exclusive, exhaustive states,
and the session-lifecycle response follows the state:

* *Pre-redemption* — no evidence the server judged the credential (a connection, DNS or SSRF-blocked
  failure, a server-error status, any unrecognised client-error). The session and its bundle are kept.
  Local preservation is not server-side validity: a token request is a non-idempotent `POST` (RFC 9110
  §9.2.2), so behind a lost response the server may already have rotated the token.
* *Credential-rejected* — the server judged the credential and declared it invalid without consuming
  the grant. Nothing rotated, so nothing is revoked, but a clear of the store entry and rotation family
  is attempted and the caller must re-authenticate.
* *Redeemed* — the server consumed the grant before a client-side check refused the result. A burned
  presented token (rotated, or an unparseable success response presumed rotated) quarantines the
  session: a known successor is revoked best-effort (RFC 7009, only when a revocation endpoint is
  advertised) and a clear is attempted; a redemption without rotation (RFC 6749 §6) keeps the session
  and revokes nothing.

Every clear spares a stored bundle whose refresh token is not the refused one (no recency check; the
bundle keeps its family); an empty or unreadable store is cleared.

The recognition rule for credential-rejected is an allow-list of exactly one code: a `4xx` status, a
body that parses as an RFC 6749 §5.2 error response, and `error` exactly `invalid_grant`. Every other
shape stays pre-redemption, including a `5xx` carrying `invalid_grant`, except the separately
allow-listed `invalid_scope` on a `4xx`, which the scope-refused amendment below classifies. The rule is
applied to the response the exchange ends on, after the one DPoP nonce retry: a non-success answer
carrying a `DPoP-Nonce` header is retried once, so a `5xx` answered by a `4xx` `invalid_grant` on the
retry is credential-rejected. The fail-safe direction is to
preserve the session, and widening the list is a decision argued one code at a time. The library's
own dispatch of a refused exchange ends in a failing `default` arm, so a further state fails loudly
instead of falling through to the session-preserving default.

=== Amendment: a refresh-token family refusal maps onto the existing states

The family refusal (reuse, or a revoked family) is classified as well, without a new kind: raised
while feeding a rotation into the family it is *redeemed*, carrying the successor as the revocation
target; raised when reading the current token of a revoked family it is *credential-rejected*. It never
maps to pre-redemption.

=== Amendment: a refused scope is a fourth classification state

RFC 6749 §5.2 `invalid_scope` on a `4xx` classifies as *scope-refused*, carried by
`InvalidScopeException`: the server judged the requested scope before applying any grant, so the
session is kept, nothing is revoked or cleared, and — unlike pre-redemption — no retry is owed and no
`WARN` is logged, because the same request gets the same answer. The order from least to most the
server did is pre-redemption, scope-refused, credential-rejected, redeemed. The family refusal never
maps to scope-refused.

Rejected throughout: clearing on every non-success (destroys healthy sessions); folding
credential-rejected into redeemed (invents a revocation target); an optional verdict instead of a total
kind (absence doing two jobs); a wider allow-list (`invalid_client`, `unauthorized_client` and
`use_dpop_nonce` do not name the presented credential); classifying `invalid_scope` as
credential-rejected or as pre-redemption.

== Consequences

* A dead credential is cleared at the first refusal and the reason is attributable; deployments with
  single-use refresh tokens and family-wide revocation are handled correctly.
* The set of failures that can clear a session grew by exactly one code, so no new transient fault
  reaches the clearing path; scope-refused changes no disposition, only the retry obligation.
* Classification now parses an authorization-server-controlled body, bounded by the payload limit;
  no part of it reaches a log or an exception message.
* A server that returns `invalid_grant` for an unrelated reason forces re-authentication; a server
  that signals a dead credential with another code or status keeps the session — both accepted.
* The pre-redemption guarantee rests on transport-code ordering (a failed send never produces a
  response object), not on an assertion.

are specified in
