== Status

Accepted

== Context

An `HttpJwksLoader` learns about rotated keys only through its periodic refresh, so a token signed with
a new key is rejected for up to one refresh interval, and a failed initial load leaves the issuer
unusable just as long. Refreshing on an unknown `kid` closes the gap but moves the trigger of an
outbound fetch onto the request path, before any signature check and with an attacker-chosen `kid`.
The design has to rule out amplification (each invented `kid` a fetch), blocking (request threads
waiting on the identity provider), displacement (forced rotations pushing legitimate keys out of the
retired sets), state poisoning (failed attempts feeding re-discovery and the staleness bound),
lifecycle leakage (a fetch of a closed generation installing keys) and overlap of three fetch paths.

== Decision

The unknown-`kid` refresh is opt-in and bounded per loader by one atomic window claim; it never blocks
the caller and never counts a failure, and it installs a key set only if that set holds the requested
`kid`, through the same commit step and the same in-flight guard as every other fetch.

* Off by default; `HttpJwksLoaderConfig.unknownKidRefreshWindow` accepts 5 to 3600 seconds, with no
  default value.
* A miss schedules at most one background fetch per window and per loader and returns at once; the
  triggering token is refused, the next token naming the new `kid` succeeds once it is installed.
* A discarded fetch changes nothing and is never recorded as a failed refresh cycle.
* A separate opt-in, `initialLoadRetry(boolean)`, retries a failed initial load with a fixed delay of
  1 second doubling to 30 seconds, never above the refresh interval.
* Both require background refresh, and both are per-issuer Quarkus properties subject to the
  orphaned-configuration rule of
  xref:0026-Orphaned_or_unresolvable_extension_configuration_fails_startup_instead_of_being_ignored.adoc[ADR-0026].
* Amendment: a read-only window pre-check runs before the guard, so a miss inside a claimed window
  never touches the guard; a failed hand-off releases the guard and burns the window.

Rejected: a synchronous fetch on the lookup (request-path outage); a global or per-`kid` rate limit
(couples issuers, or lets a `kid` spray earn fetches); installing whatever a fetch returns
(displacement); counting a failed on-demand fetch (an unauthenticated caller steers recovery);
configurable retry backoff (mis-tunable into a tight loop).

== Consequences

* A rotated key can be accepted after one on-demand fetch; an invented-`kid` flood reaches the identity
  provider at most once per window per issuer; the request path never waits on the network; without
  either setting nothing changes.
* An attacker who claims every window defers on-demand pickup entirely, leaving the periodic refresh;
  the triggering token is always refused; a held guard makes a periodic cycle skip its fetch.
* The bound holds only while every fetch path takes the guard and every installation goes through the
  shared commit step; a caller-supplied executor must run or reject every task it accepts.

The mechanics — the order of pre-check, guard and claim, the hand-off failure handling, the executor
requirement and the shared commit step — are specified in
xref:../validation/architecture.adoc#jwks-integration[Validation Architecture § JwksLoader and Key Management],
with the lifecycle fence in
xref:../validation/architecture.adoc#jwks-lifecycle[§ Loader Lifecycle Lock and Generation Epoch].
