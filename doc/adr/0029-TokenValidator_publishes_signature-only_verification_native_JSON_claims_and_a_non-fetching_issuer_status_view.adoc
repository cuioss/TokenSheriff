== Status

Accepted

== Context

`TokenValidator` answers one question through `createAccessToken`, `createIdToken` and
`createRefreshToken`: is this an authenticated token for one of my issuers? A second kind of caller —
a gateway receiving back-channel logout tokens, reading structured claims, or reporting issuer health —
needs the building blocks rather than the verdict, and otherwise re-assembles library internals
(signature check, JSON parsing with its own bounds, loader status) under different limits. Opening the
facade has three failure modes to close: a signature-only result mistaken for a verdict; claims
flattened or parsed outside the validator's `ParserConfig` bounds (a JWE-arrived token's raw token is
the outer JWE, so only the validator can re-derive its payload); and an observability accessor that
leaks the loaders the validator owns.

== Decision

`TokenValidator` publishes additive, opt-in seams, each on a type that cannot be mistaken for a verdict
or used to change validator-owned state; the three `create*` methods and every shipped health probe
keep their behaviour.

* `verifySignature(String)` returns `SignatureVerifiedToken`, a final type outside both sealed token
  hierarchies, so a token with unvalidated claims cannot reach code that accepts `TokenContent` or
  `MinimalTokenContent`. It skips the issuer's `expectedTokenType` and returns `typ` verbatim, and it
  counts one new `SIGNATURE_ONLY_VERIFIED` event.
* `getRawClaims(TokenContent)` re-decodes with the validator's own parser into a deep-immutable native
  map; claims are not stored on validated or cached tokens.
* `getIssuerStatuses()` returns read-only `IssuerStatusView`s that read the loader status without a
  fetch and expose neither the `IssuerConfig` nor the loader.
* The JWKS readiness probe gains two keys: an opt-out of issuer disclosure, and an opt-in report of an
  embedder-supplied validator.
* The library publishes a back-channel logout-token validator (`logout` package) built on these seams:
  no new `TokenType`, a bounded `LogoutTokenCheck` result without free text, a fixed check order with the
  replay guard last, an absent `typ` accepted, and a fail-closed replay guard that stores `jti` digests
  with fixed capacity, reads no clock and is decided on one instant per validation. Two amendments,
  made before and after release, refuse an `exp` exactly now (RFC 7519 §4.1.4) and bound the magnitude
  of `iat` / `exp` and the freshness window.

Rejected: a permitted subtype of `TokenContent` or an `IdTokenContent` result; applying
`expectedTokenType` in the signature-only entry; storing native claims on every token; exposing the
`IssuerConfig` or loader; reporting external validators by default; leaving logout validation to each
consumer; a logout `TokenType`; refusing an absent `typ`; evicting the oldest guard entry when full.

== Consequences

* Consumers reuse the library's string limits, issuer resolution, header posture, signature and parser
  bounds instead of copying them; cached and serialized token content are unchanged.
* The public surface grows by three methods and two types; `getRawClaims` re-decodes, and for a JWE
  re-decrypts, on every call; the new success counter is registered by default.
* A caller can still treat a `SignatureVerifiedToken` as a decision; a full replay guard refuses every
  new logout token until entries expire; the single-instant rule assumes a clock that does not step
  back.

The seams' constraints are specified in
xref:../validation/architecture.adoc#token-validator-seams[Validation Architecture § Public Seams], the
logout package in xref:../validation/architecture.adoc#logout-package[§ Logout Token Validation], and
the checks with their boundaries and limits in
xref:../validation/security-reference.adoc#logout-token-validation[Security Reference § Logout Token Validation].
