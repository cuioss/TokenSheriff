== Status

Accepted

== Context

The client's packages are `@NullMarked` under JSpecify, so optionality is declared, and the codebase
must decide every time whether a genuinely optional value is a `@Nullable` reference or an `Optional`.
The two shapes belong to different kinds of surface. A record component's accessor is projected from
the declaration, so an `Optional` component makes the container the stored state that `equals`,
`hashCode` and `toString` derive from, and `@Nullable Optional<T>` would allow two spellings of
absence. A hand-written accessor's return type is designed independently of storage, so returning
`Optional` costs no state and prevents an accidental dereference. Both shapes are live in the client;
without a rule the module looks inconsistent and drifts.

== Decision

The shape follows the kind of surface, not the kind of value:

. An optional *record component* is typed `@Nullable` and carries `null`; no `Optional` is stored.
. An optional value on a *hand-written accessor* is exposed as `Optional`.
. A record's compact constructor null-rejects every component not annotated `@Nullable`, and must keep
  doing so, because the annotation is the only signal separating optional from required and the
  constructor is reachable from unanalysed callers, deserialization and reflection.

Rejected: `Optional` components for uniformity (stored-state ambiguity); `@Nullable` accessor returns
for uniformity (loses the guard on the consumed surface); no rule (drift); dropping the constructor
checks (leaves required components enforced nowhere).

== Consequences

* Optionality is machine-readable where it is declared, and no optional component stores a container.
* The module keeps two shapes for one concept; the rule explains the split, the code alone does not.
* The `@Nullable` annotation and the constructor check are a pair that nothing links: removing one
  without the other silently widens a required component.
