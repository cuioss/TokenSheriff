== Status

Accepted

== Context

A JWKS loader's status is consumed twice: the issuer cache admits an issuer only while its loader is
`OK`, and the readiness check reports ready only while every loader it checks is `OK` as of its last
check — the answer is cached for `sheriff.token.health.jwks.cache-seconds` (default 30 s), so a loader that
leaves `OK` is reflected in readiness only once that cache expires — the loaders of
an application-supplied (external) validator are checked only when
`sheriff.token.health.jwks.report-external-validator` is `true` (default `false`). A status that does not
match the loader's real state therefore changes what is accepted or whether the application receives
traffic. The status must be truthful — an `OK` after a fetch that yielded no usable key verifies
nothing, and a loader that never leaves a failed first load never recovers. Yet not every failure is
worth retrying: an unreachable discovery endpoint is a property of the moment, while an advertised
issuer that does not match the trust anchor is a property of the document, and retrying it adds no
information but repeats an audited security event every cycle.

== Decision

`LoaderStatus.OK` is reported only while a usable key set is installed, and only transient discovery
failures are retried.

* A failed first load is recovered by the background refresh, and `UNDEFINED` after it means "a
  refresh cycle is going to retry" — published only when such a cycle is enabled, can recover and is
  actually scheduled; otherwise the result is a terminal `ERROR`.
* A failed refresh never downgrades an existing `OK`, except under an opt-in maximum staleness.
* Discovery that is unavailable is retried; a security rejection — issuer mismatch, absent advertised
  issuer, egress block, an advertised `jwks_uri` no HTTP handler can be built for — is terminal while
  no endpoint is installed. With an endpoint installed, a moved `jwks_uri` is followed by bounded
  re-discovery, and a rejected re-discovery keeps the installed endpoint.

Rejected: retrying every failure (re-counts rejections without bound); treating every failure as
terminal (turns a transient outage into a standing one); `OK` after any successful fetch (admits an
issuer with no key); immediate `ERROR` for a failed first load with refresh enabled (`ERROR` is
reserved for what nothing will retry).

== Consequences

* `OK` is a statement about key material, so the issuer cache and the readiness check act on the same
  fact; an outage heals without a restart, and nothing previously rejected is accepted.
* While discovery retries, readiness shows `IN_PROGRESS`; a permanently unreachable endpoint keeps the
  application not ready with no terminal status, and every new failure kind needs an explicit
  retryable-or-terminal classification.
* Without `maxStaleness`, keys that are never refreshed stay trusted for the length of an outage; with
  it, an outage longer than the bound rejects every token of the issuer.

The status rules, the resolution classification, re-discovery and its bound are specified in
xref:../validation/architecture.adoc#jwks-status-contract[Validation Architecture § Loader Status Contract];
the loader's ownership by the validator in § TokenValidator, its lifecycle lock in
xref:../validation/architecture.adoc#jwks-lifecycle[§ Loader Lifecycle Lock and Generation Epoch], and the
readiness check's resolution of the validator in use in
xref:../../token-sheriff-quarkus-parent/doc/integration/quarkus-integration.adoc#observability-bean-resolution[Quarkus integration § Observability bean resolution].
