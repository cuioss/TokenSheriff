== Status

Accepted

== Context

Mutual-TLS client authentication (`tls_client_auth`) is the one client-authentication strategy whose
credential is not part of the request the client composes: it is a client certificate presented in
the TLS handshake, honoured only when the transport's `SSLContext` carries client key material. The
client transport plumbs none, so a `tls_client_auth` selection would send an ordinary anonymous TLS
request. Such a strategy must not be selected, and yet, unclassified, its untested state reads as a
permanent coverage hole. Sender-constrained tokens and confidential-client authentication for first
production are already carried by DPoP, whose key material the client owns and whose binding lives in
the token; a live refresh test (`cnf.jkt` kept across a DPoP-constrained rotation) demonstrates it.

== Decision

`tls_client_auth` and its implementation `MtlsClientAuth` are an *alpha capability*, with three
properties that hold together: retained as a real, declared surface (not a stub, not deleted); never
selected by `ClientAuthenticationSelector`, whatever the server advertises; not counted as a coverage
gap while unexercised. DPoP is the sender-constraining and client-authentication direction for first
production. Leaving alpha is a deliberate architecture change — plumbing client key material and
building certificate infrastructure — not a gap a coverage pass closes.

The classification covers client authentication only; preserving a certificate-bound confirmation
claim (`cnf.x5t#S256`) a token already carries is a separate capability and is unaffected.

Rejected: making the strategy reachable now (transport and fixture capability for an unrequested
method); deleting it (discards a correct implementation and the ability to name an advertised method);
leaving it as a permanent open residual (a classification declined, not a residual tracked).

== Consequences

* No configuration or server advertisement can route a request through a method that would go out
  unauthenticated; coverage accounting gets a stable answer; effort follows DPoP.
* The codebase carries a real implementation no production path reaches, and a relying party that
  requires mTLS client authentication is not served.
* A future change that plumbs client key material could make the strategy reachable without revisiting
  this classification; the coverage exemption is sound only while the strategy is unreachable.

The selection rule and the alpha status are specified in
xref:../client/specification/retrieval-flow.adoc#_client_authentication[Retrieval & flow § Client authentication].
