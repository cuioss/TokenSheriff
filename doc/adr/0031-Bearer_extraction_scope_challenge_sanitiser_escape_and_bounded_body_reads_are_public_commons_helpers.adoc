== Status

Accepted

== Context

Four pieces of HTTP-edge logic existed as private or duplicated code. The Quarkus producer extracted
`Bearer` credentials with a private exact-prefix match that a gateway had to copy. It built the
`insufficient_scope` challenge by escaping a quote inside a scope name — a challenge the client's own
parser then refused, because RFC 6749 §3.3 allows no quote in a `scope-token`. Some sinks must carry no
non-ASCII character, which the one commons sanitiser did not offer. And the validation module and the
client each had their own bounded response-body handler, which differed in eight observable ways
(the client's had no `Content-Length` pre-check and no test class), while a gateway needed a
keep-the-prefix mode neither offered.

== Decision

The four helpers become public, framework-neutral classes in the commons layer of
`token-sheriff-validation`, and the Quarkus producer and the client adopt them:
`commons.http.BearerCredentials`, `commons.http.BearerChallenge`,
`ErrorTextSanitizer.escapeNonPrintableAscii` (a third form of the one sanitiser of
xref:0022-A_flow_context_is_single-use_and_untrusted_text_is_sanitised_by_one_commons-layer_utility.adoc[ADR-0022]),
and `commons.transport.BoundedBodyHandler` with a `FAIL` or `TRUNCATE` policy, replacing both former
handlers.

The helpers apply the RFCs strictly: the scheme name matches case-insensitively (RFC 9110 §11.1),
credentials that break RFC 6750 §2.1 are malformed, and a scope name outside the `scope-token` grammar is
refused rather than escaped. The shared body handler keeps the validation module's behaviour and failure
message; each difference of the old handlers was pinned by a named test before they were removed.

Amendment: the scopes of every `@BearerAuth` and `@BearerToken` are checked when the application is
built, through the same challenge builder the producer uses, merged per bean class as the interceptor
merges them at run time (xref:0024-The_bearer-token_interceptor_reads_its_class-level_binding_from_the_bean_class_not_the_ArC_subclass.adoc[ADR-0024]).
Two limits are accepted by the operator: an interface default method is checked on its own, and an
override of a generic base method is found by name and parameter types only. A set the check misses is
answered 500 on the request path of a request whose validated token lacks one of its scopes. The `error_description` grammar stays the RFC 9110 quoted string, and
both helpers bound their own work on hostile input.

Rejected: keeping the helpers private (the copies had already diverged); exact scheme matching (refuses
conforming clients); escaping an out-of-grammar scope (a conforming parser rejects the whole challenge);
two aligned body handlers (the client already depends on the commons layer, and copies drift again).

== Consequences

* Every HTTP edge extracts credentials, builds the challenge and bounds a read with one implementation,
  and the producer's challenge is always one the client parser accepts.
* Several defaults changed on upgrade: a lower- or mixed-case scheme is now a presented token; a token
  with an internal space or control character is answered 400 `INVALID_REQUEST`; an out-of-grammar scope,
  more than 64 scopes, or a challenge over 8192 characters fails the deployment, within the two limits of
  the amendment above (an interface default method is checked on its own, so a merged set over the limit
  passes the deployment; at request time only a request whose validated token lacks a required scope of
  that set is answered 500, because the challenge is built only then — a request without a token is
  answered 401 and a fully authorized request proceeds); the client's back-channel
  reads refuse an over-advertised `Content-Length` before reading and use the validation failure message.
* The public API of the validation module grew by three classes and one method; a `TRUNCATE` caller must
  read `BoundedBody.truncated()`.
