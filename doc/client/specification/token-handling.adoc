== Overview

_Realizes xref:../requirements.adoc#CLIENT-15[CLIENT-15]–xref:../requirements.adoc#CLIENT-20[CLIENT-20].
See xref:../threat-model.adoc[Threat Model], xref:../best-practices.adoc[Best Practices] and
xref:../architecture.adoc[Architecture]._

The *Token* aspect is the server-side lifecycle *delta* on top of the validation module: how
retrieved tokens are validated, held, refreshed, revoked, and kept sender-constrained. It
*references the validation module* for all token-trust decisions and adds no
signature/algorithm policy of its own. It is deliberately kept separate from
xref:retrieval-flow.adoc[Retrieval & flow]: retrieval acquires tokens; token handling is what
happens to them afterwards.

== Validation is inherited, not re-implemented

Every token the engine retrieves — access token and ID token — is validated through the
xref:../../validation/requirements.adoc[validation] pipeline *before it is trusted or stored*
(xref:../requirements.adoc#CLIENT-15[CLIENT-15],
xref:../threat-model.adoc#T-AUD-CONFUSION[T-AUD-CONFUSION]):

* signature verification and the algorithm policy (`VALIDATION-1.3`, RFC 8725 — asymmetric
  only; `alg=none` / HMAC / weak keys rejected) are *inherited unchanged*;
* `iss`, `aud`, `exp`, `iat` claim validation is performed by the pipeline;
* DPoP-bound tokens are validated per `VALIDATION-8.7`.

The client MUST NOT re-implement or weaken any of this. This is the primary *validation
synergy*: tokens are cryptographically validated, not merely received — closing the biggest
gap in the xref:../architecture.adoc[portal reference], where identity is taken from userinfo
with no ID-token signature validation.

== ID-token and userinfo validation

For OpenID Connect (xref:../requirements.adoc#CLIENT-16[CLIENT-16],
xref:../threat-model.adoc#T-IDTOKEN-INTEGRITY[T-IDTOKEN-INTEGRITY]):

* the *ID token* is validated for signature (via the pipeline) and claims — `iss`, `aud`,
  `azp`, `exp`, the session-bound `nonce` (xref:retrieval-flow.adoc[Retrieval & flow],
  `CLIENT-6`), and `at_hash` where present;
* when the *userinfo* endpoint is used, the response is validated (signature, if signed) and
  its `sub` is *bound to the `sub` of the validated ID token* — a userinfo `sub` mismatch is
  rejected;
* identity MUST NOT be taken from an unvalidated ID token or userinfo response.

* Source: https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation[OIDC Core §3.1.3.7], https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse[OIDC Core §5.3.2].

== Server-side token lifecycle

Retrieved tokens are held *server-side* and never returned to the browser in usable form
(xref:../requirements.adoc#CLIENT-17[CLIENT-17]). The lifecycle:

[cols="1,3", options="header"]
|===
| Stage | Rule

| *Store* | Held server-side; the BFF binding shape (server-side store or encrypted cookie) is the application's choice (<<_bff_groundwork_non_preclusion>>). Storage is minimal and protected at rest. The stored bundle records the principal the session was established for (`StoredToken.subject`), which is what <<_refresh_identity_binding>> compares against.
| *Refresh* | Access tokens are refreshed with `refresh_token`; *refresh-token rotation* is applied, and a detected reuse of a rotated token triggers *revocation of the token family* (xref:../threat-model.adoc#T-REFRESH-THEFT[T-REFRESH-THEFT]). The refresh additionally enforces the session-identity binding (<<_refresh_identity_binding>>) and reconciles the granted scope (<<_scope_reconciliation>>).
| *Revoke* | Tokens are revoked through the engine's own `RevocationClient` back-channel call (RFC 7009, on the `cui-http` transport, `COMMONS-7`) on logout (xref:step-up-and-logout.adoc[step-up & logout]) and on detected refresh-token reuse (family revocation, xref:../threat-model.adoc#T-REFRESH-THEFT[T-REFRESH-THEFT]).
| *Expiry* | Short-lived access tokens are preferred; refresh drives renewal.
|===

* Source: https://www.rfc-editor.org/rfc/rfc9700#section-4.14[RFC 9700 §4.14] (refresh-token protection / rotation), https://www.rfc-editor.org/rfc/rfc7009[RFC 7009] (revocation).

[NOTE]
====
*In-memory token material is held as immutable `String`.* Access, refresh and ID tokens — and the
`client_secret` — are carried as Java `String` instances (`StoredToken`, `RefreshTokenFamily`,
`TokenResponse`, `ClientConfiguration.clientSecret`), so they cannot be zeroed on clear or logout and
remain in the heap until the garbage collector reclaims and overwrites them. This is an accepted Java
trade-off: a `char[]`/`byte[]` custody model would let callers wipe the buffer eagerly, but the JOSE,
JSON and HTTP layers the engine builds on exchange `String`s throughout, so a byte-array custody model
cannot be maintained end-to-end without copying the secret back into a `String` at every boundary. The
residual exposure is bounded by the "protect the at-rest store" posture above — storage is minimal,
server-side, and short-lived (short access-token TTLs, revoke-and-clear on logout) so the window in
which reclaimable material lives in the heap is kept small.
====

== [[_refresh_identity_binding]] Refresh-path identity binding

The authorization-code path binds the acquired identity to the session four ways — `state`,
`nonce`, `at_hash` and `iss`. The refresh path historically carried *none* of them, so a refresh
that returned a token for a different principal would silently re-point a live session
(xref:../threat-model.adoc#T-REFRESH-IDENTITY[T-REFRESH-IDENTITY]). The refresh path now carries
its own binding, closing that asymmetry:

* `StoredToken.subject` records the principal the session was established for. It is `@Nullable`:
  a session may legitimately be stored before the principal is known.
* On every refresh the `sub` of the *newly validated* access token is compared against the bound
  subject. The comparison is constant-time, matching the `SubBindingValidator` idiom used for the
  userinfo `sub` binding.
* A *mismatch refuses the refresh fail-closed*: the atomic store transform writes nothing, so a
  refused refresh can never become a partial write.
* When the authorization server had *already rotated* the refresh token before the refusal, refusing
  is not enough — the presented token is burned at the server, so keeping it would leave the client
  holding a dead credential that fails, or trips the server's own reuse detection, on the next
  refresh. That case is therefore *quarantined*: the server-issued successor is revoked (RFC 7009),
  and the store entry and rotation family are cleared, forcing re-authentication. The quarantine is
  keyed on the *refusal itself, not on its reason*: a refused sender-constraint downgrade
  (<<_sender_constraint_preservation>>) is quarantined on exactly the same terms as a `sub`
  mismatch, because the presented token is equally burned either way. When the server returned no
  new refresh token (RFC 6749 §6 permits omitting it), the presented token is still valid and the
  untouched store entry stays usable.
* When the bundle carries *no* subject yet, the check is skipped and the refreshed subject is
  adopted — the binding takes effect from the first refresh that names a principal.
* Where the authorization server also returns a refreshed ID token, it is validated through the
  pipeline and cross-checked for `iss`/`sub` consistency against the refreshed access token before
  it is carried forward. A refreshed ID token is *not* checked for `nonce`: OIDC Core §12.2 states
  it SHOULD NOT carry one, and no fresh flow `nonce` exists to compare against.

* Source: https://openid.net/specs/openid-connect-core-1_0.html#RefreshTokenResponse[OIDC Core §12.2].

== [[_scope_reconciliation]] Granted-scope reconciliation

Every refresh reconciles the scope the authorization server actually granted against the scope
this client requested, and reports the outcome on `RotationResult`
(xref:../threat-model.adoc#T-SCOPE-DRIFT[T-SCOPE-DRIFT]):

* `RotationResult.grantedScope` — the raw `scope` value the server returned, or `null` when it
  omitted the parameter. `null` does *not* mean "no scope was granted": RFC 6749 §5.1 defines an
  omitted `scope` as *identical to the requested scope*, so an absent value means "as requested".
* `RotationResult.scopeDelta` — how the granted set relates to the requested set; never `null`.
* `ClientConfiguration.strictScopeReconciliation` — opt-in, defaults to `false`.

The full mode × outcome contract. This table mirrors the `RotationResult.ScopeDelta` enum in
`token-sheriff-client/src/main/java/de/cuioss/sheriff/token/client/token/RotationResult.java`, whose
Javadoc points back here. It is hand-authored rather than generated, because each row carries
per-posture behavioural prose an enum-name dump could not reproduce — so a constant added, removed
or renamed there must be reflected here in the same change.

[cols="1,3,2,2", options="header"]
|===
| `scopeDelta` | Meaning | Default (lenient) | `strictScopeReconciliation=true`

| `EQUAL`
| The granted set is exactly the requested set.
| Accepted silently.
| Accepted silently.

| `NARROWED`
| The granted set is a strict subset — the server withheld at least one requested scope.
| Accepted, `WARN`-logged, surfaced.
| Accepted, `WARN`-logged, surfaced (*unchanged* by the flag).

| `BROADENED`
| The granted set contains at least one scope this client did not request.
| Accepted, `WARN`-logged, surfaced.
| *Refused* with `ClientProtocolException`; no `RotationResult` is produced.

| `UNDECLARED`
| No reconciliation was performed: either this client requested no scope at all, or the server
  omitted the `scope` parameter (RFC 6749 §5.1 — "as requested").
| Accepted silently.
| Accepted silently.
|===

A granted set that both adds an unrequested scope *and* drops a requested one classifies as
`BROADENED`: the unrequested member is the signal that matters, and folding the mixed case into
the broader classification keeps the strict posture from silently accepting a grant it was
enabled to refuse.

[IMPORTANT]
====
*This is anomaly reporting, not compliance enforcement.* No published RFC obliges a client to
reject a grant broader than the one it requested. RFC 6749 §3.3 affirmatively *permits* the
authorization server to grant a scope other than the one requested, obliging it only to disclose
the result, and the *resource server* remains the enforcement point for an over-broad claim. That
is why the lenient, reporting posture is the default: refusing by default would convert a benign
server quirk — several major authorization servers canonicalise or expand scope sets routinely —
into a total authentication outage with no attacker in the loop. Enable the strict mode *only*
against an authorization server known not to do so; the outage risk falls entirely on the
deployment that opts in. Its only profile precedent is FAPI 1.0 Part 1 §5.2.3(10), an
authorization-code-response rule that FAPI 2.0 dropped.
====

* Source: https://www.rfc-editor.org/rfc/rfc6749#section-3.3[RFC 6749 §3.3] (access-token scope), https://www.rfc-editor.org/rfc/rfc6749#section-5.1[RFC 6749 §5.1] (an omitted `scope` is the requested scope).

[NOTE]
====
*Breaking record-shape change.* `RotationResult` gained the `grantedScope` and `scopeDelta`
components, and `StoredToken` gained `subject`. Both are Java records, so a relying party that
constructs either *directly* — rather than receiving one from `RefreshFlow` or
`TokenLifecycleManager` — must supply the new components. `scopeDelta` is rejected as `null`;
`grantedScope` and `subject` are nullable. The two new `RotationResult` components are
authorization metadata rather than credentials, so unlike the token fields they are rendered in
full by `toString()` — which is what makes a grant delta diagnosable from a log line.
====

== [[_sender_constraint_preservation]] Preserving the sender-constraint

Where a retrieved token is sender-constrained — DPoP (`cnf.jkt`) or mTLS-bound — the engine
keeps the binding intact across storage, refresh and any forwarding
(xref:../requirements.adoc#CLIENT-18[CLIENT-18],
xref:../threat-model.adoc#T-CONSTRAINT-LOSS[T-CONSTRAINT-LOSS]): the stored token stays
associated with its proof-key / certificate binding, refresh preserves the constraint, and
storage is kept minimal so a bound token is never copied more widely than the lifecycle
requires. A sender-constrained token MUST NOT be degraded to a replayable bearer token by the
way it is stored or forwarded.

NOTE: "mTLS-bound" here means preserving a certificate-bound confirmation claim (`cnf.x5t#S256`) a token already carries. That is separate from mTLS client authentication (`tls_client_auth`), which is an alpha capability (xref:../../adr/0012-mTLS_client_authentication_is_an_alpha_capability_DPoP_is_the_sender-constraining_and_client-authentication_direction.adoc[ADR-0012]).

A refresh that would apply no confirmed `cnf` binding to a sender-constrained bundle is therefore
*refused* by the same atomic store transform that enforces the subject binding — the refusal is
independent of what the authorization server returned, since the client cannot preserve a
constraint it was not handed. The refusal follows the same rotated-vs-not rule as the identity case
(<<_refresh_identity_binding>>): when the authorization server had *already rotated* the refresh
token before the refusal, the presented token is burned server-side, so the session is *quarantined*
rather than preserved, forcing re-authentication. When the server did not rotate, the presented
token is still valid and the untouched store entry stays usable. Sender-constrained refresh is
applied through the `applyRefresh` overload that carries the confirmed binding.

* Source: https://www.rfc-editor.org/rfc/rfc9449[RFC 9449], https://www.rfc-editor.org/rfc/rfc8705[RFC 8705].

== [[_bff_groundwork_non_preclusion]] BFF groundwork — non-preclusion

The lifecycle above is the *BFF groundwork* this capability owns
(xref:../requirements.adoc#CLIENT-19[CLIENT-19]). It MUST support *either* token-binding
deployment without forcing the choice:

* *stateful BFF* — an opaque session-id cookie + a server-side token store the engine's
  lifecycle populates;
* *stateless BFF* — the access token returned to the browser only inside an HttpOnly cookie
  encrypted with a server-side symmetric key, decrypted per request.

The engine seam — confidential retrieval, server-side lifecycle, validation — is identical
for both. The browser↔backend session cookie, symmetric-key management, backend-API CSRF and
request proxying are the *BFF application's* concern and are not implemented here.

* Source: https://datatracker.ietf.org/doc/html/draft-ietf-oauth-browser-based-apps[OAuth 2.0 for Browser-Based Apps].

== Error surfacing (delegated to commons)

The engine (pure Java) signals every failure — validation rejection, refresh failure,
normalized inbound IdP error — through the commons typed-exception hierarchy (`COMMONS-9`) and
produces *no* HTTP problem documents itself (xref:../requirements.adoc#CLIENT-20[CLIENT-20]).
HTTP-surfaced client errors conform to the commons RFC 9457 model: the
`token-sheriff-client-quarkus` edge (and any future RESTEasy / portal adapter) maps the typed
exceptions to `application/problem+json` (`COMMONS-10`), leaking no internal detail
(`COMMONS-12`). Inbound IdP error responses (`error` / `error_description`, RFC 6749 §5.2) are
normalized by commons (`COMMONS-11`), never passed through verbatim.

* Source: https://www.rfc-editor.org/rfc/rfc9457[RFC 9457], xref:../../commons/specification/error-model.adoc[commons error-model spec].

== Adversarial coverage

The commons `TokenDispatcher` / `UserInfoDispatcher` *adversarial* modes emit tampered
claims, `sub` mismatches, and reused rotated refresh tokens
(xref:../../commons/specification/transport.adoc#adversarial_dispatchers[commons transport
spec], `COMMONS-7`); the client tests assert the validation pipeline rejects tampered tokens,
the userinfo `sub` binding is enforced, rotation triggers family revocation on reuse, and the
sender-constraint survives a refresh (xref:../requirements.adoc#CLIENT-22[CLIENT-22]). The two
refresh-path controls above are covered by *matched positive/negative pairs*, so deleting either
guard turns a test red rather than merely leaving one green: a substituted-`sub` refresh is
refused and the session asserted quarantined while a matching-`sub` refresh is accepted and
rotates the bundle; and the granted-scope matrix asserts each `scopeDelta` in *both* postures, including
the `ClientProtocolException` the strict posture raises on a broadened grant. Both are
additionally proven against a real authorization server in the integration suite. The full
unit + integration coverage and the `CLIENT-N` → threat → test traceability are specified in
xref:test-strategy.adoc[Test strategy].
