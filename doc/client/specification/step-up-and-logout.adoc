== Overview

_Realizes xref:../requirements.adoc#CLIENT-12[CLIENT-12], xref:../requirements.adoc#CLIENT-13[CLIENT-13]
and xref:../requirements.adoc#CLIENT-25[CLIENT-25].
See xref:../threat-model.adoc[Threat Model], xref:../best-practices.adoc[Best Practices] and
xref:../architecture.adoc[Architecture]._

Two flows layered on the confidential authorization-code engine
(xref:retrieval-flow.adoc[Retrieval & flow]): *step-up authentication* — raising the
authentication assurance for a sensitive operation — and *RP-initiated logout* — ending the
session at the IdP and revoking held tokens. Both drive the engine's *own* hardened
back-channel HTTP (on the `cui-http` transport primitives, `COMMONS-1`), which applies the
in-module egress / path and TLS-scheme control before each fetch
(xref:../architecture.adoc#_owned_back_channel_http[owned back-channel HTTP]).

== Step-up authentication (RFC 9470)

Step-up lets a resource server demand a higher authentication assurance than the current
session provides (xref:../requirements.adoc#CLIENT-12[CLIENT-12],
xref:../threat-model.adoc#T-STEPUP[T-STEPUP]).

=== Requesting an assurance level

On an authorization request the engine can require an assurance level via:

* `acr_values` — one or more requested authentication context class references;
* `max_age` — the maximum acceptable age (seconds) of the end-user authentication.

These are sent on the authorization request built in xref:retrieval-flow.adoc[Retrieval &
flow].

=== Handling the challenge

When a resource server responds to an under-authenticated request with an
`insufficient_user_authentication` challenge (RFC 9470 — a `WWW-Authenticate: Bearer
error="insufficient_user_authentication"` carrying the required `acr_values` / `max_age`), the
engine:

. parses the challenge to recover the required `acr_values` / `max_age`;
. *re-drives authorization* with those parameters (a fresh authorization-code flow, all the
  flow-integrity checks of xref:retrieval-flow.adoc[Retrieval & flow] applying);
. on return, *verifies* the resulting ID token's `acr` satisfies the requirement and
  `auth_time` satisfies `max_age` — only then is the operation treated as sufficiently
  authenticated.

A response whose `acr` / `auth_time` does not satisfy the requirement MUST NOT be treated as
a successful step-up.

* Source: https://www.rfc-editor.org/rfc/rfc9470[RFC 9470], https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest[OIDC Core §3.1.2.1].

=== The `auth_time` freshness check

The `max_age` check compares `auth_time` with the current time, read from an injectable clock
(`InstantSource`), so the boundary can be tested against a fixed instant. An `auth_time` is
rejected when it is older than `max_age` plus a clock-skew allowance:

* the allowance tolerates a clock difference between the client and the authorization server.
  It only ever *widens* the `max_age` boundary, and it is opt-in: a caller supplies it together
  with the clock, and a negative allowance is refused;
* the default — the one `StepUpHandler` uses — reads the system clock with an allowance of
  *zero*: an `auth_time` exactly `max_age` seconds old is accepted, and one second older is
  rejected.

A challenge whose `max_age` is negative is rejected (fail-closed) before this arithmetic runs,
whatever the `auth_time` and the allowance: a negative `max_age` is no meaningful bound, and
evaluating it would let the allowance widen it into an accepting one.

== The `insufficient_scope` challenge (RFC 6750)

Next to the RFC 9470 challenge, a resource server can refuse an access token because it lacks a
scope: `WWW-Authenticate: Bearer error="insufficient_scope"`, optionally naming the required
`scope`, a `realm` and an `error_description` (RFC 6750 §3.1). `InsufficientScopeChallengeParser`
reads that challenge into an `InsufficientScopeChallenge` record — the `scope` set in first-seen
order without duplicates (empty when the challenge names none), and the optional `realm` and
`error_description`, both escaped and length-bounded before they are stored
(xref:../requirements.adoc#CLIENT-25[CLIENT-25],
xref:../threat-model.adoc#T-CHALLENGE-INJECTION[T-CHALLENGE-INJECTION]).

The parser only reports the challenge: acting on it — for example obtaining a token with a wider
scope — is the consumer's decision. It does not refresh or re-request a token, widen or request a
scope, perform I/O or keep state, and it does not parse the `invalid_token` or `invalid_request`
challenges.

=== The shared `auth-param` reader and header guard

Both challenge parsers read the `WWW-Authenticate` value through one package-private helper,
`BearerChallengeParams`, which splits the RFC 9110 `auth-param` list on commas outside a
quoted-string and unescapes quoted values. Its header guard refuses the whole value, never
repairing it, when the value:

* is longer than 8192 characters (checked before any other work);
* carries `CR`, `LF` or `NUL`, or any other control character or `DEL` — horizontal tab is
  tolerated as optional whitespace and inside a quoted-string;
* does not start with the `Bearer` scheme;
* shows a following challenge as a segment — a non-empty segment without `=` (such as `Basic` or
  `realm`) or a name that is not an RFC 9110 `token` (such as `basic realm`) — so a parameter of a
  second challenge (`Bearer error="insufficient_scope", Basic, scope="x"`) is never read as a
  Bearer parameter;
* names an `auth-param` twice.

The `insufficient_scope` parser reads in a strict mode that additionally refuses an empty
`auth-param` name, an unterminated quoted value, a trailing backslash and an unquoted `scope`
value (RFC 6750 §3 defines `scope` as a `quoted-string`, so `scope=read` is refused as well as
`scope=read write`). It then requires every `scope` token to match the RFC 6749 §3.3
`scope-token` grammar and accepts at most 64 tokens; only a `scope` of ASCII spaces alone counts
as empty, so a `scope` made of other whitespace (such as U+2003) is read as a token and refused.

The step-up parser reads in a lenient mode that keeps its earlier handling of an empty name
(skipped) and an unterminated quoted value (kept verbatim), but it now applies the same guard:
a challenge carrying another control character, longer than 8192 characters, or followed by
another scheme or a valueless segment is refused rather than read.

* Source: https://www.rfc-editor.org/rfc/rfc6750#section-3.1[RFC 6750 §3.1], https://www.rfc-editor.org/rfc/rfc6749#section-3.3[RFC 6749 §3.3], https://www.rfc-editor.org/rfc/rfc9110#section-11.2[RFC 9110 §11.2].

== RP-initiated logout

The engine triggers logout at the IdP's `end_session_endpoint` and revokes the tokens it
holds (xref:../requirements.adoc#CLIENT-13[CLIENT-13],
xref:../threat-model.adoc#T-LOGOUT[T-LOGOUT]).

=== The end-session request

The engine drives the `end_session_endpoint` with:

[cols="1,3", options="header"]
|===
| Parameter | Rule

| `id_token_hint` | The held ID token, identifying the session to end.
| `post_logout_redirect_uri` | A *pre-registered* value matched by *exact string comparison* — never pattern / prefix, to prevent an open redirect.
| `state` | Session-bound, verified on return, as on the authorization request.
|===

=== Revoking held tokens

Logout is not complete until the tokens the engine holds are revoked, so a logout does not
leave live tokens behind. The engine revokes the access and refresh tokens through its *own*
`RevocationClient` back-channel call (RFC 7009, on the `cui-http` transport, `COMMONS-7`) and
clears them from the server-side lifecycle
(xref:token-handling.adoc[token handling], xref:../requirements.adoc#CLIENT-17[CLIENT-17]).

=== Boundary: receivers are the BFF's concern

RP-initiated logout *triggering* (above) and token revocation are the in-scope building
blocks. *Front-channel / back-channel logout receivers* and the *Session-Management iframe*
are browser-session concerns owned by the BFF application, not this engine
(xref:../requirements.adoc#CLIENT-19[CLIENT-19]). A BFF that implements the back-channel logout
receiver endpoint validates the received logout token with the `token-sheriff-validation`
logout-token validator (xref:../../validation/requirements.adoc#VALIDATION-13.4[VALIDATION-13.4]).

* Source: https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OpenID Connect RP-Initiated Logout 1.0], https://www.rfc-editor.org/rfc/rfc7009[RFC 7009] (revocation), https://www.rfc-editor.org/rfc/rfc9700#section-4.1[RFC 9700 §4.1] (open-redirect defence).

== Adversarial coverage

The engine makes no end-session HTTP call — it builds the redirect the browser follows — so no
end-session dispatcher is involved; the commons `EndSessionDispatcher` is not used by the client
tests. The tests assert the redirect the engine builds (`id_token_hint`, the exact registered
`post_logout_redirect_uri`, `state`), and the revocation of held tokens is covered by the
revocation and lifecycle tests (xref:../requirements.adoc#CLIENT-22[CLIENT-22]). Step-up
is exercised by driving an `insufficient_user_authentication` challenge and asserting the
re-driven `acr` / `auth_time` verification. The full unit + integration coverage and the
`CLIENT-N` → threat → test traceability are specified in xref:test-strategy.adoc[Test strategy].
