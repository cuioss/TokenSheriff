== Overview

_See xref:requirements.adoc[Client Requirements], xref:best-practices.adoc[Best Practices]
and xref:architecture.adoc[Architecture]._

Threat model for the `client` capability — the server-side confidential-client engine that
*retrieves tokens* and drives the OAuth 2.0 / OpenID Connect *flows*. Its threats are the
*acquisition and flow* threats: authorization-code injection, mix-up between multiple
authorization servers, callback CSRF, redirect-URI abuse, weak client credentials, token
replay, insufficient authentication assurance, and logout that leaves tokens live — plus the
server-side *token-lifecycle* threats of refresh-token theft, audience confusion,
sender-constraint loss, a substituted principal on refresh, and undetected granted-scope drift.

The catalog builds on the foundational OAuth 2.0 threat model
(https://www.rfc-editor.org/rfc/rfc6819[RFC 6819]) and the current OAuth 2.0 Security BCP
(https://www.rfc-editor.org/rfc/rfc9700[RFC 9700]). Those two are the catalog's general
foundation, not a blanket warrant for every entry. Each entry cites *its own* source, a
mitigation, and the covering `CLIENT-N` requirement, grouped by aspect —
and xref:#T-SCOPE-DRIFT[] in particular is recorded as prudent hardening with no RFC mandate
behind it. Threats are kept *separate by
aspect* and *not blended* with the transport or token-trust threats owned elsewhere
(xref:#_out_of_scope_delegated[]).

== System context

The client engine:

* Constructs authorization requests and exchanges authorization codes for tokens as a
  *confidential client*, entirely server-side (no tokens in the browser).
* Authenticates to the token / PAR / revocation endpoints and *requests* sender-constrained
  tokens. The `introspection_endpoint` is only parsed from discovery metadata and, like the other
  advertised endpoints, https-checked only when the configured issuer itself uses https; it is
  never called.
* Holds retrieved tokens *server-side*, refreshes and revokes them, and validates them
  through the validation pipeline.
* Triggers RP-initiated logout and honours step-up challenges.
* Drives its *own* outbound OIDC/OAuth back-channel HTTP (discovery, token, userinfo, revocation,
  PAR) on the upstream `cui-http` library, and applies its own *path, scheme and host-address
  egress control* before each fetch (xref:#T-SSRF-ADVERTISED[]). It inherits only the `cui-http`
  TLS enforcement and the validation pipeline's own JWKS retrieval; it does not delegate the
  back-channel fetches themselves.

| *Authorization-code injection.* An attacker injects a code obtained elsewhere into a
  victim's session (or vice-versa) to have it redeemed under the wrong context.
| Bind the code to the requesting session: PKCE `S256` binds it to the `code_verifier`; for

| Validate the `iss` authorization-response parameter (RFC 9207) against the initiating
  issuer and/or use a distinct `redirect_uri` per AS; reject on mismatch before exchange.
| https://www.rfc-editor.org/rfc/rfc9207[RFC 9207], https://www.rfc-editor.org/rfc/rfc9700#section-4.4[RFC 9700 §4.4]

| xref:requirements.adoc#CLIENT-7[CLIENT-7]

| [[T-CSRF]]T-CSRF
| *CSRF on the callback.* An attacker replays a crafted callback to bind their session /

| Send an unguessable, session-bound `state` on every request; reject a callback whose
  `state` is missing or does not match.
| https://www.rfc-editor.org/rfc/rfc9700#section-4.7[RFC 9700 §4.7]

| *Weak or leaked client credentials.* A shared `client_secret` is guessed, leaked from
  config/logs, or intercepted, letting an attacker impersonate the client.
| Prefer `private_key_jwt` over `client_secret`; send secrets only over TLS and never in a
  URL; protect credentials at rest; never log them; restrict grants to the secure subset. mTLS
  (`tls_client_auth`) is alpha — declared, never selected — so it is not a mitigation route
  here, leaving `private_key_jwt` as the supported strong client-authentication route.
| https://www.rfc-editor.org/rfc/rfc7523[RFC 7523], https://www.rfc-editor.org/rfc/rfc8705[RFC 8705], https://www.rfc-editor.org/rfc/rfc9700#section-2.2[RFC 9700 §2.2]

| [[T-TOKEN-REPLAY]]T-TOKEN-REPLAY
| *Token replay (no sender-constraining).* A stolen bearer access token is replayed by any
  holder.
| Request sender-constrained tokens — a DPoP proof — at the token endpoint, and reject at
  issuance a response the AS did not bind: a `token_type` other than `DPoP`, or a JWT access
  token whose `cnf.jkt` is absent or differs from the proof-key thumbprint. Verifying the binding
  at presentation is inherited (`VALIDATION-8.7`). DPoP (RFC 9449) is the implemented direction: it
  binds the issued token to the client's key without authenticating the client, so it composes
  with `private_key_jwt` rather than replacing it. The certificate-bound variant remains
  specified as a binding kind, while mTLS client authentication is alpha.
| https://www.rfc-editor.org/rfc/rfc9700#section-4.10[RFC 9700 §4.10], https://www.rfc-editor.org/rfc/rfc9449[RFC 9449], https://www.rfc-editor.org/rfc/rfc8705[RFC 8705], https://openid.net/specs/fapi-2_0-security-profile.html[FAPI 2.0]
| xref:requirements.adoc#CLIENT-11[CLIENT-11]

| [[T-STEPUP]]T-STEPUP
| *Insufficient authentication assurance for a sensitive operation.* An operation proceeds
  with a session authenticated at too low an assurance.
| Request `acr_values` / `max_age`; honour the resource server's
  `insufficient_user_authentication` challenge (RFC 9470) by re-driving authorization; verify
  the resulting `acr` / `auth_time` before proceeding.
| https://www.rfc-editor.org/rfc/rfc9470[RFC 9470]
| xref:requirements.adoc#CLIENT-12[CLIENT-12]

| [[T-CHALLENGE-INJECTION]]T-CHALLENGE-INJECTION
| *Header injection and scope smuggling through `WWW-Authenticate`.* A resource server response,
  or anything able to shape it, makes a challenge parser read a parameter that is not the Bearer
  challenge's own: a second challenge whose parameters are read as Bearer parameters
  (`Bearer error="insufficient_scope", Basic, scope="x"`), a duplicate `auth-param`, a line break
  or other control character that splits or forges the value, or an oversized value.
| Fail closed in the shared header guard: refuse the whole value, never repair it, when it is
  longer than 8192 characters, carries `CR`, `LF`, `NUL`, any other control character or `DEL`
  (horizontal tab tolerated), is followed by another scheme or carries a valueless segment, or
  names an `auth-param` twice. The `insufficient_scope` parser additionally refuses an empty name,
  an unterminated quoted value, a trailing backslash, an unquoted `scope` value (RFC 6750 §3
  defines `scope` as a `quoted-string`), a `scope` token outside the RFC 6749 §3.3 grammar and
  more than 64 `scope` tokens, and escapes the `realm` and the `error_description` before storing
  them.
| https://www.rfc-editor.org/rfc/rfc6750#section-3.1[RFC 6750 §3.1], https://www.rfc-editor.org/rfc/rfc9110#section-11.2[RFC 9110 §11.2], https://www.rfc-editor.org/rfc/rfc9110#section-5.5[RFC 9110 §5.5]
| xref:requirements.adoc#CLIENT-25[CLIENT-25], xref:requirements.adoc#CLIENT-12[CLIENT-12]

| [[T-LOGOUT]]T-LOGOUT
| *Logout that leaves tokens live / open-redirect on `post_logout_redirect_uri`.* Logout
  clears the browser session but held tokens stay usable, or the post-logout redirect is
  abused as an open redirect.
| Send `id_token_hint`; exact-match the registered `post_logout_redirect_uri`; bind `state`;
  revoke the held tokens as part of logout.
| https://openid.net/specs/openid-connect-rpinitiated-1_0.html[OIDC RP-Initiated Logout], https://www.rfc-editor.org/rfc/rfc9700#section-4.1[RFC 9700 §4.1]
| xref:requirements.adoc#CLIENT-13[CLIENT-13], xref:requirements.adoc#CLIENT-17[CLIENT-17]

| [[T-URL-LEAK]]T-URL-LEAK
| *Tokens / codes exposed in URL query or fragment.* Credentials leak through browser
  history, server logs, or the `Referer` header.
| Use `response_mode=form_post`; exchange the code at the token endpoint over the back
  channel; never place tokens/codes in a URL.
| https://www.rfc-editor.org/rfc/rfc9700#section-4.3[RFC 9700 §4.3]
| xref:requirements.adoc#CLIENT-1[CLIENT-1], xref:requirements.adoc#CLIENT-14[CLIENT-14]

| [[T-TLS-TOKEN]]T-TLS-TOKEN
| *Token-endpoint TLS downgrade / MITM.* An on-path attacker downgrades or MITMs a token /
  PAR / revocation request to substitute responses or capture secrets.
| *Delegated to commons* — TLS 1.2+ with certificate validation on every outbound request
  (`COMMONS-2`); the TLS primitive is commons / `cui-http`, applied by the engine's own
  back-channel transport (`BackChannelHttp`). It inherits the
  `COMMONS-2` hostname-matching carve-out as the symmetric peer of the commons
  xref:../commons/threat-model.adoc#T-TLS[T-TLS] row, reached here by
  `sheriff.client.verify-hostname` — a client-wide, default-ON knob covering every HTTPS
  back-channel call (token, userinfo, revocation, PAR); a cleartext `http` target carries no TLS
  and so no hostname check. Relaxing it narrows hostname matching only — chain
  trust, expiry and algorithm constraints stay enforced — and the residual exposure is recorded
  with the delegated control, in the commons threat model's
  xref:../commons/threat-model.adoc#_residual_risks[residual risks]. When the optional
  `sheriff.client.back-channel-origin` is set, `sheriff.client.verify-hostname` and the per-client
  trust apply to the host actually contacted: the certificate presented by the back-channel host
  is validated against the back-channel host name, not the public issuer name. The back-channel
  origin therefore never widens what a certificate is accepted for.
| https://www.rfc-editor.org/rfc/rfc9700#section-2.6[RFC 9700 §2.6], xref:../commons/threat-model.adoc#T-TLS[commons T-TLS]
| xref:requirements.adoc#CLIENT-14[CLIENT-14] (relies on xref:../commons/requirements.adoc#COMMONS-2[COMMONS-2]), xref:requirements.adoc#CLIENT-24[CLIENT-24]

| [[T-SSRF-ADVERTISED]]T-SSRF-ADVERTISED
| *Back-channel request steered by a hostile discovery document (SSRF / egress).* A hostile or
  mix-up-controlled AS advertises a `token_endpoint` / `userinfo_endpoint` / `revocation_endpoint`
  / PAR URL crafted to steer a credential-bearing back-channel `POST` at an unintended target, or
  carrying a traversal / injection / encoding-evasion path.
| The engine drives its *own* back-channel HTTP and applies an *in-module egress control*: each
  advertised endpoint URL is run through the `de.cuioss.http.security` URL-path validation pipeline
  and refused if it fails; a non-TLS endpoint is refused, and an `https` issuer's discovery document
  advertising a non-`https` value for any endpoint the client models and uses (`authorization_endpoint`,
  `token_endpoint`, `userinfo_endpoint`, `jwks_uri`, `end_session_endpoint`, `revocation_endpoint`,
  `introspection_endpoint`, `pushed_authorization_request_endpoint`) — a blank value included — is
  refused regardless of `allowInsecureHttp`
  (xref:../adr/0028-Discovery_refuses_a_non-https_endpoint_advertised_by_an_https_issuer_regardless_of_allowInsecureHttp.adoc[ADR-0028]);
  a discovery, token or PAR response without `application/json` on every `Content-Type` line, or a
  userinfo response with neither `application/json` nor `application/jwt`, is refused, as is a
  value carrying `CR`, `LF` or `NUL`; a quoted `expires_in` makes a token or PAR response malformed;
  response reads are size-bounded. A *host-address egress policy* (`EgressPolicy`, configured on
  `ClientConfiguration`) runs on the URL actually contacted — after the back-channel origin rewrite —
  for every discovery and back-channel call (discovery, token, PAR, userinfo, revocation), and is
  secure by default: a host resolving to a loopback, link-local (including cloud metadata),
  site-local, unique-local, carrier-grade NAT, wildcard, broadcast or multicast address is refused.
  This default can refuse a configured or advertised internal endpoint; the only relaxations are
  explicit — `sheriff.client.allow-loopback-egress` (loopback only) and
  `sheriff.client.allowed-egress-hosts` (listed hosts bypass the range check wherever they appear,
  advertised endpoints included). The policy resolves the host immediately before the fetch, so a
  DNS answer that changes before the connection is made is not seen. The optional back-channel origin (`sheriff.client.back-channel-origin`) adds no steering
  primitive: it is operator-configured only, and an advertised endpoint is retargeted to it only
  when the endpoint shares the configured issuer's origin — advertised data selects *whether* a
  call is rewritten, never *where to*, so it cannot steer a call to a third origin. An endpoint
  advertised on a foreign origin is contacted unchanged and still faces the controls above. The
  issuer identity, the discovery-document `issuer` check and the token `iss` checks stay intact.
| https://www.rfc-editor.org/rfc/rfc9700#section-2.6[RFC 9700 §2.6], https://github.com/advisories/GHSA-7vw6-5q2f-7w5r[CVE-2026-1180]
| xref:architecture.adoc#_owned_back_channel_http[owned back-channel HTTP], xref:requirements.adoc#CLIENT-24[CLIENT-24]

[NOTE]
====
*Two response checks are deliberate narrowings beyond the specifications.* Both are stated as rules
in xref:requirements.adoc#CLIENT-14[CLIENT-14]; neither is required of a client by the standards
they rest on.

* *Media type.* https://www.rfc-editor.org/rfc/rfc6749#section-5.1[RFC 6749 §5.1],
  https://www.rfc-editor.org/rfc/rfc9126#section-2.2[RFC 9126 §2.2] and
  https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse[OIDC Core §5.3.2] tell the
  authorization server which media type to send; none obliges a client to refuse a response that
  arrives with another. The engine refuses it: a token or PAR response without `application/json` on
  every `Content-Type` line, and a userinfo response with neither `application/json` nor
  `application/jwt`, is not read.
* *`expires_in` type.* RFC 6749 §5.1 and RFC 9126 §2.2 have the authorization server send
  `expires_in` as a JSON number. A lenient client reads the number out of a quoted value; the engine
  refuses a token or PAR response whose `expires_in` is a string such as `"3600"` as malformed.

Both checks run after a success status. At the token endpoint the grant is then already redeemed,
so the refusal is raised as `RedeemedResponseException`: an authorization-code login fails, and a
refresh is classified as redeemed and, since whether the refresh token was rotated cannot be known,
its session is quarantined as presumed rotated (xref:#T-REFRESH-REFUSAL[]). An authorization server that labels its responses with another
media type, or sends `expires_in` as a string, cannot be used with this engine. That is the accepted
cost: the engine does not guess how to read a response that does not follow its own format.

== Token aspect

[cols="1,2,3,1,1", options="header"]
|===
| ID | Threat | Mitigation | Source | Requirement

| [[T-REFRESH-THEFT]]T-REFRESH-THEFT
| *Refresh-token theft (server-side).* A refresh token exfiltrated from the server-side store
  is used to mint fresh access tokens indefinitely.
| Rotate refresh tokens on each use; detect reuse of a rotated token and, on detection in the
  lifecycle manager's own `refresh()`, attempt to revoke the replayed token and then the successor
  the authorization server issued on that exchange (best-effort and only when the provider
  advertises a revocation endpoint; a server that revokes family-wide drops the whole family on
  the first) and attempt to clear the session. A reuse detected by
  `applyRefresh` clears the session but revokes nothing and leaves the successor to the caller;
  sender-constrain where available; protect the at-rest store; minimal storage.
| https://www.rfc-editor.org/rfc/rfc9700#section-4.14[RFC 9700 §4.14]
| xref:requirements.adoc#CLIENT-17[CLIENT-17], xref:requirements.adoc#CLIENT-18[CLIENT-18]

| [[T-AUD-CONFUSION]]T-AUD-CONFUSION
| *Token replay / audience confusion.* A token issued for one audience is accepted where it
  should not be, or a forged/expired token is trusted.
| Validate every retrieved token through the validation pipeline — signature, `iss`, `aud`,
  `exp`, `iat` — before trust or storage; never take identity from an unvalidated token.
| https://www.rfc-editor.org/rfc/rfc9068[RFC 9068], https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation[OIDC Core §3.1.3.7]
| xref:requirements.adoc#CLIENT-15[CLIENT-15]

| [[T-IDTOKEN-INTEGRITY]]T-IDTOKEN-INTEGRITY
| *ID-token / userinfo integrity.* Identity is taken from an unvalidated ID token, or from a
  userinfo response whose `sub` does not match the ID token (identity confusion).
| Validate the ID-token signature and claims (`iss`/`aud`/`azp`/`exp`/`nonce`/`at_hash`);
  validate a signed userinfo response and bind its `sub` to the ID token's `sub`, rejecting
  mismatches. A `sub` that is not a JSON string is refused at validation (access and ID token)
  and in a plain-JSON userinfo response, so every `sub` binding compares JSON strings only and a
  numeric `sub` can never equal a string one by its text form.
| https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation[OIDC Core §3.1.3.7], https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse[OIDC Core §5.3.2]
| xref:requirements.adoc#CLIENT-16[CLIENT-16]

| [[T-CONSTRAINT-LOSS]]T-CONSTRAINT-LOSS
| *Sender-constraint loss in storage / forwarding.* A DPoP- or mTLS-bound token is stored or
  forwarded in a way that drops its binding, degrading it to a replayable bearer token.
| Keep the token associated with its proof-key / certificate binding across storage, refresh
  and forwarding; preserve the constraint on refresh; keep storage minimal.
| https://www.rfc-editor.org/rfc/rfc9449[RFC 9449], https://www.rfc-editor.org/rfc/rfc8705[RFC 8705]
| xref:requirements.adoc#CLIENT-18[CLIENT-18]

| [[T-REFRESH-IDENTITY]]T-REFRESH-IDENTITY
| *Substituted principal on refresh.* A refresh exchange returns an access token naming a
  different `sub` than the session was established for — through an authorization-server defect,
  a mis-scoped client, or a swapped refresh token — silently re-pointing a live session at
  another user. The authorization-code path already binds the session four ways (`state`,
  `nonce`, `at_hash`, `iss`); until this control the refresh path carried *no* identity binding
  at all, and that asymmetry was the gap.
| Bind the stored session to the `sub` of the validated access token (`StoredToken.subject`). On
  every refresh, the subject of the newly validated access token is compared against the bound
  subject in constant time; a mismatch *refuses the refresh fail-closed* — the atomic store
  transform writes nothing, so a refused refresh never becomes a partial write. Where the
  authorization server had *already rotated* the refresh token before the refusal, the presented
  token is burned server-side, so the session is *quarantined* rather than preserved: the
  server-issued successor is revoked best-effort (RFC 7009, only when the provider advertises a
  revocation endpoint, and the request may fail) and a clear of the store entry and rotation family
  is attempted, forcing re-authentication unless the clear spares a stored bundle with a different
  refresh token, typically a newer grant. Where the authorization server did not rotate, it named no
  successor: nothing is revoked, and the client keeps the presented token and its session. Where the authorization server also returns a
  refreshed ID token, it is validated and cross-checked for `iss`/`sub` consistency against the
  refreshed access token before it is carried forward. A refreshed ID token that fails pipeline
  validation, like one that is inconsistent, is refused on the same rotated-vs-not rule: revoking the
  rotated successor and a clear are attempted only when the authorization server rotated the
  refresh token, and otherwise nothing is revoked or cleared. The original refusal reaches the
  caller unchanged unless that cleanup throws an uncaught exception (from a revocation call or the
  store removal), which replaces it.
| https://openid.net/specs/openid-connect-core-1_0.html#RefreshTokenResponse[OIDC Core §12.2]
| xref:requirements.adoc#CLIENT-15[CLIENT-15], xref:requirements.adoc#CLIENT-17[CLIENT-17]

| [[T-REFRESH-REFUSAL]]T-REFRESH-REFUSAL
| *Wrong disposition of a refused refresh.* A refused refresh either destroys a working session
  over a fault that says nothing about the credential, or keeps a session whose credential the
  authorization server has declared dead or burned, or retries a request whose answer will not
  change.
| Classify every refusal raised inside the exchange through `RefreshFlow.classify` into one of four
  kinds and dispatch on it with a failing default arm
  (xref:../adr/0010-A_refresh_token_the_authorization_server_declares_invalid_is_a_third_classification_state.adoc[ADR-0010]).
  *Pre-redemption* (a connection failure, a `5xx`, an unrecognised `4xx`) keeps the session; the
  client keeps the presented token locally, but the server may already have rotated it after a
  connection failure or a `5xx`. A failed client authentication — `4xx` `invalid_client`, or exactly
  `401` `unauthorized_client` — is raised as `ClientAuthenticationFailedException` and is
  pre-redemption, so a misconfigured client secret cannot end a session
  (xref:../adr/0027-A_client_authentication_failure_at_the_token_endpoint_is_a_typed_pre-redemption_refusal.adoc[ADR-0027]).
  *Scope-refused* — a `4xx` naming exactly `invalid_scope`, raised as `InvalidScopeException` with
  a sanitised `error_description` — keeps the session, revokes and clears nothing, schedules no
  retry and logs no `WARN`. *Credential-rejected* (`4xx` `invalid_grant`) attempts a clear and
  revokes nothing. *Redeemed* quarantines when the presented token was burned. The quarantine on a
  rotated refresh covers every post-redemption refusal of the lifecycle manager: a freshly issued
  access token that fails client-side validation, a broader scope under
  `strictScopeReconciliation`, an unparseable success response (presumed rotated), a refreshed ID
  token that fails pipeline validation (`TokenValidationException`) or is inconsistent with the
  access token, and a refused identity or sender-constraint binding; the last three quarantine only
  when the server rotated the refresh token. Every typed refusal is recognised by an allow-list of
  exact shapes; any other code, any `5xx` and an absent, oversize, unparseable or duplicate-member
  body stay a plain `TransportException`, and no body text reaches an exception message unsanitised.
| https://www.rfc-editor.org/rfc/rfc6749#section-5.2[RFC 6749 §5.2], https://www.rfc-editor.org/rfc/rfc9700#section-4.14[RFC 9700 §4.14]
| xref:requirements.adoc#CLIENT-17[CLIENT-17]

| [[T-SCOPE-DRIFT]]T-SCOPE-DRIFT
| *Undetected granted-scope drift.* The authorization server grants a scope set other than the
  one requested — broader or narrower — and the client neither notices nor reports it, so a
  privilege delta reaches the application unremarked and undiagnosable after the fact.
| Reconcile the granted `scope` against the requested scope on every refresh and surface the
  outcome on `RotationResult` (`grantedScope`, `scopeDelta`); a broadened or narrowed grant is
  additionally `WARN`-logged. This is *anomaly reporting, not enforcement* — see the normative
  register below: a broadened grant is accepted by default and refused only under the opt-in
  `strictScopeReconciliation` posture.
| https://www.rfc-editor.org/rfc/rfc6749#section-3.3[RFC 6749 §3.3], https://www.rfc-editor.org/rfc/rfc6749#section-5.1[RFC 6749 §5.1]
| xref:requirements.adoc#CLIENT-17[CLIENT-17]
|===

[NOTE]
====
*The scope reconciliation is prudent hardening, not a mandated mitigation.* No published RFC
obliges an OAuth client to reject a grant broader than the one it requested.
https://www.rfc-editor.org/rfc/rfc6749#section-3.3[RFC 6749 §3.3] affirmatively *permits* the
authorization server to grant a scope other than the one requested, obliging it only to disclose
the result through the `scope` response parameter, and the *resource server* — not this client —
remains the enforcement point for an over-broad claim. `T-SCOPE-DRIFT` is therefore recorded as an
observability control: it makes a delta visible and actionable, and it does not claim a
specification violation on the authorization server's part.

The strict posture's only profile precedent is FAPI 1.0 Part 1 §5.2.3(10) — an
authorization-code-response rule that FAPI 2.0 dropped. That thin precedent is precisely why the
strict mode is opt-in rather than the default.
====

=== Residual risks

Both controls above leave a residual exposure, recorded here rather than implied away:

* *A session stored without a known subject is not bound.* `StoredToken.subject` is nullable: when
  a session is established before the principal is known, the first refresh has no bound subject to
  compare against and therefore adopts the refreshed subject instead of refusing. The binding takes
  effect from that point on. A deployment that stores sessions without a subject gets rotation and
  reuse detection but *not* `T-REFRESH-IDENTITY` coverage on the first refresh.
* *Strict scope reconciliation converts an authorization-server quirk into an authentication
  outage.* Several major authorization servers canonicalise or expand scope sets as a matter of
  course. Under `strictScopeReconciliation=true` every such response refuses the refresh with no
  attacker in the loop. The outage risk falls entirely on the deployment that opts in, which is why
  the lenient, reporting posture is the default.
* *Reconciliation is skipped when no scope was requested.* With an empty configured scope set there
  is no baseline to compare against, so every grant classifies as `UNDECLARED` and no delta is
  reported. Requesting an explicit scope is what makes the control effective.

== Adversarial test coverage

Each flow / token threat is exercised by the commons `generators` dispatchers in their
*adversarial* mode (xref:../commons/specification/transport.adoc#adversarial_dispatchers[commons
transport spec], `COMMONS-7`), driven by the client unit tests
(xref:requirements.adoc#CLIENT-22[CLIENT-22]). These adversarial dispatcher cases —
malformed metadata, oversized bodies, forged responses — stay in the unit layer; the
integration suite covers only threats reproducible against real providers:

[cols="1,3", options="header"]
|===
| Threat | Adversarial dispatcher behaviour driven by the client tests

| T-CODE-INJECTION / T-PKCE-DOWNGRADE | `TokenDispatcher` rejects/accepts codes against the presented `code_verifier`; missing-PKCE and `plain` requests refused.
| T-MIXUP | `WellKnownDispatcher` advertises a mismatched `issuer`; the `iss` response parameter is cross-checked before exchange.
| T-PARAM-INTEGRITY | `ParDispatcher` accepts the parameters `ParClient` pushes on the back channel and returns a `request_uri`; the returned `request_uri` is asserted to carry none of the pushed parameters, and an error response is refused.
| T-CSRF / T-REDIRECT | Callback handling asserts session-bound `state` and exact `redirect_uri`; crafted callbacks rejected.
| T-CLIENT-CRED | `TokenDispatcher` asserts the configured client-auth method; secret-in-URL and non-TLS attempts are not made.
| T-TOKEN-REPLAY / T-CONSTRAINT-LOSS | `TokenDispatcher` issues DPoP / mTLS-bound responses; the binding is preserved through storage/refresh. Under DPoP a `Bearer`-typed response and a JWT access token whose `cnf.jkt` is absent or differs from the proof-key thumbprint are rejected at issuance.
| T-LOGOUT | No dispatcher: the engine makes no end-session HTTP call. The tests assert the end-session redirect it builds (`id_token_hint`, exact `post_logout_redirect_uri`, `state`); revocation of held tokens is covered by the revocation and lifecycle tests.
| T-REFRESH-REFUSAL | The token-endpoint, refresh-flow, classification and lifecycle tests drive the typed error codes and non-matching error bodies (other codes, `5xx`, duplicate member, oversize, and for `invalid_scope` control characters in `error_description`) and assert the typed exception, the classification and the session disposition.
| T-REFRESH-THEFT | `TokenDispatcher` refresh mode drives rotation; a reused rotated token is refused as reuse and revocation of the replayed token and its successor is attempted.
| T-REFRESH-IDENTITY | `TokenDispatcher` refresh mode returns an access token carrying a substituted `sub`; the refresh is refused and, since the dispatcher has already rotated, the session asserted quarantined. A matched positive control — a refresh whose `sub` matches — is asserted to be accepted and to rotate the bundle, so deleting the guard turns a test red rather than merely leaving one green.
| T-SCOPE-DRIFT | `TokenDispatcher` refresh mode returns broadened, narrowed, equal and absent `scope` values; each is asserted to resolve to the matching `scopeDelta`, and the broadened case is asserted accepted-and-`WARN`-logged in the default posture and refused with `ClientProtocolException` under `strictScopeReconciliation`.
| T-IDTOKEN-INTEGRITY / T-AUD-CONFUSION | `TokenDispatcher` / `UserInfoDispatcher` emit tampered claims and `sub` mismatches; validation pipeline rejects; userinfo `sub` binding enforced.
| T-SSRF-ADVERTISED | The `de.cuioss.http.security` attack-database corpora are driven through the back-channel egress-path validation; traversal / injection / encoding-evasion advertised paths are refused before any fetch, and a non-TLS endpoint is refused per client. With a back-channel origin configured, a same-origin endpoint is asserted retargeted with path and query kept, a foreign-origin endpoint is asserted contacted unchanged, and a traversal path on a retargeted endpoint is still refused. `DiscoveryAdversarialTest` asserts that an `https` issuer's document advertising an `http://` endpoint is refused, one case per endpoint field, and that a discovery response with a `text/html`, `text/plain`, `application/jrd+json` or absent `Content-Type`, or with a second, conflicting `Content-Type` line in either order, is refused; all-`https` endpoints, `application/json; charset=UTF-8` and two `application/json` lines are the positive controls. A `302` from the discovery endpoint is refused as an unexpected status and its target is never contacted. `BackChannelEgressPolicyTest` maps the mock server onto a disallowed address for each endpoint kind (discovery, token, PAR, userinfo, revocation) and asserts it is never contacted, with the back-channel origin and the explicit opt-in cases. The header line-break attack class (CR, LF, CRLF, obs-fold, NUL) is driven through every response header the client reads for a security decision, and the token, PAR and userinfo `Content-Type` and quoted `expires_in` cases are refused.
|===

== [[_out_of_scope_delegated]] Out of scope (delegated)

* *Transport threats* — TLS downgrade / MITM on any fetch belongs to the
  xref:../commons/threat-model.adoc[commons threat model] (`T-TLS`); the flow *inherits* the
  `cui-http` TLS primitive and does not restate it (`T-TLS-TOKEN` above records that reliance).
  *SSRF / egress on advertised back-channel URLs is not delegated* — the engine owns its path,
  scheme and host-address egress control and size-bounded reads on its own fetches
  (xref:#T-SSRF-ADVERTISED[]); only the egress and response-DoS controls of the *validation
  pipeline's own JWKS retrieval* stay commons / validation concerns (`T-SSRF`, `T-DOS`,
  `T-DISCOVERY`).
* *Token-trust threats* — forged signatures, `alg` confusion, claim tampering, expiry / replay
  at validation time — belong to the xref:../validation/threat-model.adoc[validation threat
  model]. The client retrieves tokens; validation decides their trust (`CLIENT-15`).
* *Error-detail leakage* at the HTTP edge — the RFC 9457 no-leak control — is the commons
  `T-LEAK` threat (`COMMONS-12`); the client engine only throws typed exceptions
  (`CLIENT-20`).
* *BFF application concerns* — the browser↔backend session cookie, symmetric-key management,
  backend-API CSRF, request proxying, and front-/back-channel logout *receivers* — are the
  BFF application's threat surface, not this engine's (`CLIENT-19`).
