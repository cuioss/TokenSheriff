== OAuth 2.1 Compatibility

Token-Sheriff is a **resource server token validation library**. It validates JWT tokens passed as strings and does not handle authorization flows, token issuance, redirect URIs, or HTTP transport of incoming tokens. When configured with HTTP JWKS or discovery endpoints, it fetches keys and discovery documents over HTTP.

The major changes in https://datatracker.ietf.org/doc/html/draft-ietf-oauth-v2-1[OAuth 2.1] (mandatory PKCE, removal of implicit and ROPC grants, exact redirect URI matching, refresh token rotation) target **authorization servers and clients**, not resource servers. **Tokens issued by OAuth 2.1 compliant servers validate correctly with Token-Sheriff as-is** when they are signed with an algorithm Token-Sheriff supports and satisfy its other validation requirements, since OAuth 2.1 does not change the JWT structure or introduce new mandatory claims for access tokens. Symmetric (HMAC) signatures such as HS256, which OAuth 2.1 does not forbid, are rejected, because the library processes asymmetric key material only.

Token-Sheriff already satisfies the OAuth 2.1 resource server requirements:

* **Scope enforcement** - `scope` claim accessible via `AccessTokenContent.getScopes()` for application-level validation; enforced declaratively via Quarkus `@BearerAuth`
* **Audience validation** - Supported via `expected-audience` configuration; mandatory for ID tokens
* **Token expiration check** - `exp` mandatory, with configurable clock skew tolerance
* **Algorithm security** - Whitelisted RS/ES/PS/EdDSA families only; HMAC and "none" rejected per https://datatracker.ietf.org/doc/html/rfc8725[RFC 8725]
* **Issuer validation** - `iss` mandatory, matched against configured issuers
* **Signature verification** - Full cryptographic validation pipeline
* **RFC 9068 token type validation** - Optional per-issuer `typ: at+jwt` header validation (see xref:#VALIDATION-8.6[VALIDATION-8.6])
* **RFC 9449 DPoP sender-constrained tokens** - Optional per-issuer DPoP proof validation binding access tokens to client public keys (see xref:#VALIDATION-8.7[VALIDATION-8.7])

NOTE: Requirement IDs are stable identifiers referenced across documentation and are not sequential. Functional requirements use IDs 1-8, 12 and 13; non-functional requirements use IDs 9-10.

[#VALIDATION-1.3]
==== VALIDATION-1.3: Signature Validation

The library must validate token signatures using cryptographic algorithms as specified in https://datatracker.ietf.org/doc/html/rfc7518[RFC 7518 - JSON Web Algorithms (JWA)].

For security reasons, only the following signature algorithms shall be supported (in accordance with https://datatracker.ietf.org/doc/html/rfc8725[RFC 8725 - JSON Web Token Best Current Practices] (February 2020) and https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-131Ar2.pdf[NIST SP 800-131A] (March 2019)):

* ES512 (ECDSA using P-521 and SHA-512)
* ES384 (ECDSA using P-384 and SHA-384)
* ES256 (ECDSA using P-256 and SHA-256)
* EdDSA (Edwards-curve Digital Signature Algorithm using Ed25519/Ed448)
* PS512 (RSASSA-PSS using SHA-512 and MGF1 with SHA-512)
* PS384 (RSASSA-PSS using SHA-384 and MGF1 with SHA-384)
* PS256 (RSASSA-PSS using SHA-256 and MGF1 with SHA-256)
* RS512 (RSASSA-PKCS1-v1_5 with SHA-512)
* RS384 (RSASSA-PKCS1-v1_5 with SHA-384)
* RS256 (RSASSA-PKCS1-v1_5 with SHA-256)

NOTE: ECDSA, EdDSA, and RSASSA-PSS algorithms are preferred over RSASSA-PKCS1-v1_5 (RS*). While RS* algorithms remain supported for broad interoperability, RSASSA-PSS (PS*) is recommended by https://www.rfc-editor.org/rfc/rfc8017.html#section-8[RFC 8017] (2016) as the successor scheme. EdDSA (Ed25519) is listed as a supported algorithm in the https://openid.net/specs/fapi-2_0-security-profile.html[FAPI 2.0 Security Profile] and is defined in https://datatracker.ietf.org/doc/html/rfc8037[RFC 8037 - CFRG Elliptic Curve Signatures in JOSE]. The default algorithm catalog is `JwsAlgorithm`; its declaration order is informational only: acceptance is by membership in the supported set, and the token's own header names the algorithm.

The following algorithms shall NOT be supported due to security concerns:

* HS256, HS384, HS512 (HMAC with SHA-2) - Vulnerable to https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/[key confusion attacks] (2015) when used in combination with RSA public keys
* "none" algorithm - Explicitly forbidden by https://datatracker.ietf.org/doc/html/rfc8725#section-3.1[RFC 8725 Section 3.1 - Perform Algorithm Verification] and https://cwe.mitre.org/data/definitions/347.html[CWE-347: Improper Verification of Cryptographic Signature]
* RSA based algorithms with keys shorter than 2048 bits - Not compliant with https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-131Ar2.pdf[NIST SP 800-131A] (2019)

Additional security considerations:

* The library must implement https://datatracker.ietf.org/doc/html/rfc8725#section-3.1[algorithm verification] to prevent algorithm substitution attacks (CVE-2015-9235)
* The library must validate that the algorithm specified in the JWT header matches the expected algorithm for the key
* The library must reject tokens with invalid signatures rather than falling back to less secure validation methods

_See specifications: xref:architecture.adoc#token-validation-pipeline[Token Validation Pipeline] and xref:security-reference.adoc#signature-validation[Signature Validation]_

[#VALIDATION-1.4]
==== VALIDATION-1.4: Token Decryption

The library supports decryption of encrypted JWT tokens (JWE) as defined in https://datatracker.ietf.org/doc/html/rfc7516[RFC 7516 - JSON Web Encryption (JWE)] (May 2015). JWE decryption is transparent — the pipeline detects 5-part JWE tokens, decrypts them using locally-configured private keys, and validates the inner JWS through the existing pipeline unchanged.

Supported key management algorithms: RSA-OAEP, RSA-OAEP-256, ECDH-ES. Supported content encryption algorithms: A128GCM, A256GCM, A128CBC-HS256, A256CBC-HS512. RSA1_5 is explicitly rejected due to Bleichenbacher's padding oracle attack.

_See specification: xref:specification/token-decryption.adoc[Token Decryption]_

[#VALIDATION-3.1]
==== VALIDATION-3.1: Issuer Configuration

Support configuration of multiple token issuers with different validation parameters.

An explicit `issuer-identifier` is the default and recommended form for every issuer, also together with `well-known-url`.

[NOTE]
====
Enforcement: issuer configuration (`IssuerConfig`) and the Quarkus `IssuerConfigResolver` require an explicit `issuer-identifier` for every enabled issuer. The configured identifier stays authoritative.

For an enabled `IssuerConfig` that loads its keys through `well-known-url` discovery, the following guarantees hold:

* The configured `issuer-identifier` is always compared with the `issuer` advertised by the OpenID Connect discovery document.
* A mismatch is a hard failure: no keys are loaded, the `ISSUER_MISMATCH` security event is counted, the `jwks_uri` of the discovery document is never fetched, and every token for that issuer is rejected.
* A discovery document that advertises a `jwks_uri` but no `issuer` is a terminal rejection as well: no keys are loaded, the `ISSUER_MISMATCH` security event is counted once, the `jwks_uri` of the discovery document is never fetched, and every token for that issuer is rejected. A document missing both `issuer` and `jwks_uri` is an unusable response and stays retryable.
* The identifier is configured once, on `IssuerConfig`. It need not be repeated on `HttpJwksLoaderConfig`: `IssuerConfig` propagates it into the loader configuration when it is built.
* An identifier set on `HttpJwksLoaderConfig` that differs from the `IssuerConfig` identifier is a build error: building the `IssuerConfig` fails instead of choosing one of the two values.
* A pre-built loader of type `WELL_KNOWN` passed via `jwksLoader(...)` must carry the same identifier as the `IssuerConfig`; a missing or differing identifier is a build error.

Standalone use of `HttpJwksLoaderConfig` and `HttpJwksLoader` without `IssuerConfig` stays supported. In that case the identifier may be omitted for well-known discovery, and no comparison with the advertised issuer takes place.
====

_See specification: xref:architecture.adoc#multi-issuer[Multi-Issuer Support]_

[#VALIDATION-4.5]
==== VALIDATION-4.5: Key Rotation Grace Period

The library must support a configurable grace period for retired keys during key rotation to ensure uninterrupted service during the transition period, as recommended by general key management best practices.

Key requirements:

* Retain retired keys for a configurable grace period (default: 5 minutes)
* Support immediate key invalidation with zero grace period configuration
* Automatically clean up expired keys beyond the grace period
* Limit the number of retained retired key sets to prevent unbounded memory growth
* Prevent unnecessary key rotation when JWKS content has not changed

This ensures that tokens signed with recently rotated keys remain valid during the transition period, preventing service disruptions for in-flight requests.

_See specification: xref:architecture.adoc#jwks-integration[JwksLoader]_

[#VALIDATION-4.6]
==== VALIDATION-4.6: Unknown Key ID Refresh

The library must support an opt-in, bounded refresh of an HTTP-loaded key set when a token names a key ID (`kid`) that is in neither the installed nor a retired key set. This shortens the time until a key rotated at the identity provider is accepted, without making the token path depend on the JWKS endpoint.

Key requirements:

* Off by default: without the setting, an unknown `kid` never causes a fetch, and a rotated key is picked up only by the periodic refresh
* The window is configured per loader, that is per issuer, from 5 to 3600 seconds inclusive, with no default value
* At most one fetch per window and per loader, whatever the request rate and the number of distinct `kid` values presented
* The key lookup performs no I/O and never waits: it only schedules the fetch on the loader's background refresh executor, and the triggering token is still rejected
* The fetched key set is installed only if it holds the triggering `kid`; installation uses the same commit step, grace period and retired-set bound as the periodic refresh (xref:#VALIDATION-4.5[VALIDATION-4.5])
* A failed fetch, or one whose key set lacks the triggering `kid`, changes nothing: keys, retired key sets, status, endpoint and the time of the last successful load stay unchanged, and the outcome is not counted as a failed refresh cycle
* The setting cannot be combined with a disabled background refresh (refresh interval 0)

The trade-off is documented: an attacker presenting an invented `kid` consumes the window. An attacker who does so in every window defers the on-demand pickup of a legitimate rotation entirely, because the fetched key set is installed only if it holds the attacker's invented `kid`; such a rotation is then picked up by the periodic refresh only. The window limits how often a fetch is claimed; it is not a deadline by which a rotation is picked up.

_See specifications: xref:architecture.adoc#jwks-integration[JwksLoader], xref:threat-model.adoc[Threat Model] and xref:../adr/0030-An_opt-in_unknown-kid_refresh_claims_one_window_per_loader_and_installs_only_a_key_set_holding_the_kid.adoc[ADR-0030]_

[#VALIDATION-4.7]
==== VALIDATION-4.7: Initial Load Retry

The library must support an opt-in, backed-off retry of a failed initial JWKS load, so that an issuer whose identity provider was unreachable at startup becomes usable sooner than one refresh interval later.

Key requirements:

* Off by default: without the setting, a failed initial load is retried only by the periodic refresh
* A single on/off setting with fixed delays: the first retry after 1 second, the delay doubling up to 30 seconds and never above the refresh interval
* Retries are strictly sequential and never overlap the periodic refresh or an unknown key ID refresh (xref:#VALIDATION-4.6[VALIDATION-4.6])
* Retries stop at the first installed key set, at a terminal error and when the loader is closed
* The loader status never reports `LOADING` during retries and reports `OK` only once keys are installed
* The enabled setting cannot be combined with a disabled background refresh (refresh interval 0); the disabled setting can

_See specifications: xref:architecture.adoc#jwks-integration[JwksLoader] and xref:../adr/0030-An_opt-in_unknown-kid_refresh_claims_one_window_per_loader_and_installs_only_a_key_set_holding_the_kid.adoc[ADR-0030]_

[#VALIDATION-8.6]
==== VALIDATION-8.6: Token Type Header Validation (RFC 9068)

The library must support optional per-issuer validation of the JWT `typ` header parameter as defined in https://datatracker.ietf.org/doc/html/rfc9068[RFC 9068 - JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens] (October 2021).

* When `expected-token-type` is configured for an issuer, tokens with a missing or mismatched `typ` header are rejected
* When not configured (default), no token type validation is performed
* Comparison is case-insensitive per RFC convention
* Validation occurs in the `TokenHeaderValidator` as part of the header validation pipeline step

_See specification: xref:architecture.adoc#token-validation-pipeline[Token Validation Pipeline]_

[#VALIDATION-8.7]
==== VALIDATION-8.7: DPoP Sender-Constrained Tokens (RFC 9449)

The library must support optional per-issuer validation of DPoP (Demonstrating Proof of Possession) sender-constrained tokens as defined in https://datatracker.ietf.org/doc/html/rfc9449[RFC 9449 - OAuth 2.0 Demonstrating Proof of Possession (DPoP)] (September 2023).

* When `dpop.enabled=true` for an issuer, tokens with a `cnf.jkt` claim are validated against the DPoP proof JWT from the `DPoP` HTTP header
* When `dpop.required=true`, tokens without a `cnf.jkt` claim are rejected
* When `dpop.required=false` (default), tokens without a `cnf.jkt` claim pass normally (bearer mode)
* DPoP validation includes: JWT format and signature verification, JWK Thumbprint (https://datatracker.ietf.org/doc/html/rfc7638[RFC 7638]) binding against `cnf.jkt`, access token hash (`ath`) verification, `iat` freshness check, and `jti` replay prevention
* Only asymmetric algorithms are permitted in DPoP proofs (HMAC and "none" are rejected)

_See specification: xref:architecture.adoc#token-validation-pipeline[Token Validation Pipeline]_

[#VALIDATION-13]
=== VALIDATION-13: Public Validation Seams and Back-Channel Logout

The library must offer consumers the narrow entries they need to build on token validation without reaching into its internals, and must validate the logout tokens of https://openid.net/specs/openid-connect-backchannel-1_0.html[OpenID Connect Back-Channel Logout 1.0] (September 2022).

_See specifications: xref:architecture.adoc#token-validator-seams[TokenValidator Public Seams], xref:architecture.adoc#logout-package[Logout Token Validation] and xref:../adr/0029-TokenValidator_publishes_signature-only_verification_native_JSON_claims_and_a_non-fetching_issuer_status_view.adoc[ADR-0029]_

[#VALIDATION-13.1]
==== VALIDATION-13.1: Signature-Only Verification

`TokenValidator` must offer a signature-only entry, `verifySignature(String)`, that applies the token string limits, resolves an enabled issuer whose JWKS loader is healthy, runs the header checks for algorithm, key ID and embedded JWK, verifies the signature and maps the claims, and reaches no claim verdict.

* The result, `SignatureVerifiedToken`, is not a `TokenContent`, so it cannot reach code that accepts a validated token
* The issuer's expected token type is not checked; the `typ` header is returned verbatim for the caller to judge
* The access-token cache is neither read nor written
* A success counts the `SIGNATURE_ONLY_VERIFIED` security event; a refusal counts the event of the stage that refused it

_See specification: xref:security-reference.adoc#signature-only-verification[Signature-Only Verification]_

[#VALIDATION-13.2]
==== VALIDATION-13.2: Native JSON Claims

The library must return the payload of a validated token, through `TokenValidator.getRawClaims(TokenContent)`, and of a signature-verified token, through `SignatureVerifiedToken.getRawClaims()`, as a native JSON map.

* The payload is decoded with the validator's own parser, so the `ParserConfig` size, depth, array and string bounds apply; a payload the parser refuses is refused as a whole
* JSON objects are unmodifiable maps in member order, JSON arrays unmodifiable lists in element order, and numbers, booleans and strings keep their JSON type
* A `null` nested inside an object or array is kept; a top-level `null` member is omitted, and for a signature-verified token it is named by `SignatureVerifiedToken.getNullClaimNames()`
* For a JWE, the payload of the inner, decrypted token is returned

_See specification: xref:architecture.adoc#token-validator-seams[TokenValidator Public Seams]_

[#VALIDATION-13.3]
==== VALIDATION-13.3: Issuer Status View

`TokenValidator.getIssuerStatuses()` must return an immutable list with one `IssuerStatusView` per enabled issuer, in configuration order.

* Each view names the issuer and its JWKS type and reads the current loader status on every call
* Reading the status fetches no keys
* The view exposes neither the issuer configuration nor the JWKS loader, so no caller can close, refresh or replace a loader through it; the loaders are closed only by `TokenValidator.close()`
* Disabled issuers are not listed

_See specification: xref:architecture.adoc#token-validator-seams[TokenValidator Public Seams]_

[#VALIDATION-13.4]
==== VALIDATION-13.4: Logout Token Validation

The library must validate a logout token of https://openid.net/specs/openid-connect-backchannel-1_0.html[OpenID Connect Back-Channel Logout 1.0] with every check of sections 2.4 and 2.6 of that specification, run in this fixed order:

. The signature, through the signature-only entry of xref:#VALIDATION-13.1[VALIDATION-13.1]
. A present `typ` header is `logout+jwt` or `application/logout+jwt`, compared case-insensitively; an absent `typ` is accepted
. `iss` equals the expected issuer
. `aud`, a string or an array, contains the expected audience
. `iat` is a number within the freshness window around now
. `exp` is a number after now; an `exp` exactly now is refused (RFC 7519 §4.1.4)
. `events` is a JSON object whose `http://schemas.openid.net/event/backchannel-logout` member is a JSON object
. `nonce` is absent, not even present as a JSON `null`
. `sub` and/or `sid` is present, and each of them that is present is a non-blank string
. `jti` is present as a non-blank string
. The `jti` passes the replay guard of xref:#VALIDATION-13.5[VALIDATION-13.5]

A claim the signature-only entry cannot map refuses the token at the first step: a present `iat` or `exp` that is not a number is refused as `ISSUED_AT` or `EXPIRATION`, any other unmappable claim - a `sub` that is a JSON number, boolean, array or object among them - as `SIGNATURE`.

A refusal names exactly one `LogoutTokenCheck`, the first check that failed. The set of checks is bounded and the result carries no text taken from the token. The validator does not log; receiving the logout request over HTTP and ending the named session stay with the consuming application.

_See specification: xref:security-reference.adoc#logout-token-validation[Logout Token Validation]_

[#VALIDATION-13.5]
==== VALIDATION-13.5: Logout Token Replay Guard

The library must refuse a logout token whose `jti` was already admitted, through a replay guard that is:

* *Bounded* - it holds at most a configured number of live entries
* *Fail closed* - at capacity, a new `jti` is refused as `REPLAY_GUARD_FULL`; a live entry is never evicted to make room
* *Digest-only* - each `jti` is kept as its SHA-256 digest, until `iat` plus the freshness window
* *Thread-safe* - one admission is a single critical section, so no two threads admit the same `jti` or take the last free entry
* *Owned by the validator* - the logout-token validator builds its guard from the configured capacity; no caller supplies a guard
* *Decided on one instant* - the guard reads no clock; the validator reads its clock once per token and passes that instant to the guard, so expired entries are purged on exactly the instant `iat` freshness was judged on, and two clock reads cannot straddle the `iat` plus window edge and admit a replay; the clock read, the claim checks and the admission of one token are one critical section, so concurrent validations cannot purge an entry an earlier reading is still deciding against

The guard is consulted last, so a token refused by any other check takes no guard capacity.

_See specification: xref:security-reference.adoc#logout-replay-guard[Logout Replay Guard]_
