== Overview

_See Requirement xref:requirements.adoc#VALIDATION-8[VALIDATION-8: Security Requirements] and xref:architecture.adoc[Architecture] and xref:security-reference.adoc[Security Reference] and xref:cve-lessons-register.adoc[CVE Lessons Register]_

This document outlines the threat model for the JWT Token Validation library. The threat model follows OWASP recommendations and the STRIDE methodology. Each category lists threats, current mitigations with implementation references, coverage status, and open recommendations.

== System Context

The JWT Token Validation library:

* Processes JWT tokens from OAuth2/OpenID Connect providers
* Validates token signatures using JWKS (JSON Web Key Sets)
* Extracts and processes token claims
* Handles multiple token types (Access, ID, Refresh)
* Supports multiple issuers with per-issuer configuration
* Implements key management and rotation
* Supports DPoP sender-constrained tokens (RFC 9449)
* Offers a signature-only verification entry, native JSON claims and a read-only issuer status view
* Validates logout tokens of OpenID Connect Back-Channel Logout 1.0 with a bounded replay guard

==== Open Recommendations

* Revocation checks for tokens revoked before they expire (a deny list of revoked token identifiers); the library has none built in. A custom `TokenValidationRule` is the extension point for an access-token check, because rules run in the access-token pipeline only; an application that needs ID-token revocation must check it separately
* Rate limiting for token validation attempts
* JWK thumbprint validation for JWKS endpoints

==== Open Recommendations

* Certificate pinning for JWKS endpoints
* Constant-time comparison for security-critical comparisons
* JWE decryption timing side channel: VTEST-14 proves *exception-path* indistinguishability across
  wrong-key / bad-ciphertext / bad-tag failures, but true *timing* indistinguishability for the
  permitted RSA-OAEP paths is not asserted by a test (mitigated in principle by rejecting `RSA1_5`).

==== Open Recommendations

* Role hierarchy validation
* Mandatory audience validation for client applications
* Warning when mutable claims (e.g., `email`) used for identification
* Both audience/authorized-party fallbacks now default to secure-by-default: `azpAudienceFallbackEnabled`
  (`azp`→`aud`) and `clientIdFallbackEnabled` (RFC 9068 `client_id`→`azp`) default to `false`, so a
  matching client-identity claim is never accepted as a substitute for a missing recipient claim
  (wired via VTEST-12 and VTEST-15; see the xref:cve-lessons-register.adoc[CVE Lessons Register]).

|PS1
|Misuse of a signature-only result as an authentication decision
|`TokenValidator.verifySignature` returns a link:../../token-sheriff-validation/src/main/java/de/cuioss/sheriff/token/validation/domain/token/SignatureVerifiedToken.java[SignatureVerifiedToken] that implements neither `TokenContent` nor `MinimalTokenContent`, so it cannot reach code that accepts a validated token and is never cached; the missing claim verdict and the unchecked `typ` are stated once in xref:security-reference.adoc#signature-only-verification[Signature-Only Verification]. |Issuer disclosure through the JWKS readiness probe
|An external validator's issuers are reported only with the opt-in `sheriff.token.health.jwks.report-external-validator=true` (default `false`); `sheriff.token.health.jwks.disclose-issuer=false` omits their `issuer.N.url`. |PS3
|Logout-token replay
|The `jti` of each admitted logout token is kept as a SHA-256 digest in link:../../token-sheriff-validation/src/main/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenReplayGuard.java[LogoutTokenReplayGuard] until `iat` plus the freshness window; a retained `jti` is refused as `REPLAYED`, and a token past that instant is refused by the `iat` check
|link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenValidatorTest.java[LogoutTokenValidatorTest], link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenReplayGuardTest.java[LogoutTokenReplayGuardTest]

|PS4
|Forged or cross-type logout token (for example an ID token presented as a logout token)
|link:../../token-sheriff-validation/src/main/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenValidator.java[LogoutTokenValidator] verifies the signature through the signature-only entry, refuses a present `typ` other than `logout+jwt`, requires an `events` object with the back-channel logout member and refuses a present `nonce`, so an ID token is refused even when `typ` is absent; see xref:security-reference.adoc#logout-token-validation[Logout Token Validation]

|PS5
|Replay-guard exhaustion

|link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenReplayGuardTest.java[LogoutTokenReplayGuardTest], link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenValidatorTest.java[LogoutTokenValidatorTest]

==== Open Recommendations

* Alert on `REPLAY_GUARD_FULL` refusals, which signal either an undersized guard or a flood of logout tokens
* The HTTP receiver endpoint for back-channel logout requests is the consuming application's concern and needs its own request-size and rate limits

[IMPORTANT]
.Wired-test rule for coverage
====
A threat may only be marked *Test Covered* (and never 100% for a category) unless it is backed by a *wired negative-path test* — a test that drives the crafted attack through the real `TokenValidator` entry point and asserts the specific rejection event, rather than a unit test that exercises a validator in isolation or a counter assertion that is trivially true.

The 100%-covered cells above are backed by the wired negative-path attack tiers added in this remediation:

* link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/security/WiredNegativePathAttackTest.java[WiredNegativePathAttackTest] — HMAC/RSA algorithm confusion (Spoofing/EoP), JWE decompression bomb (Denial of Service), cross-issuer key substitution (Tampering), unsupported JWE key-management algorithm, DPoP sender-binding violations (DPoP), and embedded-JWK header injection (Spoofing/EoP). Extended with the CVE-derived tier VTEST-10..16 (see xref:cve-lessons-register.adoc[CVE Lessons Register]): `alg` case-variant of "none" (Spoofing), over-depth JSON payload (Denial of Service), cross-audience token rejection (EoP), JWE header algorithm downgrade (Tampering), RSA-OAEP decryption-failure indistinguishability (Information Disclosure), `client_id`→`azp` fallback rejection (EoP), and an all-zero ES256 DPoP proof signature rejected at the ECDSA range check (Spoofing/Tampering, CVE-2022-21449 class).
* link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/security/PsychicSignatureAttackTest.java[PsychicSignatureAttackTest] — zero-value ECDSA psychic-signature bypass (Tampering).
* link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/TokenValidatorVerifySignatureAttackTest.java[TokenValidatorVerifySignatureAttackTest] and link:../../token-sheriff-validation/src/test/java/de/cuioss/sheriff/token/validation/logout/LogoutTokenValidatorTest.java[LogoutTokenValidatorTest] — crafted tokens driven through a real `TokenValidator` into the signature-only entry and the logout-token validator (Public Seams and Back-Channel Logout).

Any future threat marked covered without a corresponding wired negative-path test violates this rule and must be treated as an uncovered threat.
