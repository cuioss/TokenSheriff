== Overview

_See Requirement xref:requirements.adoc#VALIDATION-8[VALIDATION-8: Security]_

This document consolidates JWT attack mitigations, security controls, and best practices for the Token-Sheriff library. For the mapping of these controls against concrete real-world CVEs in other OAuth/OIDC/JWT/JOSE libraries, see the xref:cve-lessons-register.adoc[CVE Lessons Register].

[[security-controls]]
== Security Controls

[[signature-validation]]
=== Signature Validation

_See Requirement xref:requirements.adoc#VALIDATION-1.3[VALIDATION-1.3: Signature Validation]_

Supported algorithms (acceptance is by membership in the supported set only; the listing order below is not a selection order, because the token's own header names the algorithm and the validator never chooses between them):

* ES512, ES384, ES256 (ECDSA)
* EdDSA (Ed25519/Ed448)
* PS512, PS384, PS256 (RSA-PSS)
* RS512, RS384, RS256 (RSA PKCS#1 v1.5)

**Rejected**: HS256/384/512 (HMAC), "none" - per RFC 8725.

[[claims-validation]]
=== Claims Validation

An explicit JSON `null` for a claim is read exactly as an omitted member, on access, ID and refresh tokens alike: the member is dropped when the payload is parsed, so no later step can tell the two apart. This equivalence holds for top-level payload members only: `MapRepresentation.fromJson` filters `null` values out of the top-level object, but a `null` nested inside an object or an array (for example inside `cnf` or a `roles` array) is kept as parsed. For access and ID tokens, a `null` `sub` and a `null` `iss` therefore stay refused exactly as an absent one: `sub` by the mandatory-claims check, which honours `claimSubOptional`, and `iss` during issuer extraction, before issuer configuration lookup. Refresh tokens do not undergo these claim checks. An absent claim behaves as described per claim below.

* **iss** (issuer) - validated by `IssuerConfigCache` during issuer resolution. A non-string `iss` is already rejected, because issuer resolution reads it as a JSON string only.
* **sub** (subject) - mandatory by default (RFC 7519 §4.1.2), validated by `TokenClaimValidator`; may be made optional per issuer via `IssuerConfig.claimSubOptional(true)`. A present `sub` must be a JSON string: a number, boolean, object or array is refused as a counted `MISSING_CLAIM` rejection when an access or ID token is built, so it is never stringified. No comparison against a configured value reads `sub`. The client's `sub` binding between the access token and the ID token compares the values the validator supplies, which are the mapped claim values: with the default mapper these are the two JSON strings, compared for exact equality, and both tokens are signature-verified. An issuer-configured subject mapper that rewrites `sub` changes what is compared, so a subject mapper must preserve the original `sub` value if the binding is to remain an exact subject binding.
* **exp** (expiration) - mandatory, with configurable clock skew
* **iat** (issued at) - validated against `maxTokenAgeSeconds` when configured on the issuer (a token is rejected when `now - iat > maxTokenAgeSeconds + clockSkewSeconds`); when `maxTokenAgeSeconds` is unset it is extracted into token content without an age check
* **nbf** (not before) - validated if present
* **aud** (audience) - validated when `expectedAudience` is configured
** An absent `aud` claim is the only case treated as missing. It follows the azp fallback (`IssuerConfig.azpAudienceFallbackEnabled`) and, for access tokens, `IssuerConfig.accessTokenAudienceOptional`; an ID token without `aud` and without a matching fallback is rejected as a missing claim.
** A present `aud` claim, including an empty JSON array, must contain at least one expected audience. Otherwise the token is rejected as an audience mismatch, for ID and access tokens alike.
** An empty `aud` array is never eligible for the azp fallback.
** `accessTokenAudienceOptional(true)` does not accept `aud: []`. The option covers an identity provider that omits `aud`, not one that sends an empty array.
* **azp** (authorized party) - validated when `expectedClientId` is configured
** With the default mapper, a present `azp` must be a JSON string. An array, number, boolean or object is rejected when the token is built, before any validator runs, so a non-string `azp` never satisfies the authorized-party check or the audience fallback, even when its text form equals a configured client id or audience.
** With the default mapper, `client_id`, the RFC 9068 fallback for an absent `azp`, must be a JSON string when present. An array, number, boolean or object is rejected when the token is built, before any validator runs, including when a valid `azp` is present, so a non-string `client_id` never satisfies the authorized-party check, even when its text form equals a configured client id.
** This type guarantee for `azp` and `client_id` is default-mapper behaviour. An issuer-configured `IdentityMapper` for either claim stringifies a numeric value, so a number whose text form equals a configured client id would then satisfy the check. Only `sub` additionally has its raw JSON type enforced before a custom mapper runs (`TokenBuilder`).
* **jti** (JWT ID) - accessible via generic claim access on the token content; the library exposes no typed accessor for it. No comparison reads `jti`.

[[secure-communication]]
=== Secure Communication

JWKS and well-known endpoint communication requires HTTPS by default, with TLS 1.2+ enforced via `SecureSSLContextProvider` (from cui-http) and a configurable minimum TLS version; a cleartext `http://` URL is rejected. An operator can opt in to cleartext per issuer with `allowInsecureHttp(true)` on `HttpJwksLoaderConfig` and `WellKnownConfig`, or `sheriff.token.issuers.<name>.jwks.http.allow-insecure-http=true` in the Quarkus extension. With that opt-in, a discovery or JWKS endpoint with an `http://` URL is fetched without TLS, so its key material and discovery document are open to interception and tampering; the TLS settings still apply to every endpoint of that issuer that uses `https://`. The opt-in is intended for local development and integration tests, never production.

TLS hostname verification is enforced by default and can be relaxed per issuer via `sheriff.token.issuers.<name>.jwks.http.verify-hostname=false`, which narrows hostname matching only — chain trust, expiry and algorithm constraints remain enforced — is scoped to that issuer's JWKS and well-known fetches, and is intended for SAN-mismatched development certificates, never production (see xref:../adr/0008-Adopt_the_upstream_cui-http_verifyHostname_knob_rather_than_a_local_trust_manager.adoc[ADR-0008]).

[[safe-parsing]]
=== Safe Parsing

`NonValidatingJwtParser` enforces the `ParserConfig` limits. The values below are the defaults; every limit is configurable on `ParserConfig`, which is the source of truth for them: token size 8 KB (`maxTokenSize`, for a JWS and the inner JWS after decryption; with JWE decryption configured a 5-part JWE is bounded by `JweDecryptionConfig.maxEncryptedTokenSize`, at most 32 KB), each decoded header / payload part 8 KB (`maxPayloadSize`), string length 4 KB (`maxStringLength`), JSON nesting depth 10 (`maxNestingDepth`) and array size 1000 (`maxArraySize`). Protects against memory exhaustion and malformed input attacks. JWKS and well-known discovery HTTP response bodies have a separate default ceiling of 256 KB (`maxHttpResponseSize`), also configurable and enforced while the body streams.

A member name duplicated in a JWT header or payload is not rejected as a duplicate: the last occurrence wins. The header is deserialized by DSL-JSON into `JwtHeader` and the payload into a `Map` by `MapRepresentation.fromJson`, both of which keep the last value read. The header is a typed record, so an earlier occurrence whose JSON type does not match the declared field type fails deserialization before the later occurrence is read: a numeric `alg` ahead of a string `alg` is rejected, while two string `alg` members resolve to the last (both pinned by `NonValidatingJwtParserTest`); "last occurrence wins" therefore holds for occurrences of the declared type. A member whose last occurrence is JSON `null` is treated as absent.

[[signature-only-verification]]
=== Signature-Only Verification

_See Requirement xref:requirements.adoc#VALIDATION-13.1[VALIDATION-13.1: Signature-Only Verification]_

WARNING: `TokenValidator.verifySignature(String)` reaches *no claim verdict*. Its `SignatureVerifiedToken` is not an authentication decision. It establishes only that the token is within the token string limits, was signed by a key of an enabled issuer whose JWKS loader is healthy, and passes the header checks for algorithm, key ID and embedded JWK. The token may be expired, issued for another audience, lack `sub` or `azp`, or be of any token type. The issuer's configured expected token type is *not* checked: the `typ` header is returned verbatim, and judging it is the caller's job.

A caller of the signature-only entry must therefore check every claim it relies on itself, or use `createAccessToken` / `createIdToken` when it needs an access or ID token verdict. `SignatureVerifiedToken` implements neither `TokenContent` nor `MinimalTokenContent`, so a signature-only result cannot be passed to code that accepts a validated token, and it is never cached. The logout-token validator below is the library's own consumer of this entry: it checks every claim of a logout token on top of it.

The native JSON claims (`SignatureVerifiedToken.getRawClaims()`, `TokenValidator.getRawClaims(TokenContent)`) follow the null handling described under <<claims-validation>> unchanged: a top-level `null` member is omitted, a `null` nested inside an object or array is kept.

[[logout-token-validation]]
=== Logout Token Validation

_See Requirement xref:requirements.adoc#VALIDATION-13.4[VALIDATION-13.4: Logout Token Validation]_

`LogoutTokenValidator` validates a logout token of https://openid.net/specs/openid-connect-backchannel-1_0.html[OpenID Connect Back-Channel Logout 1.0] on top of the <<signature-only-verification,signature-only entry>>. It runs these checks in a fixed order and refuses the token with the first `LogoutTokenCheck` that fails:

[cols="1,3", options="header"]
|===
|Check |Refused when
|`SIGNATURE` |The signature-only entry refuses the token: empty or oversized, unknown or unavailable issuer, refused header, or invalid signature. The precise reason is counted as a security event by `verifySignature`.
|`TYPE` |A `typ` header is present and is neither `logout+jwt` nor `application/logout+jwt`, compared case-insensitively.
|`ISSUER` |`iss` is not the expected issuer.
|`AUDIENCE` |`aud`, a string or an array, does not contain the expected audience.
|`ISSUED_AT` |`iat` is absent, not a number, or further than the freshness window before or after now.
|`EXPIRATION` |`exp` is absent, not a number, or before now.
|`EVENTS` |`events` is not a JSON object whose `http://schemas.openid.net/event/backchannel-logout` member is a JSON object. The claim is read as JSON, never scanned as text.
|`NONCE` |`nonce` is present.
|`SUBJECT_OR_SESSION` |Neither `sub` nor `sid` is a non-blank string, or one of them is present as anything else.
|`JWT_ID` |`jti` is absent or not a non-blank string.
|`REPLAYED` / `REPLAY_GUARD_FULL` |The <<logout-replay-guard,replay guard>> refuses the `jti`.
|===

*Absent `typ` is accepted.* Back-Channel Logout 1.0 recommends `typ: logout+jwt` but does not require it, and many OpenID Providers omit it. Requiring it would refuse their legitimate logout tokens, so a present `typ` is checked and an absent one passes.

*`events` and the absent `nonce` close ID-token confusion.* An ID token from the same issuer for the same audience is signed by the same key and carries `iss`, `aud`, `iat`, `exp` and `sub`, so with an absent `typ` it would otherwise pass as a logout token. An ID token carries no `events` member with the back-channel logout event, which refuses it as `EVENTS`; and an ID token carries `nonce` whenever the client sent one in its authentication request, which a logout token must not, so such a token is refused as `NONCE` as well. The two checks refuse an ID token presented as a logout token even when `typ` is absent. The reverse direction is closed by the token pipelines: the logout-token validator never produces a `TokenContent`, so its result cannot be used where an ID-token verdict is expected.

The validator does not log and the refusal carries no text taken from the token, so a caller can log or meter the bounded `LogoutTokenCheck` value safely. Receiving the logout request over HTTP and ending the session the token names stay with the consuming application.

[[logout-replay-guard]]
=== Logout Replay Guard

_See Requirement xref:requirements.adoc#VALIDATION-13.5[VALIDATION-13.5: Logout Token Replay Guard]_

`LogoutTokenReplayGuard` keeps the SHA-256 digest of each admitted `jti`, never the `jti` itself, until `iat` plus the freshness window. A token is not accepted after that instant anyway, because the `ISSUED_AT` check refuses it, so the retention covers exactly the period in which a replay could otherwise succeed. A `jti` still retained is refused as `REPLAYED`.

The guard is bounded by a capacity of live entries and *fails closed*: when it is full, a new `jti` is refused as `REPLAY_GUARD_FULL` and no live entry is evicted to make room, because forgetting a live entry early would let its token be replayed. Expired entries are purged on every admission, which is how capacity is regained. Size the capacity above the number of logout tokens an issuer can send within twice the freshness window; a guard that reports `REPLAY_GUARD_FULL` refuses new logouts until entries expire. The guard is consulted last, so a token refused by any other check never takes capacity.

An admission - purge, look up, test capacity, insert - is one critical section under a private monitor, so no two threads admit the same `jti` or both take the last free entry.

== JWT Attack Mitigations

[cols="1,2,2,1", options="header"]
|===
|Attack |Description |Mitigation |Test Class
|Signature Not Verified |Skipping signature check |Mandatory `TokenSignatureValidator` in pipeline; no public decode-without-verify API |`TokenSignatureValidatorTest`
|None Algorithm |`alg: none` bypass |Explicit rejection in `SignatureAlgorithmPreferences` |`TokenSignatureValidatorAlgorithmTest`
|Weak HMAC Keys |Brute-forceable shared secrets |HMAC algorithms rejected; asymmetric-only |`KeyDisclosureVulnerabilityTest`
|Algorithm Confusion |RSA-to-HMAC downgrade |HMAC rejected; algorithm-key type matching enforced |`TokenSignatureValidatorTest`
|KID Injection |Path traversal / SQL injection via `kid` |Pre-loaded keys; no dynamic file/DB lookup; `kid` validation |`KeyInjectionAttackTest`
|Embedded JWK (CVE-2018-0114) |Attacker key in token header |`jwk` header rejected; keys only from trusted sources |`EmbeddedJwkAttackTest`
|JKU/X5U Abuse |Attacker-controlled key URLs |`jku`/`x5u` headers ignored; URLs configured at init only |`JkuX5uAttackTest`
|Psychic Signature (CVE-2022-21449) |Zero-value ECDSA bypass |Java 21 JDK providers with fix; ECDSA parameter validation |`PsychicSignatureAttackTest`
|===

== Best Practices for Integrators

=== Token Handling

* **Always use `TokenValidator`** - never decode tokens without validation
* **Do not treat `verifySignature` as authentication** - its result carries no claim verdict; see <<signature-only-verification>>
* **Configure audience validation** - set `expectedAudience` to your resource server identifier
* **Configure issuer validation** - only trust known identity providers
* **Use short token lifetimes** - 5-15 minutes for access tokens

=== Algorithm Configuration

* Prefer ECDSA (ES256) or EdDSA for new deployments
* Explicitly specify allowed algorithms per issuer
* The library rejects HMAC and "none" by default

=== Key Management

* Store private keys in secure key management services (KMS, Vault)
* Plan for key rotation; the library supports grace periods (default 5 min)
* Use HTTPS-only JWKS endpoints

=== Monitoring

* Monitor `SecurityEventCounter` metrics for anomalies
* Log validation failures (the library sanitizes sensitive data from logs)
* Set up alerts for high rates of signature/claims failures

=== Common Pitfalls

[source,java]
----
// NEVER: Decode tokens manually without verification
String[] parts = token.split("\\.");
String payload = new String(Base64.getDecoder().decode(parts[1]));

// ALWAYS: Use the validation pipeline
AccessTokenContent token = validator.createAccessToken(AccessTokenRequest.of(tokenString));
----

[[security-events-monitoring]]
== Security Events Monitoring

The `SecurityEventCounter` tracks events with categories defined in `EventCategory`:

* **INVALID_STRUCTURE** - Malformed tokens, size violations (HTTP 401)
* **INVALID_SIGNATURE** - Signature verification failures, missing keys (HTTP 401)
* **SEMANTIC_ISSUES** - Expired, wrong audience, missing claims (HTTP 401)

In Quarkus, these are exposed as Micrometer counters for Prometheus/Grafana alerting.
