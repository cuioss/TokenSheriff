= Test-Cycle Duration Analysis

Analysis date: 2026-10-09. Analysed revision: `b031ec36` (branch `main`).
Status: analysis with a ranked proposal list. Two proposals in the shared organisation workflows are implemented (see xref:implemented[Implemented]); the others await a decision. The baseline and findings chapters describe revision `b031ec36`, before those two changes.

The constraint every proposal is held to: test quality stays the same or improves. No test is removed or weakened unless another named test demonstrably proves the same behaviour, coverage does not drop, no real wait is shortened into a flake, and no gating test moves to a non-gating lane. A speed-up that works by running less is reported as a finding, not proposed.

== Summary

[cols="3,1,1",options="header"]
|===
|Pull request until all three required checks are green (analysed revision) |Median |p90

|Contributor pull request (Sonar runs; 10 commits) |32m05s |65m59s
|Dependabot pull request (Sonar skipped; 12 commits) |11m04s |18m36s
|Merge queue, second pass (24 commits) |11m03s |17m30s
|===

The time is not spent executing tests. It goes to five things:

. *The same 3,119 unit tests run three times per contributor pull request, and at the analysed revision two of those runs were sequential.* `sonar-build` (≈10 min) started only after `build` (≈9.5 min) had finished and repeated the identical `verify`. This ordering lived in the shared organisation workflow and has since been removed (see xref:implemented[Implemented]); the third run itself remains.
. *About six minutes pass before the first build leg starts.* On contributor pull requests the median gap between trigger and build start is ≈350 s, almost all of it three chained helper jobs waiting for a runner. Measured, not explained, and addressed by no proposal.
. *`token-sheriff-validation-quarkus` spends ≈223 of its 273 surefire seconds outside any test.* Every test class runs in its own JVM (`reuseForks=false`), and each of the nine `@QuarkusTest` JVMs then waits in a 10-second `quarkus-jacoco` shutdown timeout for a data file that is never written.
. *`token-sheriff-validation` spends ≈75 of its 136 surefire seconds in HTTP retry backoff.* Five test methods each wait ≈15 s (1 + 2 + 4 + 8 s) because they hit a failing endpoint with the default retry configuration. No assertion depends on the delay.
. *The integration-test lane forks one JVM per IT class as well* (≈45 s), and one IT waits ≈37 s for a real token to expire while nothing else runs.

No proposal removes or weakens a test. The genuine duplicates found cost milliseconds; they are listed in xref:duplicate-pairs[the appendix] for hygiene, not as duration levers.

Estimated effect of the open proposals: those that touch the build lane take one build leg from ≈8m05s to ≈3m15s of Maven time, so the build lane's job time falls from ≈10 min to ≈5 min. Time until green cannot fall below the slowest required lane, which is then the integration-test lane at ≈11 min today. All savings are estimates until measured on CI.

=== Critical path

On a contributor pull request `maven.yml` decides: `gate` -> `config` -> `check-changes` -> `build` -> `sonar-build` -> `conclusion`. `sonar-build` declares `needs: [config, check-changes, build]` in the reusable workflow, so the two full builds run in sequence. On a Dependabot pull request and in the merge queue Sonar does not run, and `maven.yml` still finishes last (22 of 24 merge-queue commits).

=== The Java 21 + 25 matrix

Both legs run `./mvnw verify -Dmaven.compiler.release=<version>` and execute the identical 3,119 tests in near-identical time (489 s and 484 s). No test in the repository is conditional on the Java version, so the legs are identical by construction. They run in parallel: the second leg costs runner minutes but no wall-clock.

What the second leg proves: the code compiles at release level 25 and the suite passes on a JDK 25 runtime. That is a real, distinct claim.

What is duplicated: `sonar-build` runs on Java 21 and repeats the Java 21 leg completely, adding only the JaCoCo report and the Sonar upload. This third run is the redundant one, and on contributor pull requests it is on the critical path.

== Findings

Paths are relative to the repository root. `VQ` abbreviates `token-sheriff-quarkus-parent/token-sheriff-validation-quarkus`, `IT` abbreviates `token-sheriff-quarkus-parent/token-sheriff-quarkus-integration-tests`.

=== A. Technical and architectural problems

==== A1. Retry backoff inside unit tests (≈75 s per build leg)

`RetryConfig.defaults()` of `cui-http` is five attempts with delays of 1, 2, 4 and 8 s. Five test methods run into it:

[cols="4,2,3",options="header"]
|===
|Method |Trigger |Fixable

|`HttpJwksLoaderSchedulerTest#shouldNotStartSchedulerIfInitialLoadFails` (`:309-336`) |HTTP 500 on a direct JWKS URL |Test-only: the builder accepts a `retryConfig`
|`HttpJwksLoaderFailureTest#shouldLogJwksLoadFailedWhenHttpConnectionFails` (`:60-84`) |real DNS lookup of an invalid host |Test-only
|`HttpJwksLoaderIssuerTest#shouldReturnEmptyWhenWellKnownConfigUnhealthy` (`:89-109`) |HTTP 500 on discovery |Blocked, see below
|`HttpJwksLoaderIssuerTest#shouldReturnEmptyWhenConfigReturnsEmptyIssuer` (`:208-222`) |real DNS lookup |Blocked
|`HttpJwksLoaderWellKnownAsyncTest#wellKnownDiscoveryFailureShouldBeHandledAsync` (`:68-100`) |real DNS lookup |Blocked
|===

None of these asserts the delay. The ones that assert `REQUEST_FAILED_MAX_ATTEMPTS` stay green with a fast configuration, because that message is logged whenever the last attempt fails.

The three discovery cases are blocked by production code: `token-sheriff-validation/src/main/java/de/cuioss/sheriff/token/commons/transport/HttpJwksLoaderConfig.java:751` hardcodes `.retryConfig(RetryConfig.defaults())` for the well-known configuration, so a caller's `retryConfig` silently does not apply to discovery. That is a finding in its own right: the Quarkus `IssuerConfigResolver` passes a retry configuration that takes effect for JWKS fetches only.

Three of the five tests also depend on real DNS answering NXDOMAIN quickly; they are not hermetic.

==== A2. Real clock where a seam exists (≈23 s per build leg)

* `HttpJwksLoader` schedules its refresh in whole seconds, so every "rotate, then wait for the new key" test costs ≈1.05 s. Eleven such tests exist in `HttpJwksLoaderKeyRotationTest` and `HttpJwksLoaderGracePeriodTest`. `performBackgroundRefresh()` is package-private and callable from the tests; only `HttpJwksLoaderEgressRefreshTest` uses it. ≈13 s.
* `HttpJwksLoaderLockFreeStatusTest:157` and `:269` let 50 observer threads spin for a fixed 5 s and 3 s although initialisation completes in milliseconds. ≈7.7 s.
* `HttpJwksLoaderSchedulerTest#shouldHandleBackgroundRefreshCorrectly` waits a fixed 1.2 s and then asserts a log line the initial load already produced (see xref:quality-findings[C5]). ≈1.2 s.
* `AccessTokenCacheTest:614-667` waits for a real 1 s eviction tick although the scheduler is injectable. ≈1 s.
* `DpopReplayProtectionTest:66-77` waits out a real 1 s TTL; `DpopReplayProtection` takes whole seconds and has no clock seam. ≈1 s; removing it needs a production seam, so it is left alone.

Inherent and to be kept: `HttpJwksLoaderSchedulerTest#shouldPerformBackgroundRefresh` (the one proof that the real scheduler fires) and one real grace-period expiry wait.

==== A3. Tests at the wrong level

No behaviour was found that is proven *only* through a Quarkus boot, a container or the native image while being unit-level logic. The opposite pattern exists and is harmless in time once forks are shared:

* Container-free logic inside `@QuarkusTest` classes: four of six methods in `JwtMetricsCollectorTest`, six of thirteen in `JwksEndpointHealthCheckTest`, the `ResolutionOutcomeMatrix` in `TokenValidatorHealthCheckTest`, and seven `TestConfigIntegrationTests` in `TokenSheriffDevUIRuntimeServiceTest` that exercise test helpers only.
* 38 of the 135 integration tests (22 of 30 classes, package `client`) never call the native application. They run production client code in the test JVM against Keycloak, but they wait for the native build like everything else.

==== A4. Environments

The stack is started once and stopped once per run; no test reconfigures it. All services are justified:

* Zitadel (with its database) serves 3 effective tests, Dex 5, all in `TokenValidationSpecIT`. They are the only coverage of a third identity provider, an HTTP JWKS endpoint and `offline_access`. Deliberate, not duplicate.
* Prometheus is started but unused by the IT lane (only the benchmark lane reads it). It costs no wall-clock, because its pull finishes before Keycloak's.

Two accidental costs in the start sequence:

* The application container starts as soon as Keycloak is healthy, before Zitadel has published its signing key. The application loads an empty key set and waits for its 10 s background refresh. The start script's verification loop succeeded on attempt 9 or 10 in 6 of 8 runs, on attempt 1 in the other two. ≈7 s on average.
* Keycloak runs `start-dev --import-realm` with four realms: 25-36 s until healthy, quantised by a 5 s health-check interval.

==== A5. Real sockets and TLS

Every real-socket test examined has the socket as its subject: the five real-TLS tests in the client module prove handshake outcomes (the in-memory `BackChannelHttpTlsTrustTest` proves only that configuration is forwarded), and the closed-port test proves classification of a refused connection. Combined cost ≈1.5 s. No change proposed.

`JwksLoaderFactoryTest:67-92` fetches from the real `https://example.com`; cheap (≈0.35 s) but not hermetic.

=== B. Grouping and infrastructure restarts

==== B1. One JVM per test class in every Quarkus module

`token-sheriff-quarkus-parent/pom.xml:179-181` sets `useSystemClassLoader=false` and `reuseForks=false` for surefire, under the comment "Fix for class loading issues"; `:199-201` does the same for failsafe. `forkCount` stays at 1, so the classes run strictly in sequence, each in a fresh JVM. Git history gives no rationale; the sibling project carries the same lines as copied scaffolding.

In a shared JVM the grouping would be automatic: `quarkus-junit` ships `QuarkusTestProfileAwareClassOrderer` as the default class orderer, and the repository does not override it.

What stands in the way of sharing a JVM, from reading the sources:

* 21 classes of the module use `@EnableTestLogger`, which installs a JVM-global JUL handler. In one shared JVM they would run in the same process as a Quarkus application and its JBoss log manager. Whether that interferes was not observed; it is the main risk.
* The unexplained "class loading issues" may still exist.
* Application-scoped state would be shared across the eight `JwtTestProfile` classes: the `SecurityEventCounter`, the 30 s health cache, the meter registry. No absolute-count assertion on injected beans was found.
* Not a blocker here: no test in this module swaps trust-store system properties, and no port is fixed.

Two reused forks - one for the 29 plain classes, one for the 9 Quarkus classes - avoid the first risk entirely and cost one extra JVM start.

The deployment module boots four `QuarkusExtensionTest` applications, the minimum for four such classes with different configurations.

==== B2. The 10-second `quarkus-jacoco` shutdown timeout

`VQ/pom.xml:88-92` adds `quarkus-jacoco` while `jacoco:prepare-agent` is active as well. The extension registers a shutdown hook that waits for `target/jacoco-quarkus.exec` to change, polling every 100 ms for at most 10 s. The file is never written. After a local run `VQ/target/jacoco-report/error.txt` reads:

----
Timed out waiting for Jacoco data file .../target/jacoco-quarkus.exec update,
file size before test run: did not exist, current file size: does not exist
----

followed by Quarkus's own advice to set `quarkus.jacoco.report=false`. Only `jacoco.exec` exists in `target/`.

The three gap sizes in the CI log between test classes are thereby explained exactly:

[cols="1,2,4",options="header"]
|===
|Gap |Transition |Composition

|≈7.7 s |plain class -> `@QuarkusTest` class |new JVM, JaCoCo agent, Quarkus augmentation and boot
|≈13.3 s |`@QuarkusTest` class -> plain class |teardown 11.5 s (10.0 s of it the timeout) + plain JVM start 1.7 s
|≈19.2 s |`@QuarkusTest` -> `@QuarkusTest` |teardown 11.5 s + boot 7.7 s

The sibling project has the same dependency pair and shows the same signature in its CI logs (13 s, 21 s and 2 s) and the same message after a local run.

Why the data file is never written was not established. The module sets `quarkus.jacoco.reuse-data-file=true` in `VQ/pom.xml:173` and in `VQ/src/test/resources/application.properties:11`, so the extension was configured deliberately at some point. The likely explanation is that the instrumented classes resolve the already initialised agent of `jacoco:prepare-agent`, so the data lands in `jacoco.exec`. If so, `@QuarkusTest` coverage is already in the report Sonar reads (`sonar.coverage.jacoco.xmlReportPaths` lists `target/site/jacoco/jacoco.xml` only) and the Quarkus-side report is empty and unused. A comment in `TokenSheriffDevUIRuntimeServiceUnitTest:38-40` assumes the opposite. Only a coverage comparison can settle it.

==== B3. Integration-test lane

* The stack starts once. The native image is built once per run, unconditionally: `IT/scripts/build-native-if-needed.sh:10-12` only checks whether a `*-runner` file exists, which is never the case on a fresh checkout. It is rebuilt when only tests changed, and up to four times per merged change. Nothing is cached or shared between lanes.
* Failsafe inherits `reuseForks=false`: 30 JVMs for 30 classes. 156.1 s of wall time minus 111.4 s of suite time leaves 44.7 s of pure fork overhead, and each fork repeats its first-use initialisation (RestAssured and Groovy, TLS, discovery), another ≈24-30 s. JaCoCo is not active in this lane.
* `TokenValidationSpecIT#verifySecurityEventCounterMetrics` asserts a cumulative lower bound on the single application instance. Under `multi-idp-tests` the class produces enough events by itself; under the plain `integration-tests` profile it depends on other classes having run first.
* The lane already builds the upstream modules with tests skipped and runs `verify` on the IT module alone; it does not repeat the unit suite.

==== B4. Parallelism settings and blockers

Outside the Quarkus parent, surefire runs with defaults: one reused fork, no `parallel`, no `junit-platform.properties`. JUnit parallel execution is off everywhere.

`forkCount > 1` is recorded in the maintainer's project notes as evaluated and rejected (timing flakes, JaCoCo data loss). No commit, issue or document in the repository records that decision; nothing found in this analysis contradicts it.

What prevents in-JVM parallel execution today:

* `@EnableTestLogger` installs one JVM-global log handler and clears it before each test. It is present on ≈86 classes in the validation module alone. Concurrent classes would satisfy each other's positive log assertions and break negative ones. This is the main blocker.
* `InMemoryKeyMaterialHandler.getKeyPair` is check-then-act on a static map (`:163-169`); two threads asking for the same new key id can receive different pairs.
* Static shared `SecurityEventCounter` instances with delta assertions (`TokenHeaderValidatorTest:53-56`, `TokenClaimValidatorTest:60-61`).
* Wall-clock assertions: constructor under 10 ms (`HttpJwksLoaderWellKnownAsyncTest:84`), health check under 100 ms (`JwksEndpointHealthCheckTest:379`), throughput bounds in `TokenValidatorMonitorTest` and the `IssuerConfigCache` performance tests.
* JVM-global trust-store properties in three TLS test classes of the validation and client modules; these are already `@Isolated`.

Ports are not a blocker: every MockWebServer and Quarkus test port is ephemeral.

After the proposed fixes the validation module is ≈35 s of mostly CPU-bound work. Parallel execution would buy little there and would put the log assertions at risk; it is not proposed.

=== C. Duplicates and overlap

Behaviour-to-test maps were built for JWKS loading and rotation, the validation pipeline (signature, header, claims, token types, claim mapping), JWE, DPoP, the attack tests, the Quarkus layer, the client refresh path and the integration tests. The result in one sentence: *there are genuine duplicates, and removing all of them would save less than five seconds.* No removal is proposed for the sake of duration.

==== C1. Genuine duplicates

62 pairs were found in which one test is covered by another with identical or stronger assertions at the same level. All are named with both tests and the covering assertion in xref:duplicate-pairs[the appendix].

Seven of the client pairs involve the named threat tests of `doc/client/specification/test-strategy.adoc` (`MixUpDefenseTest`, `CodeInjectionTest`); removing them would need the traceability re-pointed first.

==== C2. Deliberate defence in depth and different levels (keep)

* Unit, composite and wired proofs of the same rule: `ExpirationValidatorTest` / `TokenClaimValidatorEdgeCaseTest` / `WiredNegativePathAttackTest`; the embedded-JWK rejection with three different input shapes; the algorithm allow-list at catalog, preference, JCA and wired level.
* All six `ForeignValidatorObservabilityTest` methods have unit twins, but they are the proof that real container wiring never instantiates the default producer (regression for issue #641).
* Client refresh path: endpoint classification against manager disposition, with the matched negative controls documented in the tests.
* Integration tests against their unit counterparts: the IT adds the real authorization server (rotation, reuse detection, single flight).
* The only failsafe IT of the client module, `WiredFlowNegativePathIT`, is not redundant: it carries the only orchestrator-level proof of RFC 9207 `iss` enforcement and of DPoP on the refresh path.
* Four loader-level discovery-failure tests take the same loader branch with different failure causes (500, DNS, DNS, 404). Overlapping, cheap once the retry is fast, kept.

==== C3. Parameterised tests

No huge argument set exists. The largest are `OAuth2JWTBestPracticesComplianceTest` with `@TestTokenSource(count = 50)` twice (100 invocations, 2.6 s locally, all on one code path) and the client attack corpora (241 invocations, ≈1.3 s locally). Several `@TestTokenSource(count = 2..5)` tests ignore the generated variation. Total cost well under 3 s; a quality note, not a duration lever.

[[quality-findings]]
==== C4. Tests that do not prove what they claim

These cost nothing to speak of, but the constraint is that quality stays the same *or improves*, so they are recorded:

* `HttpJwksLoaderSchedulerTest#shouldHandleBackgroundRefreshCorrectly` (`:340-381`): the expected message does not exist in production code; the fallback assertion is satisfied by the initial load. The test passes without any background refresh.
* `JwksEndpointHealthCheckTest#healthCheckCacheExpiration` (`:294-322`): an Awaitility call without `until` never runs, and the constructor argument is seconds, not milliseconds. Cache expiry is never exercised.
* `JwksEndpointHealthCheckTest#concurrentHealthCheckCalls`: three sequential calls.
* `EmbeddedJwkAttackTest:91-92`: `assertTrue(count >= 0)`. This is the only test of the real-world JSON-object shape of an embedded JWK.
* `TokenValidationSecurityTest#shouldRejectTokensWithTamperedPayloads` and `#shouldRejectTokensWithMissingRequiredClaims` both drop the signature and so are rejected by the parser; neither reaches the check its name states.
* All eleven "warm-up race" methods of the four `IssuerConfigCache` concurrency classes and both `TokenValidatorConcurrencyTest` methods read an already immutable map; the named race is unreachable.
* `NativeTokenValidatorProducerIT` never runs (its module binds no failsafe execution) and its body is `assert true`.
* `TokenSheriffDevUIIntegrationTest` probably never runs the Dev-UI build steps it is named for; they are guarded by `IsDevelopment`.
* Coverage gaps found while mapping: no test performs two key rotations, so the retired-key-set cap and the expired-set cleanup in `HttpJwksLoader` are never exercised; no test sends or asserts an ETag / 304 response; no test asserts that `MISSING_RECOMMENDED_ELEMENT` is ever counted.

[[fixtures]]
==== D2. Shared fixtures every JVM pays for

* *`InMemoryKeyMaterialHandler`* (validation `generators` test-jar, `:102-113`) eagerly generates ten key pairs in a static initialiser, including two RSA-4096 and two RSA-3072 pairs, although a lazy get-or-generate path exists at `:163-169`. Whichever test touches it first in a JVM pays ≈3-4 s on CI (inferred from first-toucher class times). That is once in the validation module, twice in the client module (surefire and failsafe), and once in each per-class JVM of the Quarkus module that uses test tokens. Consumers of the test-jar pay it too: the sibling project forks per class and measured 3-4.5 s in each of 15 classes. The key sizes follow from JJWT's defaults and were not inspected in the JJWT source.
* *Per-test RSA key generation*: ≈93 generations in the validation pipeline, JWE, DPoP and attack tests and 58 in three client classes, at ≈0.1 s each on CI. In all of them the key is a fixture, not the subject. `KeyInjectionAttackTest#shouldRejectTokenWithMaliciousKidHeader` hides five generations, because every unknown key id triggers a new pair.
* MockWebServer is created per test; cost is single-digit milliseconds. Not worth changing.
* `DecryptionKeyLoaderTest:85-134` spawns `keytool` twice as a subprocess (≈2-4 s, estimated).
* Integration tests acquire one token per test (≈80 password grants at 0.1-0.3 s). This keeps tests independent and is cheap; no change proposed.

=== Why test quality is unchanged or better, per proposal

P2:: No test is touched. The condition is that coverage does not move: `target/site/jacoco/jacoco.xml` of the module must show the same covered instructions and branches per class before and after, and the SonarCloud figure must not drop. The change is `quarkus.jacoco.report=false`; the extension and its `reuse-data-file` setting stay until the cause of the missing data file is understood. If the comparison shows that `@QuarkusTest` coverage is *not* in `jacoco.exec` today, the right fix is the Quarkus-documented alignment of agent and data file, which raises reported coverage.

P3:: The same 38 classes and 405 tests run. The nine Quarkus classes boot two applications instead of nine; plain classes never share a JVM with a Quarkus application. Conditions: the test count stays at 405, the coverage report is identical, and no test turns out to depend on a fresh JVM. The guard test turns today's undocumented side effect into a declared rule. If the "class loading issues" resurface, they show as a failing build, not as a silent loss.

P4:: Same classes, same Keycloak image and realms. Quality is unchanged only if the new job feeds a required check; otherwise 38 gating tests would become non-gating.

P5:: The tests keep every assertion. The production change makes discovery honour a retry configuration the caller has set; callers who set none keep today's default. It needs a new test that pins the propagation, which is a gain. It is a behaviour change for the Quarkus integration, whose configured retry settings start applying to discovery.

P6:: Same number of attempts, same failure path, same log assertions. Only the sleep between attempts shrinks. Pointing the DNS-based case at a closed loopback port additionally makes it hermetic.

P7:: The same 135 tests run with 3 skips; JaCoCo is not active in this lane. The static caches involved are a concurrent discovery cache and identical RestAssured configuration.

P9:: Every assertion is kept and still observes a real expiry of the declared 35 s. No wait is shortened. `TokenValidationSpecIT#verifySecurityEventCounterMetrics` must stay sequential and last, because it asserts a cumulative count.

P10:: The keys are fixtures. Distinct keys are kept wherever "the wrong key" is the subject (`DpopProofValidatorTest#shouldRejectInvalidSignature`, `JweDecryptorTest#shouldFailWithWrongKey`, `WiredNegativePathAttackTest` VTEST-6/9/14, `JkuX5uAttackTest`), explicit weak key sizes stay in `KeyInjectionAttackTest`, and replay protection stays per test. Lazy generation must become atomic (`computeIfAbsent`), which also removes a latent race. The refresh-path coverage gates are unaffected because no test logic changes.

P11:: Better: the tests become deterministic instead of polling a 1 s scheduler. `HttpJwksLoaderSchedulerTest#shouldPerformBackgroundRefresh` stays on the real scheduler as the proof of wiring, and one real grace-period expiry wait stays. The synchronous seam also makes it cheap to add the missing two-rotation test for the retired-set cap.

P12:: Lint, format check and Jest stay enforced by all three `maven.yml` jobs, which are a required check. The two lanes consume no generated frontend output; the Dev-UI sources are served from `src/main/resources`.

P13:: Nothing in the IT lane asserts JFR. `-Ob` keeps reachability and reflection analysis identical but changes the optimisation tier; whether that is acceptable for the gating image is a judgement call, hence "measure, then decide".

P14:: Better: observers run until the initialisation future completes and then perform a fixed number of extra reads, which covers the whole status transition by construction instead of by timing. All existing assertions stay.

P15:: The scheduler test starts asserting a real background refresh instead of the initial load: better. The eviction test becomes deterministic. The ArchUnit guard keeps a byte-identical import scope and its non-vacuity check.

* `benchmark.yml` was measured but not analysed structurally; it is not gating.

=== Measured and found fine

* Dependency caches hit on every sampled run.
* The compose stack starts once and is never reconfigured.
* The integration-test lane does not repeat the unit suite.
* The Java 25 leg costs no wall-clock, and no test is conditional on the Java version.
* Flaky-test reruns are not a material cost (5 re-run attempts in 312 runs).
* No `Thread.sleep` exists in any test of the validation, client or Quarkus modules or in the integration tests; the waits are Awaitility polls, latches and production retry.
* The real-socket and real-TLS tests are cheap and have the socket as their subject.
